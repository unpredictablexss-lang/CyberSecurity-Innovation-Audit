# OHScanner 面板操作手册：源码端点选择与比较

## 1. 目的与适用范围

本文说明如何在 OHScanner Web 工作台中选择并比较源码端点，覆盖三种操作：

- **跨分支比较**：选择同一已登记仓库的两个分支、Tag 或 Commit。
- **提交者日期区间**：按时区、提交者时间和 first-parent 主线选择时间窗口，再扫描窗口两端。
- **两个 SHA 区间**：以完整 Git 对象 ID 指定基准提交和目标提交。

页面路由以工作台根地址为基准，使用 URL hash：

| 功能 | 页面路由 | 创建操作的 API 路径 |
|---|---|---|
| 跨分支比较 | `#/audits/versions` | `POST /api/v1/operations/branch-comparisons` |
| 提交者日期区间 | `#/audits/time` | 预览：`POST /api/v1/operations/date-ranges/preview`；创建：`POST /api/v1/operations/date-ranges` |
| 两个 SHA 区间 | `#/operations` → **两个 SHA 区间** | `POST /api/v1/operations/revision-ranges` |
| 查询仓库可用版本 | — | `GET /api/v1/repositories/{repository_id}/revisions` |

本手册截图分为两类：图 1–3 使用本机合成 Git fixture，仅说明端点操作页面，不代表真实漏洞发现；图 4–7 来自隔离工作台对 OpenHarmony 镜像中的 libpng 组件执行的真实静态扫描。图 4–7 保留了仓库标签、固定提交、报告状态、候选详情和复核状态。仓库标签不等同于产品身份核验，组件级候选也不等同于 OpenHarmony 产品漏洞或总体准确率结论。

## 2. 术语与端点模型

- **基准端点（baseline）**：比较的起始源码快照。
- **目标端点（endpoint）**：比较的目标源码快照。
- **Ref**：Git 分支、Tag 或 Commit 引用。分支是可移动引用；操作创建时会解析 Ref，并将解析得到的 Commit ID 固定到操作记录。
- **固定版本**：已解析的完整 Commit ID。仓库后续更新分支不会改变既有操作绑定的源码版本。
- **端点扫描**：对基准和目标两个固定源码快照分别执行扫描。跨分支比较和 SHA 区间只扫描两个端点，不逐提交扫描区间内的每个 Commit。

候选变化是两个静态扫描快照之间的观察差异。它本身不证明漏洞何时引入、是否已修复、是否可由产品入口触达，也不证明受影响的产品版本。

## 3. 操作前检查

1. 确认工作台服务可访问。
2. 在**系统设置 → 仓库与源码管理**登记本地 Git 仓库，并确认该仓库通过可用性核验。页面选择器只列出通过核验的仓库。
3. 确认所需分支、Tag 或 Commit 已存在于登记仓库中。页面 Ref 选项来自该仓库当前可读取的版本列表。
4. 选择本次审计方式。默认是**静态审计**：只执行本地检测器，不调用模型，也不发送源码。
5. 展开**高级范围与调查设置 → 范围与执行预算**，核对纳入路径、单端点超时和内存预算。默认纳入路径为 `.`（仓库根目录）；API 对单端点超时的约束为 30–3600 秒，地址空间上限为 256–8192 MiB。常规页面扫描最多处理 2,000 个源码文件、总源码 32 MiB；超限会明确失败。

检测器需至少选择一个可用项。默认关闭的研究规则需要显式开启研究模式；任务报告会记录实际规则版本、解析覆盖和未分析范围。

## 4. 跨分支比较

**适用情形：** 比较同一仓库中两个分支、Tag 或 Commit 的端点快照；不要求按祖先区间逐提交扫描。

### 操作步骤

1. 打开 `#/audits/versions`，确认选中**跨分支比较**页签。
2. 在**审计仓库**选择已登记且通过核验的仓库。
3. 在**基准版本**选择比较起点，在**目标版本**选择比较终点。可以从候选列表选择，也可以输入 Ref 或完整 Commit SHA。
4. 核对静态审计模式及高级范围参数。
5. 点击**扫描并比较两个端点**。此操作会创建持久化比较任务，并分别排入两个固定端点的扫描。
6. 在下方**操作任务**列表查看状态；打开任务详情核对解析后的 Commit ID、两个扫描报告、源码变化和候选比较结果。

两个 Ref 必须解析到不同 Commit。提交时解析并冻结版本；仅预览页面而未提交时不会创建任务。跨分支比较不要求基准是目标的祖先；如果需要严格的祖先区间语义，使用 SHA 区间操作。

## 5. 提交者日期区间

**适用情形：** 依据提交者时间在某一分支主线上选择提交窗口，并扫描该窗口固定的基准与目标端点。该操作不是逐提交扫描。

### 操作步骤

1. 打开 `#/audits/time`，选择**提交者日期区间**页签。
2. 选择审计仓库和分支或 Tag。
3. 输入**开始时间（包含）**、**结束时间（不包含）**及所选时间的时区。默认时区为 `Asia/Shanghai`；页面支持 `Asia/Shanghai`、`UTC`、`America/Los_Angeles` 和 `Europe/London`。
4. 点击**预览时间范围（可选）**。检查选中提交数、区间 `[start, end)`、拓扑跨度外提交数，以及展开**技术详情：固定提交**后显示的基线和终点 Commit。
5. 预览符合预期后，再点击**固定区间并创建任务**。提交阶段会重新解析时间窗口并固定版本；如果分支在预览后发生移动，最终固定端点可能与预览不同。因此应在创建后以操作详情中的固定 Commit 为准。

服务端以 Git **committer time** 转换到指定时区，在 **first-parent** 历史上应用左闭右开边界 `[start, end)`。基线是最早选中提交的父提交，终点是主线顺序中最新的选中提交。若两个端点之间有提交落在所选时间之外，预览会单独计数并在响应中列出。被选中的提交数是区间选择信息，不代表逐提交扫描覆盖。

预览请求是只读计算：`POST /api/v1/operations/date-ranges/preview` 不创建操作或扫描任务。创建请求为 `POST /api/v1/operations/date-ranges`。日期选择最多检查 5,000 个 first-parent 历史提交；若该分支从当前 tip 向后的可检查历史超过此限制，服务端会拒绝日期选择。无提交命中或最早命中提交没有父提交时也会拒绝该时间窗口。SHA 区间另行限制为最多 5,000 个 first-parent 区间提交。

![提交者日期区间页面：时间边界、时区和固定端点预览](images/endpoint-date-range-preview.jpg)

*图 2. 日期区间预览示例。预览选中 1 个合成提交，并展示基线和终点的 Commit 前缀；操作任务列表仍为空。*

## 6. 两个 SHA 区间

**适用情形：** 已知两个完整 Commit ID，并且基准提交是目标提交的祖先；需要比较固定的历史区间端点。

### 操作步骤

1. 打开 `#/operations`，切换到**两个 SHA 区间**。
2. 选择已登记仓库。
3. 填写**基准版本完整 SHA**和**目标版本完整 SHA**。API 接受 40 位或 64 位小写十六进制 Git 对象 ID；不要用分支名、Tag 名或缩写 SHA 代替。
4. 核对审计方式、纳入路径、检测器和执行预算。
5. 点击**扫描并比较两个端点**，然后从**操作任务**进入结果详情。

服务端会验证基准 Commit 是目标 Commit 的祖先；若不是，创建会失败，应改用跨分支比较或在具有关联案例的场景使用版本矩阵。SHA 区间最多允许 5,000 个 first-parent 提交。系统计算区间提交列表用于记录与校验，但只对指定的基准和目标两个端点运行扫描。

## 7. API 字段与服务端约束

| 参数 | 用途与约束 |
|---|---|
| `repository_id` | 已登记仓库标识；仓库必须通过路径、Git 对象和源码根目录授权核验。 |
| `baseline_ref`、`endpoint_ref` | 跨分支比较的基准与目标 Ref，各自解析为固定 Commit；两者不能解析到同一 Commit。 |
| `baseline`、`endpoint` | SHA 区间的完整 Commit ID，格式为 40 或 64 位小写十六进制；基准必须是目标的祖先。 |
| `branch`、`start`、`end`、`timezone` | 日期区间参数；时间边界为左闭右开，按 committer time 和 first-parent 选择。 |
| `include_paths` | 纳入扫描的路径列表；默认 `["."]` 表示仓库根目录。 |
| `detector_ids` | 本次使用的检测器 ID 列表；至少一个可用检测器。报告记录检测器版本和覆盖信息。 |
| `timeout_seconds` | 单端点扫描超时，30–3,600 秒；默认 600 秒。 |
| `memory_mb` | 单端点地址空间预算，256–8,192 MiB；默认 2,048 MiB。 |

任务创建 API 使用 JSON 请求并返回持久化操作记录。日期预览 API 返回所选提交、固定基线和终点、时区、边界、first-parent 拓扑以及区间外的中间提交列表；其返回值是预览数据，不是扫描结果。

## 8. 结果解释与审计记录

1. 先查看比较操作状态，再分别检查两个端点扫描的状态、报告、固定 Commit、源码快照摘要、检测器版本和覆盖率。
2. 端点扫描失败或取消时，比较结果会保持阻塞或未知；不能将缺失报告解释为无候选或安全。
3. 候选比较按检测器、规则、文件路径和符号匹配。文件重命名会参与路径归一化。输出可能包含：
   - `persistent_candidate`：两侧各有一个匹配候选且检测器版本一致。
   - `new_candidate` / `disappeared_candidate`：一侧出现候选，且对应端点对该范围具有足够覆盖。
   - `unknown`：覆盖不足、匹配存在歧义或其他条件不足以定性。
   - `unknown_detector_version_changed`：候选跨端点存在，但检测器版本发生变化。
4. 上述状态描述的是**候选观察差异**。系统将 `vulnerability_introduced_or_fixed` 和产品 `impact` 保持为 `unknown`；漏洞是否成立、由哪个版本引入或修复、影响哪些产品版本，需要结合源码、调用路径、构建配置和适用的运行时证据另行核实。
5. `completed` 或 `completed_with_limitations` 表示操作流程状态，不代表漏洞已确认，也不代表未分析范围安全。无候选、候选消失或扫描完成都不能单独作为安全结论。

## 9. 静态审计与智能审计

- **静态审计**：默认模式，仅运行本地检测器，不调用模型、不发送源码。适用于本手册的常规端点扫描。
- **智能审计**：先固定端点并展示模型目的地、源码范围、候选上限及授权摘要；每个端点均需显式确认。预览不会发送源码，确认后才会进入受限模型调查流程。模型输出仍为待复核意见，不自动升级为已确认漏洞。

若没有明确的源码外发授权，保持静态审计模式。

## 10. 常见错误处理

| 现象 | 检查与处理 |
|---|---|
| 仓库选择器没有目标仓库 | 在仓库与源码管理中登记，并确认仓库可用性核验通过；不可用仓库不会进入选择器。 |
| Ref 候选列表没有目标版本 | 核对本地仓库是否包含该分支、Tag 或对象；同步后重新打开页面或刷新版本列表。 |
| 日期预览提示区间无提交 | 检查时区、边界和分支；开始时刻必须早于结束时刻，结束边界不计入窗口。 |
| 日期预览提示没有基线父提交 | 当前窗口最早命中的是无父提交的根提交；调整窗口或选用明确的端点操作。 |
| SHA 区间提示基准不是目标祖先 | 检查输入方向和提交 ID；需要比较分叉版本时改用跨分支比较。 |
| 操作失败或有局限地完成 | 打开操作及其端点扫描详情，检查失败原因、报告是否存在、检测器覆盖和未分析范围；对未检查内容保留 unknown。 |

## 11. 真实仓库演示：libpng 静态扫描

### 演示选择与固定范围

为演示已知漏洞信号的端到端流程，本例选择包含上游 libpng 组件的 OpenHarmony 镜像仓库。扫描版本固定到 `e57b1079564a02a50321ec528aa6e41884979d32`，Git Tree 为 `02b17492f4490ff2e4d17ba74e2080358a500059`；扫描任务为 `03da6fcc605845ebaf5a15c8fd595ef2`，纳入路径为仓库根目录 `.`，模式为**仅静态扫描**。该版本含 `libpng-1.6.55` 源码归档。检测器版本 `ohscanner.known_disclosed_cves 0.19.11` 对归档源码报告了 3 条已披露 CVE 候选：两条位于 `arm/palette_neon_intrinsics.c`（第 63、108 行），标识为 `CVE-2026-33636`；一条位于 `png.h:277`，标识为 `CVE-2026-46675`。

上游 libpng 安全公告将 `CVE-2026-33636` 评为 High，影响 1.6.36–1.6.55 的 ARM/AArch64 Neon 优化路径；当前归档版本落在该范围内。公告还规定该路径需要 Neon 编译配置，产品构建是否启用此路径尚未核实。[上游公告 GHSA-wjr5-c57x-95m2](https://github.com/pnggroup/libpng/security/advisories/GHSA-wjr5-c57x-95m2) 对应本例的两个源码候选位置。

`CVE-2026-46675` 的上游公告将其评为 Moderate，影响 1.6.0–1.6.58；公告中的受影响应用还需要满足特定顺序的顺序读取 API 调用条件。[上游公告 GHSA-qvg3-h654-xq3j](https://github.com/pnggroup/libpng/security/advisories/GHSA-qvg3-h654-xq3j)。版本字符串匹配只构成组件版本候选，不代表已证明产品调用路径。
