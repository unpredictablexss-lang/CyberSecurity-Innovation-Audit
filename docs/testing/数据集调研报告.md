# OpenHarmony C/C++ 静态分析测试数据集调研

> 调研日期：2026-10-09。用途：比较自研 text / Tree-sitter AST 扫描器、Semgrep、Cppcheck、Clang Static Analyzer、CodeQL 和 Joern。本文记录联网资料核查与实验建议，不代表数据已经导入、构建成功或实验已经完成。
>
> 本次只读取官方仓库、论文配套资料、项目文档及下载页面；未下载大型数据、未执行样本、未开展 PoC / 漏洞利用、未修改现有扫描实现。

## 1. 是否存在可直接使用的 OpenHarmony 专用漏洞集

**尚未核实到同时具备可靠漏洞标签、安全对照、固定源码版本和可复现构建，并可直接用于六类工具公平比较的 OpenHarmony 专用公开数据集。** 这不是断言不存在任何 OpenHarmony 研究数据。

查到两项专用资源，但需区分其性质：

- **OH-Bench**：公开可读的 OpenHarmony 静态告警修复基准，含 359 个 C/C++ 任务。告警修复任务不是已确认漏洞真值，也不提供独立安全负例。
- **SPLVD 论文的 OpenHarmony 子集**：论文报告 5 个项目、167 个漏洞函数及 574 个非漏洞函数；复制包本次访问失败，文件内容、许可证、版本字段和构建条件未核实。

官方安全公告是最可信的域内漏洞整理入口，但 **CVE 清单不等于可复现数据集**。必须进一步关联补丁、固定提交、根因、代码定位与构建条件。OpenHarmony 和 HarmonyOS 的漏洞记录也不能混用：只有能关联到公开 OpenHarmony 源码和固定版本的记录才能入选。本次未核实到可直接使用的 HarmonyOS 专用 C/C++ 数据包。

推荐首轮组合：**已有 OpenHarmony 修复对 + 人工核验的 PrimeVul 小子集 + Juliet 正负控制样例 + 少量 SV-Benchmarks 并发任务**。CVEfixes 用于追溯及补证，Magma 留作可构建真实项目的后续补充。

## 2. 已有数据与获取核查边界

项目背景由本次调研需求提供，未在本次调研中重新运行或核验：

- 4 个 OpenHarmony 历史漏洞修复对，共 8 个固定版本单元；根因涉及生命周期 / UAF、并发、空指针与越界写。
- 当前 c_utils 完整 C/C++ 扫描范围为 123 个文件。
- 21 个 Linux host 翻译单元已完成 Clang / CodeQL 编译分析。

这些数据可以验证工程链路及域内回归，但缺少独立样本和可靠安全对照，不能据此给出完整准确率、误报率或全组件语义覆盖结论。

本文的“可获取”按以下证据描述：

| 状态 | 本次证据 | 不包含的承诺 |
|---|---|---|
| 仓库 / 文档可读 | 成功读取公开页面或小型文本文件 | 不代表所有源码、依赖、历史提交均可取 |
| 下载入口可见 | 文件名、预览页、下载链接或校验值可见 | 未验证完整文件下载、解压及内容一致性 |
| 获取未核实 | 页面失败、入口重定向或无法读取文件清单 | 不认定资源已删除，也不认定数据可用 |

本次没有下载并校验任何完整数据包，没有实际构建候选项目。因此下文的构建判断是文档证据及引入条件，而不是构建验证结果。

## 4. 根因筛选与构建复现

真实数据集的 C/C++ 根因比例需要实际提取后统计，不能用“覆盖 140+ CWE”推断五类根因均衡。CWE 也不是根因的一一映射：同一漏洞可能涉及整数计算、容量不足和越界，多标签需要保留证据。

建议筛选入口：

| 根因 | 筛选线索 | 核验重点 |
|---|---|---|
| 生命周期 / UAF | CWE-416、对象析构、释放 / 引用 / 回调关系 | 生命周期、别名、所有权及跨函数上下文 |
| 并发 | CWE-362 等、锁 / 原子 / 线程交互 | 不把 TOCTOU、一般竞态和纯生命周期缺陷混为同类；优先 SV-Benchmarks 的明确并发性质 |
| 空指针 | CWE-476、返回值及失败路径 | 上游非空约束、分配失败与错误传播 |
| 越界 | CWE-119 / 120 / 121 / 122 / 125 / 787 等 | 区分读写、容量 / 长度 / 索引、检查位置与实际危险操作 |
| 整数溢出 | CWE-190 / 191 等 | 位宽、符号、转换、分配尺寸及后续访问关系 |

这些编号只是候选检索线索，不是自动归类依据。OpenHarmony 官方记录中存在 CWE-190 的[可核查实例](https://nvd.nist.gov/vuln/detail/CVE-2024-28044)，但仍需解析实际补丁才能成为实验样本。

构建条件应单独登记：

- **OpenHarmony**：固定组件 SHA 之外，还要固定 manifest、产品 / 架构、SDK / toolchain、生成头文件、宏与依赖。仅有发行版本或 PR URL 不足够。
- **函数挖掘数据**：函数 / 文件可以用于文本和 AST 筛选；编译分析必须恢复原始上下文。模型训练的 environment.yml / requirements.txt 不是被测 C/C++ 项目的构建配置。
- **Magma**：Linux / Docker 和目标构建脚本有文档支持；需要单列真实 bug 移植差异及插桩，不能把 canary 检查当漏洞证据。
- **Juliet**：使用官方支持文件、完整跨文件样例及分离的 good / bad 配置。
- **SV-Benchmarks**：记录架构、性质和 verifier 语义；适配代码不能无记录地删除关键控制流或非确定行为。

六类工具应分别登记源码读取、解析、翻译单元提取及目标代码覆盖状态。Clang 的[项目分析文档](https://clang.llvm.org/docs/analyzer/user-docs/CommandLineUsage.html)明确区分单翻译单元和项目构建驱动。CodeQL 首轮沿用项目已经验证的编译提取模式，固定工具和查询包版本；不同提取方式分开报告。

## 6. 真值、负例、去重与泄漏规则

### 6.1 修复后不是整个函数安全

只标记“目标漏洞已修复”，不把整个函数、文件或项目标为安全。修复后报出另一种缺陷应独立审查。diff 行不能直接当漏洞发生行：补丁可能在入口增加检查，危险操作位于别处。

建议保持至少四种语义：

- confirmed_vulnerable：有公开来源和人工根因证据的目标漏洞。
- target_fixed：该目标漏洞修复后代码。
- property_negative：在明确模型和性质下的控制负例。
- unlabeled：未完成目标性质审查的真实代码。

Juliet good / SV-Benchmarks true 只能评价指定性质；真实 repaired 和未标注函数不能默认进入 TN / FP 分母。已完成指定性质审查的真实代码可以作为受限安全对照，并保留审查范围。

### 6.2 按事件和补丁归一

同一 CVE、多分支 backport、上游 / 下游移植、相邻版本及函数重命名均需检查。联合使用 CVE / 事件、规范仓库、补丁身份、原始与归一化函数哈希，并人工复核近重复；不能只比 URL 或原始函数文本。

PrimeVul 重构既有数据；DiverseVul 官方仓库提供与 BigVul、CVEfixes 等合并的划分。因此通用来源之间不能假定独立。OH-Bench 与 OH-MAS 描述同一 741 任务，也不能重复计数。

### 6.3 与已有 OpenHarmony 样本重叠

**实际重叠未知。** 本次没有读取四个漏洞的 CVE / 仓库 / commit 清单，也没有下载数据进行交叉比对。官方 OpenHarmony 记录及 SPLVD 子集存在重叠可能；通用集可能包含 OpenHarmony 使用的 Linux、OpenSSL 等上游漏洞。仓库名称不同不能证明事件独立。

### 6.4 留出策略

before / after 同组，同事件全部版本同组，Juliet 同模板家族同组。调规则与最终测试按事件 / 项目分离，可辅以时间切分。即使没有模型训练，反复查看测试集调自研规则、Semgrep 或 Joern 查询也会造成测试泄漏。

先冻结样本清单、规则 / 查询版本、工具配置及判定准则，再运行最终比较。既有 4 对若已经用于调规则，应标为回归集，不能包装成独立测试集。

## 7. 入选清单与指标口径

新增每个真实样本至少记录：

| 字段组 | 最低内容 |
|---|---|
| 来源 | 数据集及版本、原始公告 / CVE / bug URL、许可证及核查日期 |
| 版本 | 仓库 URL、修复 SHA、修复前 SHA、backport / 上游关系；不能机械假定 merge commit 的任意 parent 就是漏洞版本 |
| 定位 | before / after 路径和函数范围、危险操作 / 根因位置、标注证据与粒度 |
| 标签 | 目标根因、CWE、标签产生方法、人工审核状态及未知项 |
| 构建 | 产品 / 架构、toolchain、依赖版本、生成文件、编译命令、TU 与宏覆盖 |
| 分组 | 事件 ID、补丁 / 函数哈希、重复家族、回归 / 调规则 / 留出分区 |
| 适配 | stub、插桩、移植及支持文件差异；不能静默改变关键语义 |

分别报告以下结果，不合成一个缺乏共同分母的总准确率：

1. 已确认漏洞事件上的目标召回率，按根因给出样本数与不确定性。
2. 目标修复前后告警变化；保留修复后新发现的其他问题。
3. 性质控制集的 TP / FN / FP / TN 及误报率，明确性质与模型。
4. 真实告警审查 precision、审查数量及 unresolved 数量；未决项单列并说明分母。
5. 全量源码扫描与语义分析各自的文件 / TU 覆盖、解析失败、编译失败、提取失败及耗时。

无法解析或编译的样本单列，不能悄悄计作 TN 或删去。六工具排名只在共同覆盖范围计算，同时报告各自总覆盖和独有候选。21 个 host TU 的结果不能代表全部 123 文件或完整 OpenHarmony 产品构建。
