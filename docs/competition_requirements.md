# 2026 赛题要求拆解：OpenHarmony 开源代码漏洞挖掘

> 赛题名称：OpenHarmony 开源代码漏洞挖掘  
> 赛题日期：2026-04-07  
> 本文仅对官方赛题要求进行结构化拆解；“工程落地建议”均单独标注，不等同于官方原文。

---

## 1. 赛题核心目标

本题要求参赛队伍实现一套**完整的自动化开源代码漏洞分析工具**，面向 OpenHarmony 社区开源代码进行大规模漏洞分析。

官方目标不是单纯“找出可疑代码”，而是要求形成以下完整安全分析链路：

```text
OpenHarmony 大规模源码
        ↓
自动化代码扫描与分析
        ↓
发现真实安全漏洞
        ↓
漏洞分类（CWE）
        ↓
已有漏洞关联 CVE（如有）
        ↓
生成可执行 PoC
        ↓
分析影响模块 / 功能 / 版本 / 分支
        ↓
给出修复建议或补丁
        ↓
生成完整漏洞报告
        ↓
统计扫描耗时、内存等性能指标
```

因此，本项目最终不能只停留在“静态规则命中”或“LLM 判断存在漏洞”，而必须能够提供可验证、可复现、可解释的结果。

---

## 2. 官方要求的六项核心能力

### 2.1 大规模自动化源码分析

工具需要能够高效分析 OpenHarmony 社区开源代码，并识别其中存在的安全漏洞。

### 需要具备的实际能力

- 获取或导入 OpenHarmony 指定源码
- 对大型代码仓库进行递归扫描
- 支持大量源码文件
- 支持多模块代码组织
- 对扫描范围有明确记录
- 尽量提高代码覆盖率与扫描粒度
- 对大型项目保持可接受的运行时间和资源占用

### 我们的工程落地

项目必须至少具备：

- Repository / Directory Scanner
- 文件语言识别
- 模块识别
- include / import 依赖提取
- 可增量扩展的 Parser
- 扫描进度统计
- 扫描文件数 / LOC 统计
- 跳过文件原因记录
- 运行时间和内存指标记录

---

### 2.2 漏洞描述、CWE 与 CVE 信息

每一处发现的漏洞需要输出：

- 简要漏洞描述
- CWE 信息
- 若漏洞已经存在公开 CVE 编号，则输出对应 CVE 编号

### 工程含义

Finding 不能只记录“命中了某个规则”。

至少应包含：

```text
vulnerability_name
description
cwe_id
cwe_name
cve_id (optional)
evidence
confidence
```

### CVE 处理建议

项目后续需要区分：

1. **新发现疑似漏洞**
   - 没有公开 CVE
   - 不应强行猜测 CVE 编号

2. **已公开历史漏洞**
   - 需要尽可能准确匹配已有 CVE
   - 可以结合代码位置、补丁、版本、提交记录等信息辅助判断

---

### 2.3 为每处漏洞生成可执行 PoC

官方明确要求针对识别出的每一处漏洞，产出**可执行 PoC（概念证明）代码**。

这意味着：

- 只有“静态扫描结果”是不够的
- 只有“漏洞解释”也是不够的
- 工具需要尽可能进入漏洞验证环节

### PoC 必须关注

- 可执行性
- 可复现性
- 稳定性
- 指定环境下能够成功触发
- 明确说明运行依赖和复现步骤

### 推荐输出结构

```text
poc/
├── README.md
├── poc.xxx
├── build.sh / run.sh
├── environment.md
├── expected_result.md
└── evidence/
```

### 工程要求

每个 Finding 后续应允许关联：

```text
poc_status
poc_path
poc_language
poc_environment
poc_steps
expected_behavior
actual_behavior
reproducibility
```

---

### 2.4 严重程度与影响范围分析

工具需要评估漏洞的：

- 严重程度
- 影响代码模块
- 影响功能模块
- 影响 OpenHarmony 版本
- 影响分支

### 重点

这里不是只输出 High / Medium / Low。

工具需要回答：

```text
漏洞存在于哪里？
影响哪个组件？
攻击面是什么？
哪些版本包含这段漏洞代码？
哪些版本已经修复？
不同分支之间是否有差异？
```

### 推荐后续能力

- Git 历史分析
- vulnerable commit / fix commit 定位
- 分支 diff
- patch propagation 分析
- 版本范围推断
- 模块依赖分析

---

### 2.5 修复建议或补丁方案

官方要求针对漏洞：

- 提供修复建议
- 或提供补丁方案

优秀结果应尽量做到：

```text
漏洞根因
    ↓
为什么危险
    ↓
应该修改哪里
    ↓
如何修改
    ↓
修复后是否引入兼容性问题
    ↓
给出 Patch / Diff
```

后续建议支持：

- 自然语言修复建议
- 代码级修复示例
- Unified Diff
- 修复前后对比
- 回归测试建议

---

### 2.6 漏洞报告自动生成

官方要求工具具备报告生成功能。

单份漏洞报告至少必须覆盖：

- 涉及漏洞的源码位置
- 涉及漏洞的源码内容
- 漏洞详细信息
- CWE
- CVE（如有）
- 触发条件
- 影响路径
- PoC 代码
- 影响代码模块
- 影响功能模块
- 影响 OpenHarmony 版本 / 分支
- 修复建议
- 补丁代码（如有）

项目应将“报告生成”作为独立模块，而不是比赛最后人工拼接。

## 3. 官方重点考察的六种能力

### 3.1 大规模自动化代码分析

关键词：

- 大规模
- 自动化
- 高效
- 全面

因此，单纯调用 LLM 按文件逐个读取通常不足以满足整个比赛目标。

---

### 3.2 丰富的漏洞知识

官方举例包括：

- 缓冲区溢出
- 空指针解引用
- 整数溢出
- UAF
- 信息泄露
- 权限提升
- 拒绝服务
- 逻辑漏洞

这说明项目应覆盖多种漏洞类别，而不是只针对单一漏洞。

---

### 3.3 漏洞深度分析与分类

需要准确获取或判断：

- CWE
- CVE
- 漏洞详情
- 补丁信息

这要求工具不仅做“检测”，还需要具备漏洞知识关联和历史信息分析能力。

---

### 3.4 高质量 PoC

PoC 是独立考察能力。

工具发现漏洞后，必须尽量提供：

- 可执行
- 可复现
- 稳定
- 可验证

的 PoC。

---

### 3.5 影响范围评估

需要分析：

- 版本
- 分支
- 模块
- 风险

因此 Git / Version Analyzer 是比赛后期的重要模块。

---

### 3.6 修复能力

需要提供：

- 合理修复建议
- 可操作方案
- Patch

意味着系统最终应从“漏洞检测器”升级为“漏洞分析与辅助修复平台”。

## 5. 官方明确提醒

### 5.1 疑似漏洞需要真实安全价值

发现的疑似漏洞可以提交 OpenHarmony 安全漏洞奖励计划。

因此我们的核心目标应是：

> 找到真实、可验证、有实际安全影响的漏洞。

---

### 5.2 PoC 必须稳定

PoC 应具有较高：

- 可复现性
- 可执行性
- 稳定性

不能只给理论攻击代码或不完整片段。

---

### 5.3 必须控制误报

官方明确要求避免把以下问题误判成安全漏洞：

- 普通功能性 Bug
- 非安全健壮性问题
- 普通逻辑错误

因此项目必须有“候选漏洞 → 二次确认 → 最终漏洞”的筛选过程。

---

### 5.4 普通 DoS 不建议纳入

如果 DoS：

- 没有实际安全危害
- 没有明显利用价值

则不建议作为安全漏洞提交。

---

## 6. 对本项目最重要的结论

### 结论 1：不能只做代码规则扫描器

比赛真正需要的是：

```text
检测 + 验证 + 分类 + 影响分析 + PoC + 修复 + 报告
```

---

### 结论 2：误报控制优先级非常高

因为官方评价中明确：

- 准确率重要
- 误报会扣分

项目应宁可把“低可信候选”单独放入 Candidate Finding，也不要全部作为最终漏洞输出。

---

### 结论 3：需要同时兼顾覆盖率

只追求准确率也不够。

官方同时看：

- 完整性
- 漏报
- 代码覆盖率
- 扫描粒度

因此要避免过度保守导致大量漏报。

---

### 结论 4：需要多类型漏洞能力

官方对漏洞类型多样性给予权重。

我们的规则库、程序分析和测试集都不能只围绕单一 CWE。

---

### 结论 5：C/C++ 内存安全值得作为重点方向之一

官方示例中明确出现：

- Buffer Overflow
- Null Pointer Dereference
- Integer Overflow
- UAF

结合 OpenHarmony 系统代码特点，项目需要认真建设 C/C++ 分析能力。

> 这是工程优先级建议，不代表官方只考 C/C++。

---

### 结论 6：LLM 应该作为辅助分析层，而不是唯一引擎

为了兼顾：

- 大规模性能
- 准确率
- 可解释性
- 稳定性

更适合采用：

```text
静态分析 / 程序分析
        ↓
筛出候选
        ↓
LLM 深度研判
        ↓
验证与报告
```
