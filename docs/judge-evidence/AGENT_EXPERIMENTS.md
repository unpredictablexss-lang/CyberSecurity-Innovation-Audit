# Agent 候选复核实验：固定源码、阶段化流程与失败边界

**评委阅读版｜2026-10-19**

## 实验目的

验证 Agent 原型能否围绕静态候选，在固定 commit/tree 和文件哈希约束下调用只读源码工具、逐项检查义务，并在证据不足时保留待复核状态。此次实验的目标是验证链路和失败边界，不是衡量漏洞检测准确率。

## 固定输入与静态覆盖

- 仓库：`openharmony/security_access_token`
- 源码 commit：`17d88bfb36bea6c9370ba919ac41a22d16dd66b3`
- Git tree：`4621b3e40b31a958a4bbe9be87690afb6cec44b0`
- 扫描清单：550 个源码文件；8 个检测器；16 条诊断；5 个检测器为 blocked。
- 扫描任务状态：`completed_with_limitations`。
- 被选复核项：`interfaces/innerkits/accesstoken/src/accesstoken_callback_stubs.cpp:103`，IPC 静态候选；源码 SHA-256 `a0b148f9f0f1f06344477a9e3309c3efaa81b8b2d89be00a25f794ce66243340`。

源码快照是真实固定仓库源码；本轮模型端使用 Fake Provider，没有向真实模型 API 发请求。

## 工作流设计及治理边界

原型采用单个受限模型会话按序执行的 Taskflow，而非多个独立 Agent：

1. 将候选绑定到固定仓库、commit/tree、报告和源码哈希。
2. 通过白名单只读工具取符号、函数和受限源码范围。
3. 检查支持证据与反证，并保留无法由固定源码解决的产品/运行时义务。
4. 输出结构化复核结果，由服务端校验 schema、引用来源和行范围。
5. 人工在结果产生后处置；Agent 不能直接将漏洞状态改为 confirmed。

当前原型尚不能据此声称生产级自动复核闭环或提升准确率；真实样本独立盲测、自动派发和持续授权治理仍需完成。

## 结论

这批证据支持“已跑通固定源码候选复核的离线原型，并验证了证据不足时保守停留在 candidate/unknown”。它不支持“Agent 已确认该候选为漏洞”“静态扫描覆盖完整”或“Agent 提升了召回/精度”。下一步应在冻结的独立样本集上记录支持/反驳/unknown、引用准确性、失败率、token/费用、耗时和人工最终结论。
