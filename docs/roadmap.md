# 两周参赛执行路线

> 起点：2026-10-02，用户估计距离比赛约两周。这里使用 D1–D14，相对日期从队伍正式开始那天计算；具体截止时间以赛事公告为准。当前仓库只有文档与空目录，以下任务均为待执行，不把规划写成完成进度。

## 1. 验收目标与优先级

**最低可交付**：一个真实 OpenHarmony 组件与固定版本；可复现的扫描/候选导出；一个公开历史修复前后对的原组件验证；完整报告样例、使用说明、性能统计和失败覆盖说明。

**期望增量**：在另一位置找到经独立复核的有效候选；证明安全约束迁移相对简单相似检索的收益；独立 fuzz 路线能产生可记录的覆盖/异常信息。

**不承诺**：两周内找到被官方受理的新漏洞、全 OpenHarmony 深度覆盖、自动生成所有 PoC、在没有设备时证实系统权限漏洞。

历史公开案例可证明工具能力，不能替代新漏洞成果。新候选即使没有完全验证，也应如实保存为研究线索，而非正式漏洞。

## 2. 人员与交接

按 3 人设置角色，第 4 人加入时分担版本与实验。每人每天留 30–60 分钟互相复核关键证据。

| 角色 | 主责任 | 每日可检查产出 |
|---|---|---|
| A：组件/构建（嵌入式方向） | OpenHarmony 版本固定、源码/依赖、原组件构建、harness、sanitizer | 构建命令、日志、目标 SHA、可运行文件 |
| B：安全分析（Web 方向） | 攻击面、输入契约、source/guard/sink、安全后果、CWE/CVE/公告 | 候选卡、正常/恶意对照、根因解释 |
| C：工具与评价（基础/CTF 方向） | 现成分析器与自定义规则、证据数据、CLI/报告、性能与复现包 | 每日扫描结果、失败清单、复现记录 |
| D：可选 | 历史补丁卡、跨版本、消融实验、独立复现 | 对照数据和版本矩阵 |

A 与 B 不能同时只做各自方向而没有共同目标。每个候选必须有“谁负责构建/输入”和“谁负责影响判断”。第三人负责把零散发现写入统一记录，不承担全部验证责任。

## 3. 每日推进表

| 天数 | 主要工作 | 当日必须看见的证据 | 未达成时 |
|---|---|---|---|
| D1 | 核实报名/截止/目标范围；服务器准备；列 3 个组件 | 官方范围记录、机器配置、三张目标卡 | 不开始大规模下载或自建框架 |
| D2 | 为三个目标探测构建与测试；锁定主/备选 | 一个真实 target 编译及普通测试通过 | 换组件；若都失败，优先找已有 host test/fuzz target |
| D3 | 原组件历史修复前后验证；成熟工具基线 | 两个 SHA、可重复构建、原始输出及目标代码位置 | 无法在原组件重现则换历史案例 |
| D4 | Candidate/Evidence 最小格式；轻量扫描；独立 fuzz 尝试 | 可导出候选、失败文件清单、基线性能 | 先减规则数量，避免只堆告警 |
| D5 | 第一条完整 PoC 对照与安全影响复核 | 一份从干净目录可运行的复现包 | 立即补构建或 oracle，不新增复杂漏洞类型 |
| D6 | 抽取 1 类历史补丁安全约束 | 补丁卡、适用条件、两个安全反例 | 若抽象过泛，收窄到一个尺寸关系 |
| D7 | 在第二目标/不同位置做迁移；中期路线复盘 | 新候选与反证、每百候选审核量、耗时 | 没有有效增量则保留研究记录，转向完善闭环 |
| D8 | 版本矩阵和真实调用者核查 | 至少修复前/后 + 另一快照的状态及证据 | 无法拉通版本则写 unknown，不假定受影响 |
| D9 | 加一条第二类型或独立 fuzz 案例 | 第二类问题的候选、证据和验证状态 | 若首类尚不稳定，继续完善首类 |
| D10 | 修复建议/补丁对照；报告生成 | 修复后原 PoC、正常输入、边界变体结果 | 功能退化时撤回“修复成功” |
| D11 | 冷/暖扫描与资源测试；消融 | 目标/版本/工具固定的性能和对照表 | 无统计基础时只报原始计数 |
| D12 | 技术说明、使用说明、漏洞报告、演示脚本 | 所有必交付章节有真实命令和输出 | 冻结新功能，补齐缺口 |
| D13 | 全新环境复现与成员交叉审核 | 非作者按 README 从零成功运行 | 只修复复现问题和结论错误 |
| D14 | 交付冻结、录像、提交前核对 | 源码、说明、视频、报告、性能数据一致 | 遵循赛事截止时间，提前留上传缓冲 |

D2、D5、D7、D12 是硬切换点。超过时限仍无法运行真实组件，必须换可验证对象。可以保留失败经验，但不能继续消耗主线。

## 4. 三条并行工作流如何汇合

### 工作流 1：工具闭环

D1–D5 把固定版本输入、候选、证据、原组件 PoC 和报告跑通。D6 后只围绕已遇到的缺口加深 CFG/数据流或上下文，不按架构图从头实现全部模块。

### 工作流 2：创新实验

D3 确立历史基线。D6 抽出 1 类可表达的安全约束。D7–D11 用留出样本及安全反例比较文本/AST 相似检索、约束迁移和动态复核。若无新增真实根因，可报告明确的误报减少或验证时间差，不能自称“发现 0-day”。

### 工作流 3：比赛交付

从 D1 保存运行环境和日志；从 D5 开始同步写案例；D8 建版本表；D11 做性能和覆盖；D12–D14 冻结报告与视频。所有图表必须能追到原始运行记录。

## 5. 审核候选的统一问答

每张候选卡在进入正式报告前回答：

1. 目标仓库、manifest/commit、构建配置和代码行是否固定？
2. 外部或低权限主体具体控制什么输入？合法调用约定是什么？
3. 实际对象、容量、长度单位和 guard 是什么？
4. 是否存在上游、调用者、系统服务层或配置级保护？
5. PoC 调用的是原代码吗？环境替身改变了关键逻辑吗？
6. oracle 是否在运行前确定？异常落在组件还是 harness？
7. 成功和失败重复多少次？另一位成员复现过吗？
8. 安全影响是什么？为什么不只是普通 Bug/无价值 DoS？
9. CWE 根据什么根因映射？已有 CVE 如何排查？
10. 哪些版本已有证据，哪些仍 unknown？
11. 修复建议是否针对根因，修复后正常功能是否保留？

任何关键项缺证据就保留候选状态，记录下一步，而不是让报告语言补足。

## 6. 学习路径只服务当日问题

- D1–D2：Git 的 commit、tag、manifest、不同仓库版本；C/C++ 构建目标、头文件、编译参数。
- D3–D5：AST、调用者、ASan/UBSan 日志、fuzz harness 和正常输入对照。
- D6–D8：CFG 与支配关系、数据流摘要、整数位宽/溢出、CWE 根因。
- D9–D11：版本回迁、补丁等价性、样本泄漏、覆盖率与误报实验。
- D12–D14：独立复现、演示叙事、技术说明书。

每次让 AI 解释具体函数、日志和约束；学习成果要以能够复现一条真实链路来检验。不要先完整学完所有程序分析教材才开始做组件。

## 7. 里程碑和退出条件

| 里程碑 | 完成定义 | 若未完成 |
|---|---|---|
| M0 环境与目标 | 版本锁定、普通测试可运行 | 改选目标，不开始模型/UI |
| M1 基础闭环 | 修复前后案例+PoC+报告从新目录复现 | 集中修复构建与 oracle |
| M2 发现层 | 自定义候选有可解释关系，保存安全反例 | 减少规则，保留成熟工具基线 |
| M3 创新增量 | 约束迁移实验有公开样本与对照 | 写研究局限，不冒充性能提升 |
| M4 比赛交付 | 五类交付件一致，可按文档执行 | 冻结开发，补文档与视频 |

## 8. 设备条件的分岔

D2 前若拿到匹配版本开发板/镜像，可以由嵌入式成员在不影响主线构建的前提下建立设备启动与 HDC 调试；D5 前若有低权限正常对照，再考虑 IPC 权限审计。否则保持 C/C++ 组件主线，设备学习作为后续扩展。环境细节见 [environment_guide.md](environment_guide.md)。

## 9. 最终陈述应如何客观

比赛报告分别列出：

- 工具在公开历史对照上的已验证能力；
- 在指定 OpenHarmony 源码中扫描到的候选和人工审查情况；
- 经真实组件/目标配置/系统入口验证的案例；
- 已知、疑似新发现、已向官方提交以及已接受的不同状态；
- 未覆盖仓库、失败构建、未证明路径和性能限制。

这些类别清楚，评委才知道什么是实测成果，什么仍是研究计划。
