# 技术路线比较与选择实验

> 本文是参赛决策文件。路线 A/B/C/D 可以组合，但两周内应有一条主线和明确放弃条件。下列成本和成功率为待测指标，不是已测结果。

## 1. 用什么标准选路线

选题不能只按“听起来先进”。在同一目标快照、同一机器和相近人力投入下，比较五项：

1. **环境可得性**：是否能拿到真实源码、构建命令、测试入口和必要设备。
2. **可验证性**：能否用原组件代码、合法输入和明确 oracle 证明事实。
3. **覆盖与精度**：能扫多少目标、每百个候选有多少值得人工深入、已知样本漏掉多少。
4. **差异化**：比原有静态工具与通用 fuzz 多解决什么具体问题。
5. **两周交付风险**：构建/调试耗时、是否由某位成员单点负责、失败时能否产出可信基线。

第 2 天完成三个组件的“源码固定—构建探测—现有测试运行”表，第 3 天做路线锁定。没有可运行环境，就不把动态验证承诺写成已实现功能。

## 2. 路线 A：静态分析主导的内存与整数安全

**适合**：能拿到编译信息或可对目标组件构建，目标存在外部长度、偏移、索引、解析逻辑。

### 工作链

源代码与构建配置 → 成熟引擎做已有检查 → 针对目标 API 做尺寸/容量关系查询 → 追踪调用者约束 → 产生验证计划 → 原组件测试和 sanitizer。

“自定义”应集中于 OpenHarmony 组件中的接口/包装函数摘要、长度单位、分配与访问关系；基础 AST、CFG、指针分析优先复用工具。第一轮可比较 Clang Static Analyzer、CodeQL C/C++、轻量语法规则的可运行性。Joern 作为需要代码属性图探索时的备选；不要同日集成四套引擎。

[CodeQL 官方文档](https://docs.github.com/en/code-security/reference/code-scanning/codeql/build-options-for-compiled-languages)说明 C/C++ 支持无构建模式，也说明宏和外部依赖可能影响精度。它是候选基线，不保证适合所选 OpenHarmony 组件。若评估它，应对相同文件比较无构建与真实构建模式的解析覆盖和告警差异。[Joern 前端文档](https://docs.joern.io/frontends/)用于确认其实际语言支持，不能仅凭“CPG”名称断定完整 C++ 语义。

### 最小研究问题

对每个候选给出四元组：外部长度/偏移、目标对象实际容量、沿途约束、危险访问。先覆盖两种关系：

- 算术结果用于分配，后续按原始长度访问；
- 边界检查存在，但检查对象、单位或时机与实际访问不一致。

输出的是待验证假设。只有找到合法输入和运行证据才升级为案例。

### 主要风险与止损

| 风险 | 检查 | 处理 |
|---|---|---|
| 编译数据库不完整 | 抽样核对原始编译命令与真实头文件 | 标记 semantic_partial，转局部构建；无法补齐就换组件 |
| 规则命中太多 | 每百条人工复核与安全对照 | 收紧关系约束或缩小到一种义务 |
| 没有可达入口 | 从公开调用者和测试接口追溯 | 仅保留组件缺陷候选，不写系统漏洞 |
| 只有普通崩溃 | 记录权限、服务影响与攻击者能力 | 作为质量问题或继续调查 |
| 自研数据流投入过大 | 比较复用引擎是否已有所需边 | 停止大范围自研，聚焦摘要与验证 |

**两周适用性：最高。** 与现有仓库 P0 方向相符，但需要更早做真实组件构建和证据实验。

## 3. 路线 B：coverage-guided fuzz 与静态线索协同

**适合**：组件已有 fuzztest/单元测试，或 1–2 天内能用原组件建立合法输入 harness。OpenHarmony 的[开发测试框架](https://github.com/openharmony/testfwk_developer_test/blob/master/README_zh.md)支持 FUZZ 类型；目标组件是否有可直接复用的 fuzz target 须逐一检查。

### 双入口设计

1. **独立探索入口**：选择外部输入组件，不要求静态规则先命中；利用已有 harness、seed、字典、覆盖反馈寻找异常。
2. **候选引导入口**：对静态发现的比较值、长度条件和解析格式构造 seed，让 fuzz 触达特定位置。

两路共用崩溃归并、复现、原始组件核对和根因分析。这样可以测量：静态引导增加多少独有有效路径；独立 fuzz 找到多少静态遗漏的根因。

[LLVM libFuzzer 文档](https://llvm.org/docs/LibFuzzer.html)可作为一种本地 coverage-guided 引擎的技术基线。具体 OpenHarmony 构建或设备侧可用工具要按目标版本确认；不默认官方仓库里的 FUZZ target 就能在租用服务器上原样运行。

### 主要风险

- 测试只覆盖 helper 函数，绕开原入口的合法输入校验；
- 所有 crash 最后来自 harness；
- 编译因平台依赖失败，转而重写大量源代码，失去原组件意义；
- 只展示运行时长，没有覆盖与独立根因；
- 没有正常输入对照，不能判断安全影响。

**两周适用性：高，但依赖目标组件。** 若第 3 天还没有原组件 harness 试运行，则降为辅助方向，不挤占主线静态验证时间。

## 4. 路线 C：历史补丁“安全约束”迁移

**适合**：能收集明确的公开安全修复前后对，且代码类型与当前目标相近。这是建议主打的创新增量，但必须建立在 A 或 B 的可验证闭环之上。

### 与普通补丁相似度检索的区别

普通检索问：另一处代码像不像修复前代码。本路线问：另一处代码在相似前提下，是否满足同一个安全性质。例如“可控元素数乘以元素大小必须可表示，实际分配大小必须覆盖后续访问”。变量名、API 名变化后，性质仍可检查。

一期只抽取 1–2 类性质。卡片包括适用条件、潜在违例、可接受的等价防护、反例和验证方案。可用 LLM 起草卡片，成员必须逐项复核，再让程序分析确认候选关系。

### 数据泄漏与真假创新

历史补丁的原位置、相邻函数、已知分支不应成为“未知漏洞发现”测试集。对比采用：

- 时间切分：某日之前公开的补丁用于提取，之后公开的修复用于评估；
- 仓库/函数家族切分：同一补丁的回迁与近重复代码放同组；
- 负例：相似但有上游约束、等价 guard、不同位宽语义的安全代码；
- 人工审核：每个宣称新增的根因先查历史公告和重复报告。

历史标签可能不完整，未标注样本不能一律计为阴性。消融至少比较文本/AST 相似检索、约束迁移、约束迁移加动态反馈三组。

**两周适用性：中高。** 首先做小而严谨的样本和一个可复现的迁移案例；若第 7 天没有新增有效线索，展示为研究实验，继续把精力投到 A/B。

## 5. 路线 D：IPC 权限与逻辑审计

**适合**：能获得匹配版本的标准系统镜像、设备或可信模拟环境，能运行低权限应用/进程，并定位公开服务入口。学习 Web 安全的成员可负责主体、资源、动作和权限策略建模；嵌入式成员负责设备、镜像和系统调用链。

### 静态线索

服务暴露面与请求码清单 → 身份获取 API → 策略检查 → 受保护操作。找缺失检查、检查不支配敏感操作、参数声称身份、状态变化后授权不一致。相邻 API 的检查差异只是待调查线索。

### 动态证明

建立至少两组主体：合法授权者成功、普通调用者按策略应失败。保存应用声明、UID/token、系统版本、服务响应与副作用。只有真实低权限调用越过应有边界，才能声称权限漏洞。mock、root shell 或直接调用内部函数不能代替系统证明。

**两周适用性：条件性。** 第 2 天前若无设备或可运行的目标系统，就仅做攻击面映射和有限人工审计，不将它写入必交付主线。

## 6. 路线 E：全语言、全模块、全程序图加 Agent

理论上可扩展性强，但两周里构建、语义、验证、评价的组合复杂度过高。若仅展示规则命中与模型解释，赛题最重的 PoC 与误报要求无法证实。因此本轮只保留数据接口，不安排实现。待真实组件闭环和实验结果稳固后再考虑扩充。

## 7. 推荐组合与切换规则

推荐组合是 **A 为骨架、B 为独立发现和验证、C 为研究亮点、D 为有条件的第二方向**。资源分配起点可为：约一半投入真实组件构建和 A/B 闭环，约四分之一投入 C 和实验，剩余投入报告、版本、环境与演示。具体以第 2–3 天探测结果调整。

### 决策树

~~~mermaid
flowchart TD
    S["第 2 天：真实组件能否编译/运行测试？"] -->|可以| F["静态基线 + 原组件 harness"]
    S -->|不能| R["更换备选组件，不延长自建环境调试"]
    F --> Q{"已有可复用 fuzz 入口？"}
    Q -->|有| B["并行独立 fuzz 与候选引导"]
    Q -->|无| A["围绕一个合法入口构造最小 harness"]
    B --> C["第 5 天：历史约束迁移"]
    A --> C
    C --> D{"有真实低权限系统环境？"}
    D -->|有| P["有限 IPC 权限复核"]
    D -->|无| E["专注内存/整数与交付件"]
~~~

所有路线切换都要保留目标 SHA、失败日志与原因。不要因为找不到新漏洞就把旧样例说成新成果。

## 8. 三个具体对照实验

1. **扫描价值**：在相同目标与人力预算下，比较成熟工具基线与本项目增加的容量约束查询。输出各自独有的有效根因、需人工审核的候选数及耗时。
2. **补丁迁移价值**：比较 token/AST 相似检索与安全约束迁移在留出补丁、等价防护负例上的表现；人工复核随机低分候选，估计漏报。
3. **动态反馈价值**：对同一候选池，比较静态排序与加入真实验证后的报告精度、每个有效案例的平均验证时间。未验证候选计作未知，不悄悄从分母删除。

在两周内即使样本少，也应公布样本、来源、重复处理和置信区间/限制。若没有合适样本，不报虚假的精确率或召回率。

## 9. 人员分工原则

不按“会不会让 AI 写代码”区分能力，按输出物与互相复核安排：

- C/C++ 与嵌入式方向：真实构建、编译配置、sanitizer/fuzz 执行、环境一致性。
- Web 安全方向：攻击面、输入控制、权限主体/资源、CVE/公告检索、报告安全影响。
- 第三位：样本与负例整理、性能/覆盖计量、复现包、自动化脚本、独立复验。
- 如有第四位：版本矩阵、公开补丁知识卡和消融实验。

每天一位成员必须独立重现另一位负责的关键结果。模型生成草案可节省语法劳动，但构建、oracle 与结论的责任必须明确到人。
