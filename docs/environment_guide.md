# 两周参赛的 Windows、Linux 与开发板入门

> **状态说明（2026-10-04）**：本文最初来自 PR #1 的两周实施方案，现保留为环境准备与设备选择参考。实际已完成进度、当前分支与验证结果以仓库根目录 `PROGRAM_STATUS.md` 为准；文中的 Day 1～Day 5、硬件规格和路线时限属于当时的工程计划，不代表当前完成状态或赛题官方要求。

> 面向第一次做 OpenHarmony 系统代码审计的 3–4 人队伍。本文件解释环境各自的作用和准备顺序；具体依赖命令随锁定版本和组件调整，执行后必须记录实际结果。

## 1. 先理解三种机器

**你们自己的 Windows 电脑**可以直接完成 Python 工具开发、轻量源码索引、结果整理、文档和视频。若要在同一台电脑上使用 Linux 构建工具，优先尝试 WSL2 中的 Ubuntu；它运行在本机，不需要租服务器。源码和构建输出建议放在 WSL 的 Linux 文件系统内，而非 /mnt/c 等 Windows 挂载目录。

**Linux 构建环境**可以是本机 WSL2/Ubuntu、独立 Linux 电脑或租用服务器。它负责拉取选定源码、生成/捕获编译参数、运行静态分析、构建可移植组件、做宿主机 sanitizer 与 fuzz 测试。三者的任务基本相同，先选本机能稳定运行的方案。

**开发板**是一台能运行特定 OpenHarmony 镜像的目标计算机，外接供电、存储、网络或 USB 调试接口。它用于验证真实系统服务、权限身份、目标架构和设备相关行为。开发板不是静态扫描和大多数宿主机组件测试的前提；但没有目标系统就不能宣称已在系统入口验证权限绕过。

[OpenHarmony 官方环境准备文档](https://github.com/openharmony/docs/blob/master/zh-cn/device-dev/quick-start/quickstart-pkg-prepare.md)建议 Ubuntu x86_64 编译环境、至少 16 GB 内存，并强调用户名不能含中文。该页面是设备开发入门说明，具体赛题版本、产品形态及完整系统编译需求还要以对应版本文档和实际测量为准。

[微软 WSL 文档](https://learn.microsoft.com/en-us/windows/wsl/install)说明 Windows 可以本机运行 Ubuntu 等 Linux 发行版。OpenHarmony 官方上述页面给出的是 Ubuntu 环境要求，**并未保证每个 OpenHarmony 版本/产品在 WSL2 下完整编译成功**；先以你们选中的组件做实际构建探测。

## 2. 先试本机，必要时再租服务器

### 2.1 本机快速判断

先确认 Windows 版本支持 WSL2、已开启虚拟化，记录本机可用内存和剩余磁盘。在 WSL2 Ubuntu 中只拉取选定组件及依赖，运行它的原有小型测试，再尝试静态分析与短时间 fuzz。不要一开始下载和编译完整系统。若只是写 Python 编排与报告，可直接用 Windows 原生环境。

本机验收看三件事：目标组件能否从新目录稳定构建；运行期间是否频繁 OOM/磁盘不足；长时间分析是否影响团队日常使用。若都能满足，就继续用自己的电脑。WSL2 的项目文件放在 Linux 文件系统内是[微软建议的性能做法](https://learn.microsoft.com/en-us/windows/dev-environment/wsl-interop)。

### 2.2 何时租用

仅当本机资源不足、持续 fuzz 影响使用、多人需要共享同一可复现构建环境，或 WSL2 与目标版本/工具链存在无法快速解决的兼容问题时，考虑租 Linux 服务器或使用现有实验室机器。此时租机器是工程便利，不是赛题要求。WSL2 兼容问题也可先试普通 Ubuntu 电脑，不必直接付费。

### 2.3 首次租用的工程起点

如果只做**单组件构建 + 静态分析 + 少量 fuzz**，可先准备 x86_64 Ubuntu、8 vCPU、32 GB RAM、200 GB SSD，优先选可扩容/可制作快照的实例。这是团队的起始预算估计，**不是官方最低规格或全量 OpenHarmony 保证配置**。全量源码、完整系统构建、并行 fuzz 可能需要显著更多磁盘和内存；先用实际组件测峰值再扩容。

检查项目所在地区的网络可访问源码镜像。不要把“租更大的机器”当作解决下载源、依赖和编译参数错误的方法。

建议分卷或至少分目录保存：源代码、构建缓存、临时运行、长期证据。保留足够剩余磁盘给编译输出和 sanitizer 日志；首次运行记录 df、free、CPU 型号与峰值。连续两次因 OOM/磁盘不足失败再按实测扩容。

### 2.4 Linux 环境的第一天检查

无论是本机 WSL2、普通 Ubuntu 电脑还是租用服务器，都安排一位成员负责环境记录，完成并截图/存文本：

1. 记录 OS 发行版/内核、CPU、RAM、磁盘与文件系统；确认 x86_64 和普通英文用户名。
2. 若是远程服务器，设置 SSH 密钥登录、个人账号、最小访问权限和定时快照；本机 WSL2 不需要 SSH 才能使用。把多个成员的修改记录到仓库。
3. 验证官方 OpenHarmony 源码入口与所选仓库可以访问；记录目标 SHA 与 manifest 版本。
4. 安装所选版本要求的构建工具；先运行目标组件原有单元测试或最小 target，别先启动全量构建。
5. 为 fuzz/PoC 留独立普通用户或隔离容器，限制 CPU、内存、墙钟时间和工作目录。
6. 记录一份 environment manifest：系统版本、clang/其他工具版本、OpenHarmony 目标 SHA、构建参数与命令。

脚本输出只写受控目录，避免把凭据或 SSH 私钥放入日志/报告/模型请求。远程服务器若可快照，可保存“能构建”的状态；本机则保存依赖清单与可重现的构建步骤。

### 2.3 源码获取的正确顺序

第一步看赛题给出的 [官方源码下载入口](https://www.openharmony.cn/download)，确定当前赛题认可的源码和版本。第二步确认相应 manifest 及各组件 commit；[OpenHarmony manifest 仓库](https://github.com/openharmony/manifest)展示多仓库组织方式。第三步才下载目标组件及它的实际依赖。

为性能探索可以只取组件和依赖，但报告要明确“分析了哪个源码集合”，不能把一个仓库的覆盖率称为全 OpenHarmony 覆盖率。若需时间窗口输入，另外保存窗口起止日期、时区、相关提交集合，以及分析所用的固定快照。

可把从官方仓库拉取的源代码保存在本机 WSL2 或服务器的 Linux 文件系统内；竞赛工具仓库只保存目标 URL/SHA、脚本、规则、经审查的小样本和报告。不要上传整个 OpenHarmony 源码快照到参赛仓库。

## 3. 什么是开发板，什么时候需要

例如官方站点列有面向**标准系统**的 DAYU200/RK3568 类板卡；具体支持版本和镜像必须以项目当时的[官方设备文档](https://docs.openharmony.cn/)与厂商资料核实。板卡型号只是例子，不是购买建议。

只有以下任务可能迫切需要它：

- 验证真实服务经 IPC 被低权限客户端调用；
- 观察设备/驱动/硬件相关缺陷；
- 检查 ARM 目标 ABI、配置或系统组件在真实镜像中的行为；
- 需要赛事指定的目标设备环境。

若主线是可宿主机编译的解析库或数据处理组件，先不购买；两周里选板、烧录、配镜像、调试驱动容易吞掉主要时间。第 2 天前若确认权限方向有强候选、目标版本和设备资源，再决定借用、租用或购买。

### 3.1 买/借前核对清单

- 赛题指定什么 OpenHarmony 版本与产品形态？
- 该板的官方/厂商镜像是否与之匹配？能否重新烧录并复原？
- 开放串口、USB/HDC、日志、网络、调试权限吗？
- 目标服务和待测试接口是否实际随镜像构建？
- 能否运行低权限测试应用/进程，而非只有 root shell？
- 有无文档化的供电、下载线、存储介质和调试工具？
- 两周内拿得到、能启动、能由另一人重现吗？

任何一项关键条件不明，都不要因“做 OpenHarmony 必须有板”而仓促花钱。借到板后先运行官方示例、记录镜像构建号、服务列表和正常调用对照，再测试候选。

### 3.2 设备验证的限制

“x86 宿主机触发 ASan”可说明在该配置下的原组件问题；不能直接证明板卡上的权限或可利用性。“板卡上运行成功”若测试进程有系统/root 权限，也不能证明低权限越权。设备报告必须列明镜像/构建号、架构、身份、权限、目标服务、命令、日志和正常对照。

[OpenHarmony 开发测试框架文档](https://github.com/openharmony/testfwk_developer_test/blob/master/README_zh.md)说明部分用例可按子系统/部件/测试类型运行，并展示 HDC 远程连接示例；具体命令与产品配置以目标版本为准。

## 4. 从零到第一条真实验证链

### Day 1：固定对象

从 3 个候选组件中挑选有输入处理和现成测试的项目。对每个保存 repo、commit、关键源文件、构建脚本和依赖清单。完成一个普通测试的编译和运行。

**通过条件**：可从干净目录重复构建同一组件；一名同伴按记录复现。失败时先定位网络、工具链、头文件或配置，不进入自动漏洞生成。

### Day 2：建立两组样本

选择一个已公开修复对：修复前版本与修复后版本，锁定 SHA。另选至少一个有类似危险形态却安全的对照代码。若没有合适 OpenHarmony 公开案例，先用自建样例测试管线，但不能把它作为正式结果。

**通过条件**：相同入口下，修复前测试触发预期错误，修复后安全处理，正常输入保持功能。若修复前无法运行，换案例。

### Day 3：接上发现层

运行一套现成分析器和少量自定义关系查询，记录输出数、解析失败数、耗时及内存。并行运行已有 fuzz harness，证明动态通道无需静态规则命中也能工作。

**通过条件**：候选能映射到固定 SHA 和行号；工具失败与“无漏洞”明确区分。

### Day 4–5：完成第一张案例卡

将静态路径、PoC、运行日志、CWE、影响范围、修复前后对照整理为可独立运行的复现包。第二位成员在新目录执行，不使用作者的缓存。

**通过条件**：案例既有原始代码与日志，也说明测试环境和未证明的影响边界。

若 Day 3 仍无法构建一个真实组件，应切换备用目标，不继续在首选目标上无限调环境。

## 5. AI 可以怎样帮助初学者

给 AI 的每个任务限制为一个可核对输出：

- 解释指定函数的调用约定，并逐行引用真实代码；
- 从两份固定 SHA 的补丁提取可能的安全性质，并列出反例；
- 根据实际编译错误提出最小环境修复步骤；
- 为已有测试入口生成 harness 草案，由你们自己核对输入契约；
- 根据 ASan/UBSan 原始日志提出可能根因与排除实验；
- 用已确认事实起草报告。

每次保留仓库、SHA、日志、生成建议、执行命令和结果。AI 能加速学习和样板代码，不会代替对目标系统的真实运行、官方漏洞认定及比赛答辩。模型看不到的文件与测试结果应明确写“未知”。

## 6. 常见卡点与处理

| 现象 | 优先排查 | 做法 |
|---|---|---|
| 下载很慢/失败 | 源码站连通性、镜像、磁盘 | 不更改目标版本；使用官方允许的镜像后核对 SHA |
| 源文件语法能解析、Clang 深审失败 | 宏、生成头、sysroot、编译命令 | 标记 partial；修复真实配置，避免伪造头文件改变语义 |
| 组件在宿主机编译失败 | 目标特定依赖/架构接口 | 优先已有 host test；必要时换组件 |
| fuzz 很久无结果 | harness 是否触达目标、seed、覆盖 | 检查路径覆盖，不只增加时间 |
| ASan 栈在 harness | 测试代码错误 | 修 harness，暂不记为组件发现 |
| PoC 只在修复前跑、修复后编不过 | 环境不一致或补丁依赖缺失 | 暂缓“修复有效”结论 |
| 已知漏洞无法映射 CVE | 组件、版本、补丁证据不足 | 写未匹配，不能编造编号 |
| 本机/服务器的 Linux 环境能复现，板卡不复现 | 架构/宏/入口差异 | 各配置分别报告，追查前置条件 |
