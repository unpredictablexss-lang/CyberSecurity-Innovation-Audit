# 从当前版本到赛题交付：优先级与验收

2026-10-13。本文件是开发次序，不是已完成能力。三份导向文件的具体目录仅为建议，
现有 src/workbench + web 已实现同等基本职责，不必另造 backend/frontend/worker 项目。

| 顺序 | 任务 / 负责人 | 具体完成标准 |
|---|---|---|
| P0 | 公共契约收口 / 队长 | 固定 integration-base；v1/v2 决策、兼容测试；不丢 partial 候选义务 |
| P0 | A/B 最小可用检测器 / 两队友 | 每线先交一个窄家族正/fixed/safe、明确已知误报和范围；负责人五组件对照 |
| P1 | 源码显式同步 / 队长 | 独立 clone/fetch 任务、来源白名单/超时/日志；扫描阶段仍只读固定对象 |
| P1 | 提交区间审计 / 队长+A 配合 | 先两个固定 SHA 与端点比较，再日期解析；记录拓扑/时区/提交者时间；不自动判漏洞引入 |
| P1 | 统一验证证据 / 队长+A/B | 先接入已有受控 Harness，绑定目标、命令、环境、日志、hash；正/fixed/patch 重验 |
| P2 | 版本影响与报告 / 队长+A/B | 围绕同一根因；affected/fixed/not_present/unknown 需有证据；CWE/CVE 不凭名称猜 |
| P2 | 只读 Agent / 队长 | 源码/义务/补丁查询有限工具，预算/审计日志；无模型核心可用；不自动确认 |
| P3 | 大组件性能/多仓/部署 | batch Git/分片需证明覆盖不变；RSS 实测；Manifest 分仓 SHA；原生 Ubuntu 重跑验收 |

时间紧时不是所有 P2/P3 都压后：高价值候选的 Harness、修复重验和报告应与面板并行，
这是赛题真实得分成果。不要为“功能齐全”先做空菜单或下载完整 OpenHarmony。

## 两个独立维度

审计对象：snapshot（已有） / commit range（未实现产品入口） / version impact（未实现）。
发现策略：static（已有） / LLM exploration（未实现） / hybrid（未实现）。
不能把两个三模式混成一个选项；A 的研究 sidecar 不等于后端产品模式完成。

## 当前可以演示

登记已有本地仓库 → 固定版本快照扫描 → 真实覆盖与 unknown → 候选固定源码 →
人工复核/源码摘录/调查分组 → 原报告及审计包导出。
不能演示为已确认漏洞/完整影响版本/已部署验证 Agent。原始 candidate、根因案例、确认数分开。

## 推荐下一轮具体范围

先完成一份契约决策与 B M1/M2 的选择性集成：
1. 以本工作台公共底座起独立集成分支，选择接口包、正反例、方法卡；不覆盖 runner。
2. 针对错误接口、同文件委托、partial、blocked、义务混用和来源 hash 做回归。
3. 固定五组件 commit/include，比较迁入前后候选差异及新增/消失原因。
4. 对 A 最新静态模块单独审查文件所有权/接口，给出可迁入清单；不直接 merge 全研究历史。
5. 契约与检测修复稳定后，才进入 source-sync + 两 SHA 区间产品入口。

最终赛题矩阵：
准确率/完整性 → 独立 holdout 与覆盖；
CWE/CVE → 有来源的根因映射；
PoC/影响/修复 → 受控可复现证据与前后版本对照；
性能 → 同组件同范围 wall/RSS；
创新 → 自研算法增益与证据约束 Agent 对照实验。
本轮组织整理没有新增这些指标的实验结论。
