# 鸿鉴 OHScanner — 面向用户的一站式 OpenHarmony 智能安全审计平台 PRD（V1 产品目标）

> 更新：2026-10-20。依据 main@dd8b12b9、11 页本地 8765 HTML 快照、现有 `src/workbench` / `web/src` 实现、A/B/C/D 准入状态制定。**这是目标产品与可执行实施规范，文中「应当」并不代表功能已上线。** 本次 PR 的实际完成内容以 PR Changed Files 和验收记录为准。
>
> 产品原则：**普通用户只决定审计对象、范围和是否授权模型分析；系统负责源码准备、检测器调度、Agent 多步取证与报告。专家可展开技术证据。**

## 0. 对赛题负责的定位

赛题要求识别 OpenHarmony 开源源码漏洞、提供可核验证据与安全影响说明；比赛作品应形成：源码审计、已披露 CVE/补丁对照、未知漏洞线索、可复核 PoC/受控验证、CWE/CVE 对应、影响范围、修复建议、性能评估、报告导出。**静态候选与模型判断都不是已确认产品漏洞**；不能因为需要交付 PoC 就伪造未执行的 PoC 或完整产品影响。

当前快照已具备单仓快照、时间端点、跨版本/矩阵、静态规则、人工案例、只读 Agent 原型、受控 AUTH-01 Harness、原始 JSON/MD/manifest/review 导出。明确缺口：在线官方仓库目录和下载扫描联动、三个审计入口统一自动智能工作流、全量专业风险卡、复杂 Agent 跨文件可验证编排、友好的综合报告、独立准确率评价、生产级多用户认证与 Docker 验收。

## 1. 用户与使用场景

- **普通审计用户**：在网页上搜索 OpenHarmony 仓库，选版本/时间/对比方式，一键拿到有颜色和理由的风险清单；点击“AI 追查”或“人工复核”，不需要知道 R0/R1/R2、规则 ID、真实文件路径。
- **专业审计员**：浏览静态入口→guard→sink、完整/部分解析、上下文证据及模型工具轨迹，提出误报/确认/仍待验证决定，可关联多个候选根因。
- **管理员**：管理服务器上的安全下载目录、仓库镜像、代理与模型 Provider、API Key、成本/Token 配额、任务并发、只读隔离和审计日志。
- **比赛评委**：从一条风险跳转固定 Commit/文件/行/规则版本/报告摘要，复查修复前后源码与 Harness 证据，确认该结论由哪些步骤支持。

## 3. 三种审计方式——每种都能选择【静态】或【智能】

### 3.1 仓库快照审计

输入：仓库名、默认分支/Tag/Commit、可选文件范围。初次使用时系统从受控目录同步；已有对象优先复用。用户看到【标准智能审计（推荐）】和【仅静态】。标准模式在**显式审核源码外发计划及预算后**，执行 `download/sync → pin commit/tree → static → aggregate → AI triage → optional read-only deep research → report`；没有授权则可退回纯静态，任务仍完成并标记「智能研判未请求」。

### 3.2 时间增量审计

输入：仓库、分支、近 7/15/30 天或自定义时间与时区，提示为 committer-date + first-parent 端点比较、并非逐 commit 遍历。锁定 baseline/endpoint 的两个真实 SHA，先在两个端点分别做静态，再对**新增、消失、同根因变化、未能比较**的候选做语义差分。智能模式在**整个双端点计划经过授权**的前提下，优先对新增/高影响/疑似补丁未生效候选执行 Agent 追查；模型读到的每个端点和文件需在授权范围。未建成多端点模型授权之前，UI 只能诚实显示“静态完成，智能研判可逐条授权”，不能虚假显示“智能模式已完成”。

### 3.3 跨版本安全分析

输入：同库两分支/Tag/固定提交；高级版本矩阵支持 2–8 个版本，保留原始 SHA。静态模式分别扫描端点并展示 `present/absent/changed/unknown`，避免“候选消失=已修复”；智能模式可让 Agent 在授权版本间读取具体补丁前后路径、相关 helper、守卫与调用链，给出条件化“可能修复/根因仍在/未覆盖”；真正 `affected/fixed` 必须有编译配置、修复映射或验证证据。

**所有模式的统一产品语义**：静态/智能是用户选择的扫描深度；R0/R1/R2 是内部研究实现/性能对照，普通用户永远不用选择模型调用轮数或工具类别。一次审计由 `audit_id` 关联 `source_prep → scan_job_ids → diff_job → agent_batch → human_review → report`，每阶段保持独立状态，重试幂等且绑定原始版本。

## 4. 风险中心：三个彼此独立的维度

### 4.1 可信度 Confidence / Evidence Tier

- **高可信风险候选**：固定 Git/source/report hash 可校验、根因和上下文证据具有充分独立支撑；若属于 N-day/1-day，必须核验具体历史公告、漏洞根因模式、目标仓库当前未修复代码及适用条件，而非仅匹配 CVE 字符串/版本号。Agent 结论本身不能充当独立事实。
- **待验证候选**：扫描器命中，但守卫、攻击入口、动态影响、解析或模型调查不完整。
- **来源/覆盖未知**：证据绑定不成立、parser blocked/partial 影响了所需推理；仍属于候选，不能称安全。
- **低优先级/已反证**：人类或独立静态证据指出反例，保留历史，不悄悄丢弃。

当前 `smart_audit.risk_snapshot` 高可信门依赖完整来源与人工 R0 义务审查，**不得直接换成“LLM 高置信度”**。未来可增加官方补丁/固定版本的确定性专用 Gate，但必须记录可检验的来源链和审查依据。

### 4.2 严重程度 Severity / Impact（独立于可信度）

| 级别 | 视觉 | 含义 |
|---|---|---|
| 严重 | 紫红 | 可能具有严重影响，仍按证据说明 |
| 高危 | 红 | 潜在高影响 |
| 中危 | 橙 | 潜在中等影响 |
| 低危 | 蓝 | 潜在较低影响 |
| 未分级/提示 | 中性 | 信息不足，**不能偷偷默认低危** |

优先依据可追溯 CVSS 向量及影响条件；若目前只有检测器自报 severity，在界面明确为「危害等级（初判）」。Agent 可以提交**建议等级 + CVSS 假设 + 证据引用**，不允许无事实依据改写静态原始严重度。

### 4.3 验证状态 Verification（与上述两者并列）

`candidate` → 人工复核 `needs_evidence | likely_false_positive | confirmed_component_mechanism` → 在运行时影响/入口/产品条件完整时 `confirmed_product_vulnerability`；实际数据库迁移要保留当前既有状态枚举和审计追踪，不允许前端单方面写 `confirmed`。

**一条风险卡应同时显示**：「高可信候选」/「高危（初判）」/「尚未确认」/「已完成 AI 研判」；另显示组件、函数、CWE/CVE 关联、证据数量、受限覆盖、简要根因、建议下一步。点击进入详情 → 固定源码证据 → AI 解释 → 人工判定。

### 4.4 风险去重/分组

一次漏洞可能触发多个规则、文件、多次扫描；默认优先按源码根因指纹/入口/汇点/别名关系聚合，若缺充分证据只做“相同观测”聚类，**不能宣称多行记录是同一个已确认漏洞**。跨版本根因匹配记相似度和反证，不把规则/源码行号相同当成产品影响。

## 5. 用户可读的 Agent 多阶段工作流（目标，当前尚未全部实现）

不把 Agent 做成普通聊天框或一轮意见生成，而是一个有状态、可复核、分步限权的证据调查过程：

| 阶段 | 内部代理/职责 | 输入与输出 |
|---|---|---|
| G0 候选门控 | Deterministic Router | 绑定候选与源 hash、风险类别、证据义务、优先级；筛掉错绑和明显重复 |
| G1 根因分析 | Root Cause Investigator | 从危险语句推断需要证明的 Source/Caller/Guard/Sink/Effect，生成可测试假设 |
| G2 跨文件追踪 | Context Navigator | 只访问固定 Commit 中经校验的文件范围；函数定义/引用、caller/callee、宏与配置定位；多步读取有引用 |
| G3 反证搜索 | Skeptic / Counterexample | 主动寻找上层鉴权、长度检查、对象生命周期、sanitizer、不可达分支，减少误报 |
| G4 历史补丁对照 | Disclosure/Patch Analyst | 仅使用有来源的公告、补丁、固定历史对象；确认 N-day / 1-day 适用性和是否回归 |
| G5 验证规划 | PoC Planner（无执行权限） | 输出 Harness 所需编译、输入、失败观测、修复对照的**可执行计划草案**；不能假造运行结果 |
| G6 证据裁决 | Evidence Judge | 逐条引用工具证据、说明未解决项，给出高可信/待验证建议；系统确定性 Gate 决定实际风险标签 |
| G7 报告撰写 | Report Writer | 依据锁定证据生成可读摘要、根因、影响条件、修复建议与未验证事项，引用 SHA/路径/行 |

“多代理”可以是**单 Provider + 多角色隔离提示/状态机**，无需同时购买多个模型；独立反证和 Gate 才是创新重点。每一步保存运行 trace、工具输入输出 hash、冻结的 prompt/tool/model 版本和实际 Token/费用。失败降级只影响智能层，不能删除静态结果。

**必须加的工具能力**（受约束）：`find_symbol_definitions`、`find_callers`、`read_fixed_file_range`、`find_related_files`、`inspect_guard`、`read_patch_diff`、`get_parse_coverage`、`get_build_profile`；每个工具只能查指定仓库固定对象、受限文件数量/字节/步数；不得让模型执行 Shell、联网访问任意 URL、读任意服务器文件或提交源码更改。可跨已授权的其他源码文件夹/仓库，仅当这些源对象在任务授权的 scope 与 manifest 中；任何新文件/新增远端来源都必须重新预览授权。

创新可写入作品报告的内容：**多引擎候选协同 + 证据义务驱动 Agent + 主动反证 + 历史补丁可回放 + 跨版本根因关联 + 源码保密授权闭环 + 以人工真值对照评估“误报减少/证据完成率/成本”**。不声称单层 LLM 即自动发现产品漏洞。

## 6. 人工与 AI 双通道，不互相覆盖

默认扫描结束进入统一风险中心。操作：「AI 继续追查」「人工审查」「加入调查案例」「历史对照」「导出报告」。人工可标记 `确认候选机制/误报/证据不足/接受风险/待修复` 并上传有效证据；若要“确认产品漏洞”，必须有独立证据门（产品构建、可达性、权限/攻击者控制、CIA 安全影响、运行或授权 Harness 复现、修复重验）。模型可提出理由和建议，但不得自动代替人工签字；审查员的复核历史不能覆盖或篡改原始 Detector/Agent 记录。

## 7. 高质量漏洞报告

用户版报告每一项必须有：标题、风险类型/CWE/CVE 关系、初判严重度、可信度与验证状态、受影响仓库/分支/提交、源码定位及关键代码、根因简述、攻击前提/入口/调用链、模型证据支持与反证、修复策略（代码层与配置层）、补丁差异、验证方案与结果、覆盖限制。**没有执行的 PoC 用「PoC 计划（未执行）」；组件 Harness 不能写作“产品已利用”。** 输出人类可阅读 HTML/MD；带页码的 PDF 可后续接入。专家版导出 raw report/manifest/review/agent trace/哈希及 deterministic report provenance。

报告需保留两种视图：「审计概览（受众为管理者）」及「技术详细报告（受众为审计员与比赛评委）」，同一个 report_id、同一来源与版本，不允许 AI 编辑基础扫描记录。每项报告建议按结构化 Schema 生成，先校验证据引用再渲染 Markdown/PDF。

## 8. 仓库中心与自动下载

来源目录推荐 OpenHarmony GitCode 组织镜像，通过独立定期同步元数据校验名称/clone URL/默认分支/镜像来源。用户只选仓库名称；管理员指定一个默认受控下载目录、多个只读现有根目录，支持同名仓库副本归并、默认只展示健康副本。启动审计若 Git 对象缺失则先进行允许来源的 Git clone/fetch，再固定 SHA/Tree；未通过远端校验、磁盘配额和目录安全校验禁止自动下载。Docker Worker 使用只读持久化 volume，共享固定对象的身份与 hash，不运行仓库 hooks、submodules、构建命令或 Git LFS 自动获取。多仓全量扫描另设批量配额，不等于普通单仓模式自动支持全部 807 个仓库。

## 9. Agent 费用与数据安全

商业用户可以使用较大预算，但**不能无限制扣费或无授权外发源码**。推荐初始“企业标准”：每任务最多分析 20 条高优先候选，最多 6 条升级跨文件深查，每个候选最多 6～12 个受限工具步骤，**建议管理员默认上限 USD 25/任务**，可在管理员政策内放宽；每次预览展示最坏请求/Token/费用与文件类别，授权与计划 SHA、模型 endpoint/model、实际脱敏类别及允许目录绑定。当前实际实现的限制仍是最多 5 条初轮、有限 R2，不得把推荐数当已完成。按 Provider 的真实费率卡判断可用性，缺费率必须经显式费用风险确认或阻止自动流程，不能承诺账单硬限制。

采用 fail-closed 的只读文件权限、自动脱敏、隐私标注、禁止 Prompt Injection 诱导扩权、跨租户/跨仓库隔离。证据中不得透出 API Key、仓库凭据或私有源码路径给未授权的用户。

## 10. 任务状态机与降级

`created → source_preparing → version_pinned → static_running → static_completed → agent_queued → agent_investigating → report_ready`；分开记录 `source_status`、`scan_status`、`agent_status`、`report_status`。静态扫描 partial/blocked 时报告仍可生成但不能标安全。模型无配置、无外发授权、连接失败、费用不足、证据校验失败、取消时保留原始扫描，标记 `agent_not_requested | agent_blocked | partially_completed`，报告明确“AI 未完成”与原因。对端点扫描失败的时间/版本操作保留已完成端点，不输出虚假“已修复”。

## 11. 用户端到端验收场景

| 用例 | 期望 |
|---|---|
| 无本地仓库、在线目录选择已批准 OpenHarmony 仓库 | 后台下载/固定 commit 后执行所选模式，能观察失败和重试 |
| 仅静态（全部三种方式） | **零模型请求**，有风险与覆盖报告 |
| 智能授权（全部三种方式） | 冻结全任务及各端点外发清单，自动启动多阶段 Agent，用户无须逐条选择 R1/R2 |
| 已披露 CVE 旧版及修复版 | 有根因与 source/hash/补丁对照；匹配不等于产品已受影响 |
| 同一规则高严重度但 parser partial | 应标“待验证 · 高危（初判）”，不自动升级高可信 |
| 模型说“100% 已确认” | 仍是待审候选；人工/运行证据门未通过 |
| AI 跨文件检索误请求目录外文件 | 工具拒绝，保留日志及 unknown，不扩大作用域 |
| Agent 费用/超时/撤权 | 静态报告保留，智能状态明确部分完成 |
| 人工反证/确认 | 审查历史追加留痕，AI 与静态原始记录不被覆盖 |
| PoC 没执行 | 报告明确标为“计划”，不编造输出 |
| 模型生成漏洞报告 | 所有事实与代码/补丁/验证结果有引用，缺项明确标 unknown |
| 重启/幂等重试 | 固定提交/授权哈希不变，队列重复请求不重复创建相同模型作业 |
