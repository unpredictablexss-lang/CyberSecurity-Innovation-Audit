# 2026 OpenHarmony 漏洞挖掘系统架构与实施决策

> 设计版本：2026-10-02。适用条件：3–4 名计算机专业成员、约两周准备期、可先用 Windows 电脑上的 WSL2/Ubuntu，必要时租 Linux 服务器，尚无 OpenHarmony 开发板。本次只设计方案，不实现扫描器。
>
> 推荐方案：以可构建的 OpenHarmony C/C++ 组件为切入点，先完成“候选发现—原代码验证—安全影响复核—版本分析—报告”闭环；将历史补丁中的安全约束迁移作为主要研究增量。IPC 权限语义审计为有目标环境时的扩展路线。
>
> 本文中的模块、时间预算、验收门槛均为工程设计，未经过本项目实测，不代表官方指定方案或已实现能力。

## 1. 先做哪些决定

两周内的首要矛盾是验证环境与有效成果的获取成本。代码可以由 AI 辅助编写，但构建是否可信、调用是否可达、PoC 是否违反接口契约、修复是否损害正常功能，仍需靠实验回答。方案的实施单元应是一条真实组件上的闭环，不是依次写完九层抽象框架。

建议锁定以下范围：

| 决策 | 两周版本 | 扩展条件 |
|---|---|---|
| 主语言 | C/C++ | 有真实额外攻击面和验证环境后再增加其他语言 |
| 主漏洞族 | 长度/尺寸计算导致的越界读写、整数异常形成的内存安全后果 | 主闭环完成后增加有限生命周期 UAF/重复释放 |
| 主目标 | 一个可构建、可测试、有外部输入路径的真实组件；再扩到第二个 | 不先承诺具体仓库必有漏洞 |
| 广度 | 对锁定源码集合做轻量索引与候选扫描，记录未覆盖项 | 不能把少量组件深审宣称为全 OpenHarmony 深度覆盖 |
| 创新增量 | 从历史修复抽取安全约束，在其他位置检查约束是否成立 | 用留出样本验证，不能把历史已知漏洞重现说成新发现 |
| 平台 | 本机 WSL2 或独立 Linux 构建/分析环境 + 隔离执行器 + 文件化证据 | 资源不足时再租服务器；不优先建设微服务、图数据库、复杂前端 |
| 大模型 | 辅助理解、查询草案、harness 修订、报告解释 | 不能直接决定漏洞成立、CVE、权限模型或环境等价性 |
| 设备 | 第一阶段以宿主机组件验证为主 | 第 2 天前若获得匹配目标版本的系统环境，再开 IPC/权限路线 |

两周应形成三个分开的成果层级：可复现的工具闭环、历史漏洞与安全对照上的实测能力、真实目标中的新候选及其审核状态。前两者可作为工程验收目标；新漏洞数量及官方认可不能保证，也不能用旧漏洞代替。

## 2. 对赛题和现有资料的重新核对

### 2.1 六项能力和五类交付物

用户提供的 2026 赛题要求：自动分析 OpenHarmony 源码；给出描述、CWE 和已有 CVE；为识别出的每处漏洞提供可执行 PoC；评估严重度及模块/功能/版本影响；提供修复建议或补丁方案；生成完整报告。

五类交付物是工具源码、源码技术说明书、使用说明书及 DEMO、漏洞分析报告、性能说明。因此系统的核心数据需要直接支持这五类导出，不能将报告完全留给最后手工整理。

修复补丁的自动生成、自动应用、自动重验是本项目建议增加的能力。官方允许提供修复建议或补丁方案，并未要求所有补丁都由工具自动产生。

### 2.2 不能遗漏的范围与表述

赛题交付物中仍有“指定时间段或指定版本的代码提交”表述。应同时支持：

1. **版本快照模式**：分析固定 manifest、仓库 SHA 与构建配置。
2. **时间窗口模式**：枚举窗口内提交及受影响函数，并在明确的代码快照中分析。窗口外的调用者、头文件、防护逻辑仍可能是必需上下文。
3. **历史复现模式**：使用已披露漏洞的修复前后版本检验工具，结果单独标注。
4. **跨版本模式**：对给定版本集合逐项记录状态，不根据分支名猜测。

时间窗口究竟要求逐提交扫描、窗口末快照还是其他形式，用户提供的赛题没有进一步说明，需要向赛事渠道确认。架构保留输入适配能力，不退回到只分类安全提交。

官方提及 DoS、空指针，又排除普通 DoS、功能问题和无安全影响的健壮性问题。结论应取决于攻击者能力、受影响服务和安全边界；“进程崩溃”不足以自动成为合格漏洞。具体边界以赛事答疑和官方审核为准。

### 2.3 对旧架构保留与修正

| 原有思想 | 保留部分 | 必须补上的条件 |
|---|---|---|
| 漏斗式九层 | 广扫与深审分离 | 独立 fuzz 发现通道，避免所有发现被规则过滤 |
| Tree-sitter → Clang | 轻量解析和精确语义分工 | 语法树不提供完整类型、宏展开、别名和可达性证明 |
| Evidence / Finding / Case | 统一证据与根因归并 | 加入目标快照、构建配置、实验记录、反证与不确定性 |
| PoC 状态机 | 生成、构建、运行分别记录 | 编译成功不等于触发，触发不等于安全影响，失败不等于无漏洞 |
| 分支补丁匹配 | 用等价变化查回迁 | 提交存在仍可能被撤销、部分修复或重新引入 |
| 内容 hash 缓存 | 避免重复解析 | 头文件、宏、ABI、规则、摘要和编译参数变化必须失效 |
| 多证据融合 | 排序与可解释性 | 同一根代码事实不能因多个工具重复报告被反复加分 |
| 最后做 Benchmark | 无 | 基线与资源计量从第 1 天建立 |
| 全程序图与多语言 | 作为远期接口 | 两周内只建设真实案例需要的局部表示和适配器 |

2025 项目的经验来自用户提供的复盘文档，本次未独立检查朋友项目源码与获奖证明。可以继承问题拆解方法，不能据此声称拥有或复现了其实现。

## 3. 总体架构：多路发现、统一证据、按需验证

~~~mermaid
flowchart TD
    A["指定版本 / 时间窗口 / 本地源码"] --> B["目标清单与构建配置冻结"]
    B --> C["语法索引与攻击面清单"]
    C --> D1["规则与现成静态分析"]
    C --> D2["历史补丁安全约束迁移"]
    B --> D3["现有或新增 harness 的独立 fuzz"]
    C --> D4["接口与权限语义审计"]
    D1 --> E["候选池 / 根因关联 / 证据仓"]
    D2 --> E
    D3 --> E
    D4 --> E
    E --> F["预算调度：选取下一项缺失证据"]
    F --> G1["局部程序分析与路径核对"]
    F --> G2["原组件构建与动态验证"]
    F --> G3["目标系统可达性与身份验证"]
    G1 --> E
    G2 --> E
    G3 --> E
    E --> H["安全影响复核与报告门槛"]
    H --> I["CWE / CVE / 版本影响"]
    I --> J["修复建议或补丁与对照实验"]
    J --> K["报告 / 复现包 / 性能与覆盖统计"]
    E -. "上下文与实验反馈" .-> L["受约束的 LLM 辅助"]
    L -. "待验证建议" .-> E
~~~

图中的“层”是职责边界，不要求部署成不同服务。第一版可用一个控制程序、少量独立工具进程、SQLite 元数据和按 hash 保存的证据文件实现。

关键设计是双向反馈。例如构建失败后，调度器转去补依赖；fuzz 触发后再补静态根因；静态分析找到真实上游约束后记录反证；目标系统不可达时，保留组件缺陷证据但限制结论范围。并非所有候选都机械地穿过全部模块。

## 4. L0 目标与构建环境必须成为一等对象

### 4.1 OpenHarmony 是多仓库组合

用官方源码入口确认比赛范围，再解析所选发布版本的 manifest，记录仓库到源码目录的映射及每个仓库的实际 commit。不能随意拼接各仓库最新 master，随后称为某个 OpenHarmony 发行版。

OpenHarmony 官方组织提供 [manifest 仓库](https://github.com/openharmony/manifest)。GitHub 镜像可用于阅读和检索，但参赛目标的来源、版本及同步状态需与官方入口核对。本次未验证比赛最终指定版本。

TargetSnapshot 至少记录：

- manifest 来源、版本和内容 hash；
- repo URL、repo commit、源码相对目录、文件内容 hash；
- subsystem、component、构建 target；
- target triple、CPU 架构、位宽、sysroot、宏、编译参数；
- 工具链版本、生成头文件、依赖版本和构建日志；
- 是否来自完整源码、组件裁剪或教学样例。

manifest 与各仓库提交一起固定才能复现；分支名和 tag 只保留作展示标签。

### 4.2 三种分析能力模式

| 模式 | 可用条件 | 可以声称 | 不能据此声称 |
|---|---|---|---|
| syntax_only | 源码和轻量解析器 | 语法位置、调用形态、候选结构 | 完整类型语义、所有防护缺失、目标可利用性 |
| semantic_partial | 部分真实编译参数/头文件/类型 | 已解析范围内的关系及假设 | 未解析部分安全、跨配置结论普遍成立 |
| build_verified | 锁定目标配置可构建或真实编译单元验证 | 该配置下更可靠的类型、宏与程序关系 | 构建通过即证明无漏洞或 PoC 必定可达 |

宿主机可编译和目标系统可编译也需分开。x86_64 上的尺寸、对齐、signedness、库函数行为不能自动代表 ARM 目标。

[Clang 编译数据库规范](https://clang.llvm.org/docs/JSONCompilationDatabase.html)描述了每个编译单元的目录与参数。首选获取已有数据库或从所选版本构建系统导出/捕获真实编译命令；导出方法需在那个版本上试验，不能假设所有 GN target 都能直接导出。生成数据库后抽查少量原始编译单元，确认工作目录、宏、sysroot、生成文件和参数有效。

### 4.3 先选可验证组件

第 1–2 天对 3 个候选组件做构建探测，最终保留一个主目标、一个备选。选择表需实际填写：

| 条件 | 证据 | 用途 |
|---|---|---|
| 有输入处理边界 | 文档、公开 API、解析入口及调用者 | 确认研究对象与攻击面 |
| 有单元测试或 fuzz harness | 对应 target、构建文件与试运行日志 | 降低验证成本 |
| 能保持原代码编译 | 实际组件对象和链接依赖 | 避免把重写片段当原系统 |
| 有已披露修复对 | 公告、修复前后 SHA、差异 | 建立对照基线 |
| 不依赖难获得硬件 | 设备/驱动/权限依赖清单 | 决定是否适合两周主线 |
| 目标版本存在 | manifest 映射与源文件证据 | 避免分析赛题范围外代码 |

解析器、序列化、数据转换、文件格式处理是候选方向，不是已确认漏洞清单。IPC 核心和 AccessToken 属于需要认识的平台机制，不代表首个目标必须审计这两个核心仓库。

## 5. L1 与 L2 发现通道和最小程序表示

### 5.1 先复用分析引擎

首版建议：轻量语法索引 + 一个可运行的成熟 C/C++ 分析器 + 少量面向目标组件的自定义查询/规则。工具选择实验见 [路线文档](technical_routes.md)。没有必要同时集成 Clang、CodeQL、Joern、Semgrep 并自研另一套全程序分析器。

本项目应自建的主要部分是目标配置适配、安全约束模型、证据契约、验证调度、版本对照和报告闭环。第三方工具负责已有解析/分析能力；报告明确记录来源，避免将引擎能力当作原创算法。

### 5.2 最小表示

保留文件、函数、符号、调用、参数位置、分配/释放/使用事件、约束与证据引用即可。可按需读取现有引擎 CFG/数据流，不必将全库永久转换为统一超大图。

每条调用边标记 direct、resolved_indirect、possible、unresolved。未解析函数指针、虚调用、动态注册、宏条件、FFI 和异步回调必须显式留下缺口。可能调用关系不是已证明的执行路径。

函数摘要应表达：哪些参数影响返回值/输出参数、长度与容量关系、分配/释放与所有权变化、前置条件、失败语义、可能副作用，以及摘要来自静态计算还是人工模型。LLM 草案通过人或工具验证之前不作为已确认摘要。

### 5.3 候选不能只围绕危险函数

优先寻找“不可信尺寸—运算/转换—容量—实际访问”关系，涵盖循环、容器索引、自定义拷贝和包装函数。看到 memcpy_s 不能默认安全：传入容量可能不真实、返回值可能未处理；反过来，看到 memcpy 也不能直接报告漏洞。

独立 fuzz 通道从原组件入口和现有测试出发，不要求已有静态命中；保留少量探索预算给低排名组件，测量静态筛选之外能新增多少根因。这是控制漏报的结构性设计。

## 6. L3 三类分析使用不同语义模型

### 6.1 内存与整数主线

围绕一次访问建立证明义务：

- 对象的真实容量是多少，来自哪个分配或容器状态；
- offset 和 length 的有效范围是什么；
- 长度单位是否一致，是字节、元素、字符还是结构体数量；
- 运算的位宽、符号、提升和截断是什么；
- guard 在哪些路径成立，保护哪个对象与哪一版本的值；
- 检查到使用之间是否重新赋值、改变对象或发生别名写入；
- 外部调用者是否已经限制输入；
- harness 是否满足入口的合法调用约定。

例如“不超过剩余空间”的安全性质可写为数学关系 offset ≥ 0、length ≥ 0、offset ≤ capacity、length ≤ capacity − offset；必须先约束 offset ≤ capacity，再在目标机器整数语义下检查减法。仅写 offset + length ≤ capacity 可能遗漏加法回绕。此处是建模示例，不能机械地替换所有项目代码。

分析从函数内区间/关系开始，对少数候选按需扩展调用者与被调函数。循环、递归和别名复杂时输出 unknown，不因超时推定安全。若采用约束求解，整数位向量、内存模型和摘要假设要保存；模型下不可满足只表示对应路径被排除，不是整个函数安全。

### 6.2 UAF 和重复释放作为可选增量

状态应绑定抽象内存对象，不只绑定变量名：allocated、live、released、escaped、unknown。跟踪释放后使用时，还需检查别名、所有权转移、引用计数、容器失效和回调存活。

两周内只考虑实际目标出现的函数内或短调用链案例。并发 UAF、复杂共享指针语义与异步状态空间先保留为人工审计候选。线程竞争的可靠证明需要调度证据或 happens-before 推理，不能由文本中先 free 后 use 推出。

### 6.3 IPC 权限与逻辑问题

[OpenHarmony IPC 官方仓库](https://github.com/openharmony/communication_ipc)描述 Proxy/Stub 与系统服务通信；[AccessToken 官方仓库](https://github.com/openharmony/security_access_token)描述基于 token 的权限管理。由此设计的审计链是：

真实调用者 → 服务暴露入口 → 请求解包 → 身份来源 → 权限策略 → 受保护资源/操作 → 可观察结果。

这是本项目的审计模型，不是上述文档声明存在的漏洞。需要核对：

- 服务能否被该低权限主体获取并调用；
- token/UID 是可信运行时提供还是参数声称；
- 校验的主体、资源、动作与最终操作是否一致；
- 检查结果是否控制路径，而非仅调用了检查 API；
- 身份切换、代理调用、异步任务之后使用的是谁的权限；
- SDK、IPC 公共入口、服务内部是否存在其他有效防护。

普通 source-to-sink 污点路径不足以表达全部授权关系；需要 subject、resource、action、policy、decision、effect 六类事实。兄弟 API 不一致只是线索，因为两者策略可能合理不同。

主机 mock 身份检查能测试分析器，但不能证明目标系统越权。必须使用真实低权限主体和真实服务，加入授权主体成功、未授权主体应失败等对照；root shell 调用成功不能证明普通应用权限绕过。

## 7. 主要创新：从补丁表面变化迁移到安全约束

旧文档提出“修复前模式 A → 修复后模式 B”。本方案进一步要求抽取补丁修复的安全性质，而非只查找 A 的相似代码。

一张 PatchPatternCard 包含：

| 字段 | 作用 |
|---|---|
| provenance | 公告/公开补丁、修复前后 SHA、知识可用时间、许可 |
| root_cause | 为什么原行为违反内存/权限/生命周期性质 |
| preconditions | 模式适用的类型、调用约定、数据可控性 |
| unsafe_relation | 可能被违反的关系 |
| repair_obligation | 修复想保证的性质 |
| accepted_guards | 已识别的等价防护形式 |
| counterexamples | 看起来类似但安全或不适用的实例 |
| validation_recipe | 检测该性质的测试方式与依赖 |
| confidence_and_review | 提取可靠性及复核记录 |

例如某补丁增加尺寸乘法前的上界检查，可抽象“用于分配的乘积必须在指定类型中可表示，并与后续访问单位一致”。迁移对象即使使用另一变量名、另一分配 API，也可被检索；已在调用者检查、使用受检算术 API 或限制容器长度的候选，应保留为安全对照。

流程分四步：低成本 token/语法召回 → 变量/对象关系对齐 → 搜索能满足该义务的等价 guard → 为缺失或未知部分产生验证任务。相似度只负责召回，不宣布漏洞。

历史补丁不天然等于安全补丁，修复后也不天然全局安全。混合提交、功能修改、部分修复需人工剥离。本次两周内建议做 1–2 类可明确建模的尺寸/边界义务，避免构建通用“漏洞知识大模型”。

需用消融回答：相同成本下，这种约束迁移相对文本/AST 相似检索，是否减少误报、发现不同位置的根因、缩短复现时间。没有实验前只称“研究假设”，不声称独创、领先或能发现未知漏洞。

## 8. L4 证据、状态与预算调度

### 8.1 漏洞判断分三个正交维度

- **缺陷事实**：候选、静态支持、动态触发、已反证、证据不足。
- **环境与可达性**：教学样例、宿主机原组件、目标配置组件、真实系统入口。
- **安全影响**：尚不明确、普通质量问题、局部安全后果、已证实边界突破。

三者共同决定能写什么结论。不能用“ASan 触发”统一覆盖所有维度，也不能让一个未经校准的 0.9 替代证据。

Evidence 要保存产生工具/版本、完整源位置与 hash、目标配置、假设、原始 artifact、正反结论和依赖证据。AST、规则、LLM 都引用同一代码事实时，不能当作三份独立证据累加。人工修改判断需保留理由和旧状态。

### 8.2 任务失败不等于候选被否定

验证结果至少区分 build_failed、environment_blocked、timeout、not_triggered、triggered、harness_invalid、inconclusive。LLM 或 fuzz 尝试失败不减少代码本身的缺陷证据；只能降低本轮继续投入的优先级，或形成下一项实验。

只有确认有效 guard、路径不成立、输入不符合契约等具体反证，才能关闭对应假设。not_triggered 只说明这次输入/预算未触发。

### 8.3 调度依据下一项缺失证据

候选卡列出最重要的未知项及最便宜的验证动作。例如：

- 类型未知：补编译配置，不先反复生成 PoC。
- 入口未知：检查调用者与输入契约，不先增加 fuzz 时间。
- 已触发但无安全影响：做攻击者能力/可达性复核。
- 系统依赖缺失：标记阻塞，切换到备用可验证候选。
- 已有稳定 PoC：优先完成版本、修复和报告，避免留下半成品。

队列按可验证性、潜在影响、证据缺口成本与类型覆盖排序。可预留约 20% 探索预算给独立 fuzz/低排名样本；这是可调整的起始预算，不是统计最优值。不要强行将每层候选压成预设百分比。

## 9. L5 PoC 的设计和验收

### 9.1 四级环境证据

| 级别 | 实际完成的实验 | 可表达的结论 |
|---|---|---|
| V0 教学/合成 | 自建或重写样例触发 | 验证分析管线，不计为 OpenHarmony 发现 |
| V1 原组件宿主机 | 固定 SHA 原始源码在 Linux harness 中触发 | 原组件在该宿主配置和契约下有缺陷；目标适用性待核 |
| V2 目标配置组件 | 对应架构、宏、依赖与运行环境中触发 | 指定组件配置受影响；系统入口可能仍待核 |
| V3 系统入口 | 从真实允许的低权限/外部入口到达并触发 | 在记录的主体、设备、镜像与版本下证实影响 |

正式报告必须标出级别；V1 是否满足赛事“指定环境”的要求需要确认。没有目标设备时可继续推进组件证据，但不能默认为 V3，也不能认为所有 V1 都一定被比赛接受。

### 9.2 优先复用原 harness 和构建目标

验证计划包含目标函数、合法输入空间、必要初始化、依赖替身清单、预期安全性质、观测方法、清理方法及超时。stub 只替代与所验证性质无关的环境依赖；不能移除长度检查、身份检查、锁或所有权逻辑来制造触发。

优先链接原始组件；必须裁剪时保留原始文件 hash、裁剪差异与语义限制。摘抄十行危险逻辑自行编译，只能证明摘抄版本，不足以确认原系统。

### 9.3 不同类型有不同 oracle

Oracle 是“怎样认定实验真的出现所研究问题”的明确判据。

| 类型 | 必需观察 | 常见误判 |
|---|---|---|
| OOB/UAF | 对应目标代码的 sanitizer 栈、对象/分配信息、可重复输入 | harness 自身越界、错误初始化 |
| 整数异常 | 具体位宽与运算异常，及后续错误容量/访问或边界后果 | 正常设计的 unsigned 回绕 |
| 信息泄露 | 未授权主体获得带标识的合成敏感数据 | 本就允许读取的数据或单纯崩溃 |
| 权限问题 | 主体权限状态、预期策略与实际敏感副作用 | 测试进程原本有高权限 |
| 生命周期 | 分配、释放、使用的同一对象及顺序证据 | 无关指针、正常所有权转移 |
| 高影响 DoS | 真实外部触发、服务影响与恢复条件 | 测试程序自崩溃，无安全边界说明 |

[ASan 文档](https://clang.llvm.org/docs/AddressSanitizer.html)支持将越界、UAF、重复释放等作为内存错误观察手段；它不替代本项目对攻击面与安全影响的分析。[UBSan 文档](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)明确指出 unsigned 溢出与部分转换检测不包含在普通 undefined 组中。应记录实际启用检查，不能笼统宣称 ASan/UBSan 覆盖所有整数问题。

### 9.4 重现、最小化与修复对照

最小化必须保持同一个根因/目标位置与判据，不能仅保持进程非零退出。保存原始和最小输入、随机种子、执行命令、依赖与输出 hash。

内部验收可要求确定性 PoC 在干净状态重复 5 次，并由另一成员从新目录复现；这只是最低工程检查，不意味着统计上证明普遍稳定。保存成功次数/总次数，对并发问题另报调度条件和更充分的实验，不把一次触发称稳定。

修复验证包含：

1. 原始版本能构建，恶意输入触发预期问题。
2. 修复版本能构建，同一输入按设计被安全处理。
3. 正常输入在两版本保持合理功能行为。
4. 临界相邻输入与同族变体继续检查。
5. 证据与原始二进制/补丁 hash 绑定。

“补丁后 PoC 失败”不能指编译失败、程序退出在无关路径、测试不再调用目标或删除整个功能。通过上述检查仍只支持已测试范围，不能声称形式化证明所有漏洞消失。

## 10. L6 分类、CVE 和严重度

CWE 按已确认根因选择，必要时保留后果类别；不要为一次越界触发拼接多个 CWE 增加“类型数量”。参考 [MITRE 根因映射指南](https://cwe.mitre.org/documents/cwe_usage/guidance.html)，记录分类依据和不确定项。

CVE 关联按公开公告、产品/组件、受影响配置、代码位置、补丁与行为逐项匹配。没有足够材料时使用 cve_status=unmatched 或 insufficient_evidence，绝不因类型相同强行匹配。未检索到编号不等于新漏洞，更不等于已确认 0-day。

新发现状态独立保存：novelty_unassessed、possible_new、submitted、acknowledged、accepted、duplicate、rejected。具体官方认定按赛题奖励计划评审结果；两周内未收到回应就如实展示待审。提交和公开发布是人工流程，不由工具自动向外发送。

严重度先写攻击者权限、交互条件、影响数据、可用性范围、作用域和部署前提。若使用 CVSS，则固定版本、列出向量及每项证据；未证实代码执行时不能凭堆越界自动写 RCE/高危。排序优先级、模型置信度和严重度是不同字段。

去重以根因与修复义务为中心，关联多个位置、路径和版本。相同栈顶不一定相同根因；同一个根因在三个分支不计为三个独立漏洞。聚类支持人工拆分/合并并保留来源。

## 11. L7 版本影响与修复

每个版本必须映射到 manifest 和实际 SHA，并单独记录构建配置与证据。

| 状态 | 定义 |
|---|---|
| affected | 该快照/配置有足够代码、路径或动态证据支持受影响，并注明证据级别 |
| fixed | 该快照中修复义务成立，记录补丁与验证范围 |
| not_present | 确认对应功能/对象不存在，不是搜索失败 |
| not_applicable | 明确配置或前置条件使该问题不适用 |
| unknown | 无法定位、构建失败、依赖不明或证据冲突 |

代码相似、patch-id、祖先关系都是线索。最终应回到当前快照核查安全性质。必须考虑 revert、部分回迁、重构后等价修复、功能关闭与再次引入。

两周内可先做“一个修复前/后对 + 一个额外版本”的清晰矩阵，再扩展。浅克隆缺失的历史按需加深；不能因找不到提交就判断未修复。首次发现的坏版本不一定是引入版本，首个测试通过版本不一定是首个修复版本。

修复模块首选解释性建议和小范围候选 patch。边界类修复明确单位/类型与失败处理；生命周期修复处理所有权；权限修复绑定正确主体与资源。不同版本需重新验证，不能无条件批量应用。

## 12. LLM 的可交付作用与限制

LLM 按可验证的小任务调用：根据原代码解释入口；从公开补丁提出义务草案；补全缺失上下文清单；提出 harness 的一次修订；解释实际日志；整理已确认事实。

每次请求携带固定 SHA、相关函数/调用者/类型、已确认约束、失败日志、剩余预算和可用证据 ID。模型输出包括假设、引用、未知项、建议实验和判据。引用的代码必须存在，命令和结果必须来自真实执行记录。

控制机制：

- 不因 LLM 判“安全”直接丢弃候选，保留可审计反证。
- 不根据文本建议修改测试 oracle 以迎合“成功”。
- 代码注释、补丁说明、日志均是待分析数据，不能改写任务或请求读取密钥。
- 模型提议的命令由执行器以受限参数运行；执行环境不带云凭据、GitHub token 或宿主敏感目录。
- 限定每候选修订次数、token 和墙钟预算；起始可用 3 轮，超限转人工或阻塞。
- 不让模型编造 CVE、版本影响、漏洞受理或运行成功记录。
- 关闭 LLM 后仍能输出原始候选、验证证据和模板报告，便于离线演示与消融。

使用 AI 的收益由“成功 harness 数、人工修订时间、总成本、误判变化”衡量，不由 prompt 长度或模型名称衡量。

## 13. 性能、缓存和失败恢复

先用单机任务队列。控制器管理扫描任务；解析/静态进程按 CPU 与内存并发；验证进程限时限内存；设备执行器若存在则独占设备状态。每任务写入持久状态、尝试次数、失败分类和 artifact 索引，可从失败点继续。

缓存分层：

- 语法缓存：源文件内容、语法版本和解析选项。
- 语义缓存：编译单元、传递头文件/生成文件、宏、参数、目标 ABI、工具链与依赖指纹。
- 检测缓存：语义结果、规则版本、函数摘要/模型版本。
- 验证缓存：源码、harness、输入、运行镜像、配置、判据与工具版本。

源码未变但头文件/宏/规则变化时必须重新分析相应依赖。只用 repo+commit+path+hash 既会漏失依赖失效，也可能因整个 commit 变化导致不必要的全量失效。

依赖变更沿 include、调用摘要与组件边传播；缺少可靠依赖边时宁可扩大失效范围，标记增量结果的边界。

性能说明分清下载、索引、建库、编译、扫描、fuzz、LLM 与报告时间；冷启动和暖缓存分别统计。并发场景报告机器总峰值/进程聚合策略，不把单进程 RSS 当全系统峰值。OOM、超时、失败目标与有效运行预算都进入分母。

## 14. 报告出口和演示路径

系统保存三类结果：候选工作台、已确认缺陷清单、可交付漏洞案例。所有未确认项可导出给研究人员，但不得计为已确认漏洞数。

正式案例最低要求：精确目标、合法触发条件、可执行 PoC、真实结果、安全影响依据、CWE、CVE 状态、版本矩阵与未知项、修复建议、复现说明。项目自设 reportable 门槛不能缩小比赛最终要求；尚缺 PoC 或指定环境证据的项目必须明确为未完成项。

演示建议展示一条完整路径，再展示规模与限制：

固定目标 → 扫描/导入真实结果 → 展示 source/guard/对象关系 → 执行原始版本 PoC → 展示安全对照 → 检查版本矩阵 → 导出案例 → 展示覆盖、耗时和失败清单。

独立 fuzz 新发现的候选也应展示来源。离线录制与实时运行区分；不能把预存报告伪装为现场新发现。

## 15. 两周内的架构取舍

**必须完成**：目标版本固定、一个真实组件的构建验证、基础候选与证据、至少一个历史修复前后案例、真实目标候选研究、报告/使用说明/性能统计。

**优先增加**：尺寸约束迁移、独立 fuzz 通道、有限跨函数上下文、第二组件或第三版本、harness 辅助修订。

**有条件增加**：真实系统 IPC 权限案例、较复杂 UAF、自动 patch。

**本轮暂不投入**：全程序符号执行、自研通用 CPG、多语言统一分析、模型训练、分布式集群、复杂 UI、无人监督自治挖洞代理。

没有新漏洞时，工具和历史基线仍是有效工程成果，但不足以替代新发现方面的比赛竞争力；应坦诚说明。这也是必须在第 3 天就拿到真实组件闭环、而不是第 10 天才开始验证的原因。
