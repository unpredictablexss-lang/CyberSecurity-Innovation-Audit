# 实验与评价方案

> 本文件区分赛事评分维度与本项目内部可复现实验。比赛没有公布可直接套用的固定评分公式；以下门槛与统计方法由团队制定，不能当作官方标准。

## 1. 三套结果分别统计

1. **公开历史回放集**：已披露修复前代码，验证工具能否找出已知根因，测试修复后能否不误报。它证明能力，不代表新发现。
2. **安全对照集**：具有相似 API/结构但安全的代码，检查 guard、调用契约与版本差异，测误报。不能只用毫不相似的“安全 hello world”。
3. **目标源码盲审集**：在锁定的当前目标快照内搜索，候选由成员独立审核；实际真值可能不完整。它是发现新问题的地方，不能把未经审核样本全算阴性。

三套数据彼此隔离。回迁补丁、同根因多个分支、近克隆应归同一组；训练/调规则时看到的案例不算独立测试。

## 2. 对应官方评价项的实际证据

| 评价方向 | 该记录什么 | 不能怎样算 |
|---|---|---|
| 准确性 | 审核后 TP、FP、仍未知；正式报告独立复核 | 将未验证候选删除后宣称 100% 精度 |
| 完整性 | 已知修复对命中率、静态候选范围、独立 fuzz 新增根因 | 在未标注全库上声称真实 recall |
| CWE | 根因分类、目标 CWE、人工复核依据 | 用规则名称自动填 ID 即算准确 |
| CVE | 公告/补丁/版本对应，匹配/未匹配/未知 | 未搜索到就称 0-day |
| PoC | 构建成功、有效 harness、触发、重复、跨环境复现 | 把 build_success 当 trigger_success |
| 分支 | 每个固定快照的 affected/fixed/not_present/unknown | 把分支名或 cherry-pick 当最终状态 |
| 修复 | 原样恶意输入、正常功能、边界变体、补丁可应用 | 补丁让测试不再执行目标就算修复 |
| 性能 | 冷/暖耗时、CPU、峰值内存、失败数、覆盖分母 | 排除下载/构建时间却称端到端速度 |
| 创新 | 与成熟引擎和相似度检索比较及消融 | 只说“融合 AI” |

## 3. 覆盖率必须分多层

定义同一 ScanScope 的分母，例如某 manifest 指定的 C/C++ 源文件总数。分别报告：

- acquisition：成功取得的仓库/目标数 ÷ 计划目标数；
- syntax：成功解析的文件/LOC ÷ 纳入范围的文件/LOC；
- semantic：有可靠编译上下文的编译单元 ÷ 计划编译单元；
- rule：执行某类规则的目标数及排除原因；
- dynamic：实际进入 harness 的入口/代码区域；若可测，给执行覆盖；
- version：被判断为非 unknown 的快照数及每个状态的证据。

这些数字不能合并成一个“全库覆盖率”。按仓库、组件、语言、阶段列出跳过文件及原因。第三方、生成代码、测试代码是否计入分母须预先写规则，不能为了提高指标事后删掉困难文件。

## 4. 精确率、召回率与未知真值

在公开标注集上可以计算 TP/(TP+FP) 和 TP/(TP+FN)，但必须先定义单位是**根因**还是**告警**，并做跨版本去重。若负例集只是部分人工选取，结果只代表该测试集。

对目标源码，真值不完整，不能宣称全量召回。可报告：

- top-k 人工审核有效率及每例耗时；
- 随机抽样的低分候选中发现的漏筛根因；
- 独立 fuzz 发现、静态未命中的有效根因数；
- 未验证和环境阻塞数；
- 已公开漏洞与待审新候选分别统计。

抽样方法和 k 值在实验前固定。样本很小时展示原始计数，并明确不确定性；不为了漂亮数字发明小数点后两位。

## 5. PoC 质量协议

每份 PoC 保存原始代码 SHA、环境、编译命令、输入、oracle、正常对照、修复后对照、首次成功时间、重复运行成功次数与总次数。至少从干净目录由非作者成员复现一次。内部起始门槛可设为确定性案例 5/5 次触发同一根因，但并发和时序案例另定实验，不将 5/5 当严格概率保证。

复现层级标注 V0 自建样例、V1 宿主机原组件、V2 目标配置组件、V3 真实系统入口。视频和正式报告用相同级别表述。记录失败运行，不只截图成功一次。

Sanitizer 命中只能证实其对应的运行错误；其本身不能证明远程可达、权限边界和实际严重度。特别记录 harness 与组件栈帧的归属。

## 6. 性能测量协议

固定目标 manifest/commit、机器规格、OS、工具版本、规则集合、线程数、缓存状态、排除项。至少运行：

1. 冷扫描一次：源代码已在本地，但分析缓存为空；下载单独计时。
2. 暖扫描一次：目标与规则均不变；报告缓存命中率。
3. 增量扫描一次：只改变一批指定文件/头文件，检查失效传播。
4. 端到端一例：从输入到报告，单列构建、静态、fuzz、LLM、人工审核时间。

采集墙钟时间、峰值机器内存/进程内存的定义、CPU、磁盘占用、成功文件和失败文件、PoC 数。若机器内其他负载显著，重新测或注明干扰。不能拿冷扫描和其他工具暖扫描比较。

## 7. 创新模块的最小消融

在相同版本、样本和资源预算下比较：

| 组 | 包含能力 | 看什么 |
|---|---|---|
| B0 | 成熟静态工具/朴素 API 规则 | 候选量、独有有效根因与审核时间 |
| B1 | B0 + 文本/AST 历史补丁相似检索 | 相似候选的召回和误报 |
| B2 | B0 + 安全约束迁移 | 在等价防护负例、改名/重构样本上的结果 |
| B3 | B2 + 独立 fuzz 与动态反馈 | 新增根因、可报告案例、每例验证成本 |
| B4 可选 | B3 + LLM 辅助 | 成功 harness、时间和误判是否改善 |

若 B2/B3 没有统计上或实践上清楚优势，论文/答辩就陈述限制，并展示失败例。不能从“组件数量增加”推断算法创新。

## 8. 赛题提交材料与指标追溯

工具源码提供固定版本、依赖和一键命令；技术说明解释算法边界与模块；使用说明逐步复现；视频展示同一 case_id；漏洞报告引用 Evidence 和 RunRecord；性能说明引用 ScanRun。五项材料不得出现相互冲突的漏洞数量、版本或运行环境。

正式报告中的每个漏洞要包括：源码位置和内容、根因、CWE、已有 CVE、触发条件、影响路径、PoC 源码/步骤/结果、模块/功能/版本、严重度依据、修复建议或补丁，以及未知项。见 [交付清单](deliverables_checklist.md)。

## 9. 可接受的负面结果

真实目标上没有新漏洞、某版本无法编译、某候选被上游 guard 排除、某 PoC 只能 V1、某补丁造成回归，都必须进入实验记录。负面结果帮助选路线，也防止在最后把“工具跑过”误写成“漏洞已经确认”。
