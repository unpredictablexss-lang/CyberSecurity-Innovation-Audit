## Upstream source identity

The official GitHub repository is `pnggroup/libpng`. GitHub commit metadata identifies the fixed change as `aa77ef38c17ab2fc1b41bec09fb973c6a386641d` (`fix: Clear stale zstream pointers when releasing the inflate stream`), parent `4eeb825ab26605ed34cd74495d4cce920939fe9f`. The commit describes stale `zstream.next_in` / `avail_in` after chunk decompression ownership release, allowing `png_read_IDAT_data` to skip refill and inflate from a deallocated input buffer when `png_read_end` precedes row reading. The patch adds `png_inflate_detach_buffers` and calls it on claim and release paths. GitHub reports 19 additions and 14 deletions in `pngrutil.c`.

The ordinary `git clone --bare --filter=blob:none` attempt failed with a connection timeout to `github.com:443`. The connector returned commit metadata and exact file bytes but not the official commit tree ID. The tree ID therefore remains explicitly unavailable; it was not inferred from a file blob.

## Status and remaining evidence

`CVE-2026-46675` remains `PARTIAL/BLOCK`. The source pair is now file-byte bound and the upstream patch rationale is confirmed. The current model does not represent zstream buffer state ownership across chunk decompression and IDAT reads. `png_handle_iCCP` parse remains partial; source-only replay does not establish malformed-chunk trigger feasibility or OpenHarmony product reachability.

Minimum next evidence: obtain the upstream full Git object graph/tree ID; resolve parser-visible declarations for the partial iCCP fragment (or review a bounded local-fragment contract); then model and independently validate the release-to-IDAT read transition with vulnerable, exact fixed, read-rows, malformed-chunk, safe, and unrelated controls. Product build and call-path evidence remain separate requirements.
