The pinned D52 interface assigns `GET_PASTE_DATA = 0`; the stub maps that request to `OnGetPasteData`, which calls `GetPasteData`. I confirmed line 41, D77's candidate anchor, is the opening brace of `OnRemoteRequest`, not a permission check or data operation.

The exact-revision whole-tree permission-helper probe has five hits, all declarations/definitions or the helper's delegation to the mock. It identifies no call site on the GET route. D77 correctly treats descriptor mismatch, invalid account mapping and absent clip as transport/identity/data-absence controls, not permission controls. The controls are source-bound; no test binary or device behavior is claimed.

### `SUPPORT_PENGLAI_MODE` branch

The exact SAMgr source contains the reported branches in `GetSystemAbilityInner` (lines 650–653), `CheckSystemAbilityInner` (688–691), and `LoadSACheck` (780–783). Each is compiled only under `SUPPORT_PENGLAI_MODE` and then guarded at runtime by `isPengLai_` before calling `SamgrUtil::CheckPengLaiPermission(systemAbilityId)`. The fixed SAMgr `BUILD.gn` defines the macro only when `support_penglai_mode` is enabled. These are additional checks on SA acquisition/loading, alongside the conditional SELinux check.

That strengthens the reason to leave effective external authorization unknown: the inspected source has more than one conditional acquisition policy. It does not show a check on every later Pasteboard Binder call. D77 accurately leaves product build flags, runtime mode, policy, installed profiles and method-level authorization unresolved. The new evidence does not change the narrow D52 finding: the pinned component method path has no visible local caller read-permission predicate before the per-user lookup/copy.
