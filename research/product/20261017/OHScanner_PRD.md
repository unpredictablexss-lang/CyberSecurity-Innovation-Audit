## V4.1 需求变更（最高优先级）

1. **新建审计只是可展开的导航分组**，点击标题只展开/收起，不跳转中转页，删除旧「新建审计」首页。
2. 分组下直接放三个二级菜单：**仓库安全扫描 / 时间增量扫描 / 跨版本安全分析**，分别直达表单；普通用户无需选检测器。
3. **官方仓库清单**内嵌到仓库扫描和系统设置；**整个社区近15天审计**纳入时间增量扫描的范围选项，不再占独立顶级菜单。
4. **任务详情**归属任务中心；**源码证据、原始候选、人工复核**归属风险中心；**Agent 调查步骤和案例**归属智能调查。
5. **PoC 验证**保留顶级菜单；**版本影响矩阵 + 修复方案 + 修复重验**合并到影响与修复。
6. **漏洞确认与证据门槛**是风险详情、智能调查和 PoC 验证的共同流程，不占左侧菜单。
7. **报告中心**包括单仓、多仓、社区增量、PoC/漏洞案例、性能和赛题交付审计包。
8. **系统设置**含官方仓库来源管理、Git 缓存、语言/规则能力、Agent 模型连接、Worker、日志和实验配置。
9. 所有按钮必须对应真实动作或明确标为设计原型；不得捏造仓库扫描数、已验证 PoC、已确认漏洞和模型调用。

## 三、三个审计表单的关键交互

**仓库安全扫描**：默认检索官方活跃仓库。用户可勾选任意一个/多个，或启用“全选所有已核验活跃仓库”，另设“包含已归档仓库”。默认各仓主分支固定 full SHA，对所有支持的源码按仓/分析单元切片。启动前预检磁盘、仓库清单、工作者资源、语言覆盖与预计任务规模；异步 clone/fetch，避免每次重复下载。本地 Git 对象缓存共享给增量与版本比较。

**时间增量扫描**：范围可选一个仓库、多个仓库或全社区主分支；时间可选 7/15/30 天或绝对时间范围（明确时区和边界）。先冻结来源清单、分支、时间语义、基线和终点 SHA，再确定相关提交、变更文件、影响上下文；不把“15 天内提交者时间”自动等同于“15 天内合入主分支”。全社区方案为仓库级有界并发、失败重试、暂停/恢复及覆盖汇总。

**跨版本安全分析**：单个仓库中的分支/Tag/Commit 解析固定 SHA，支持 2–8 版本矩阵；从风险详情直接“检查其他版本”。输出 `persistent_candidate/new_candidate/disappeared_candidate/unknown` 等静态观察，不依据候选消失就自动判定漏洞已修复；受影响/未影响/已修复须独立证据支持。

## 四、一级页面的视觉结构与动作

**总览**：三种审计方式的快捷入口；最近任务、待处理风险组、PoC 阻塞、Agent 可用性与真实覆盖。**任务中心**：总任务 + 仓库任务 + 文件分片，展示等待、运行、部分完成、失败、取消与可恢复状态；点击任务进入完整日志、资源曲线、源码版本与结果。**风险中心**：默认问题分组而非原始 229 条告警列表，点开查看源码/规则/反证、CWE、公开 CVE 查询结果和人工审查；提供“智能调查”“去 PoC 验证”“跨版本检查”的上下文动作。

**智能调查**：把 Agent 和人工案例放在同一入口；默认以固定源码候选为起点；记录调用计划、只读工具、EvidenceObligation、LLM 提示词版本与调用费用；允许明确受约束的主动研究，但不能自由执行任意宿主命令。**PoC 验证**：待验证候选、审批、只读源码/隔离 Docker worker、验证计划与 PoC 代码、重复实验结果、失败原因以及受控反例；Docker 缺失显示 `blocked`。**影响与修复**：相关代码模块/功能模块、各 Release 分支的实际观察与有效证据、补丁 diff、修复前后重验。**报告中心**：导出完整赛题要求：源码位置、CWE/CVE（公开才标注）、PoC、严重度与影响版本、补丁建议、性能、局限和证据哈希。**系统设置**：官方来源目录与 GitCode/Gitee 官方映射、仓库缓存容量、调度资源、支持语言/规则、模型连接、安全隔离环境。

## 五、实施状态与工程约束

- **可直接复用（前期 GitHub 验证快照）**：React/Ant Design/Monaco + FastAPI/SQLite/Worker，单仓固定 SHA 扫描、候选与 coverage、同版本快照来源核验、人工复核、操作队列、初版日期/双 SHA/版本矩阵、只读调查轨迹、PoC Docker-only 框架。
- **需新开发/重验**：多仓与全社区编排、自动全仓/归档选择、分片续扫、完整语言支持、自动检测器调度、真实 LLM 调用、源审计权限门槛、受控 PoC 实机三方验证、跨版本影响真实性及赛题正式报告闭环。
- **严禁夸大**：C/C++/ArkTS/JS 的目标支持不代表当前均已具备成熟规则；聚类组不等于真实根因；`0 findings` 不能证明安全；安全性不是模型说“确认”就确认。
- **面板样例值一律用“演示数据”显式标注，真实报告必须绑定仓库、提交、解析覆盖、规则版本、人工审查和执行结果。**

### 两个强约束
- 普通 DoS、功能 Bug 不能在没有实际安全影响的情况下被自动升格为安全漏洞。
- “候选”≠“真实漏洞”，静态比较≠“已修复”；PoC 未执行不得写“已验证”。

## 1. 已确定的产品边界
- **对象**：只允许经核验的 OpenHarmony 官方组织及官方镜像，不扫描任意私人仓库；仓库数量不写死 807。
- **语言**：目标 C/C++、ArkTS/ETS、JS/TS 同步支持；当前实际分析能力要在面板上逐语言标注。
- **扫描入口**：仓库安全扫描、时间范围增量扫描、跨分支/版本分析。
- **仓库全选**：默认全选活跃仓库；“包含归档仓库”独立开关；在开始前冻结仓库清单和各仓 commit。
- **执行**：统一自研扫描器，通用漏洞规则借鉴允许使用的公开思路并独立实现，OpenHarmony 特有 IPC/Parcel/权限深挖。
- **检测器**：普通页面不显示选择；规则来源在候选详情与技术设置页保留。
- **高级功能**：PoC 必须人工明确授权、隔离运行，不得由 Agent 在宿主机任意执行。

## 4. 三种扫描任务的精确定义

### 仓库安全扫描
- 范围：手选 1 个、多个，或**全部当前已核验官方仓库**。
- 默认：每仓默认主分支的冻结 SHA；额外“包含归档仓库”开关。
- “全量”指针对固定快照中的**全部受支持源码执行适用规则**，未支持语言、解析失败、资源超限必须显式统计。
- 所有仓库不会同时启动：父任务→仓库→文件/分析分片，控制并发，断点续扫。

### 时间范围增量扫描
- 默认最近 15 天；可选 7/30 天、自定义；区分 committer time 和实际主分支合入语义，显示用户采用的准则。
- 固定清单、主分支端点与提交集合；保留重命名/删除和上下文扩展，不把未变更行全部视为安全。
- 单仓、多仓、整个社区三种目标；无变更仓库报告 `unchanged`，非 `safe`。

### 跨版本安全分析
- 单仓多个不同分支/Tag/SHA，及社区多组件 Manifest 的每仓真实 SHA。
- 状态 `candidate_persists`/`appeared`/`disappeared` 是观察差异，漏洞影响标签必须保留 `unknown` 直到有事实证明。
- 从候选详情可以直接“检查其他分支”，从修复页面可触发修复前后验证。

## 5. PoC 验证（重点必备完整模块）

### 5.1 用户流程
1. 在风险详情点击“加入调查案例”；先确认源码、规则和证据义务。
2. 在案例里点击“准备 PoC”；填写目标固定 SHA、受控运行环境、测试依赖、PoC 源代码与安全影响假设。
3. 进入**PoC 实验室**：提交验证任务，要求人工确认并强制独立容器沙箱；不允许网络连接、不挂宿主机敏感目录、不提升权限。
4. 同一环境对漏洞前版本、修复后版本、补丁版进行对照；有正常输入和触发输入，至少多次重复并保存日志、退出码、资源、哈希。
5. 形成 `blocked`（缺环境）、`failed`（执行失败）、`inconclusive`（证据不足）、`reproduced`（在严格条件下成功触发）；只有达到证据门槛后人工确认。
6. 可在报告导出 PoC 源码、构建与运行指令、环境/镜像摘要、控制实验记录。

## 7. 非功能要求与验收
- **大规模调度**：全选仓库必须启动前确认选择数、活跃/归档统计、冻结清单、磁盘预算和并发计划；不可默认无限并发。
- **可恢复**：断网/退出/重启后任务状态一致，已完成分片按内容哈希和规则版本可复用。
- **隔离**：Git 同步网络访问与 PoC 执行权限分开；PoC 无网络、最小权限、独立容器、资源限额、持久审计日志。
- **性能**：报告每仓扫描耗时、CPU/RSS、吞吐；社区聚合不可掩盖失败仓库。
- **漏洞证据**：包含源码对象哈希、路径行号、规则标识、扫描配置、候选/确认阶段、人工复核历史。
- **公平实验**：PoC、跨版本推断必须有真实对照；召回与误报来自独立标注样本。

## 10. 为什么需要 Agent，但不能直接用 Agent 确认漏洞

真实流程是：自研静态扫描识别候选 → Agent 分析证据、查找反例、管理不确定项 → 程序工具验证路径事实 → 人工批准的隔离 PoC 验证 → 人工依据可信证据最终判定安全影响。模型生成的解释、漏洞名称或 PoC 草稿，本身均不能成为“已确认漏洞”的充分依据。

Agent 能做两件不同的事：**候选导向调查**（主要交付方式）和**受约束主动探索**（后续研究方向）。后者可以在重点安全接口上提出漏洞假设，但必须绑定固定源码和受审计的只读工具，且不能冒充覆盖了全社区所有漏洞类型。

### 核心约束
- 不修改 Git 对象、历史候选、人工审查日志和已冻结扫描报告。
- 不得在宿主机执行模型自行构造的 shell 命令；只允许批准工具注册表中的只读分析能力。
- 不得由模型自动将 Candidate 升级成 Confirmed/Reportable。
- PoC 代码或运行建议必须经过人工审核，交给 Docker-only 独立 Worker；容器无网络、最小权限、只读挂载、资源限额及审计留痕。
- 必须保存模型名称、模型版本/提供方、调用时间、Prompt 版本、固定输入事实摘要、工具调用及结果哈希、Token/费用/耗时、失败与取消原因。
- 当模型不可用/预算耗尽时，传统静态扫描、原始证据查看、人工复核与报告仍可独立完成。

## 11. 新页面：Agent 智能审计中心（17）

### 用户故事
研究人员从风险中心选中一个问题组后点击“Agent 调查”，系统自动附上固定 Commit、候选、源码证据和未完成的 EvidenceObligation。用户不需要自己拼 Prompt。

### 完整线框图
```text
┌──────────────────────────────────────────────────────────────────────────────────┐
│ OHScanner  /  Agent 智能审计中心                                                  │
├──────────────────────────────────────────────────────────────────────────────────┤
│  [待调查风险组 —] [调查中 —] [证据义务待完成 —] [可提交验证 —]                     │
├──────────────────────────────────────┬───────────────────────────────────────────┤
│  发起调查                            │  Agent 能力与安全约束                     │
│  对象：[从风险中心/案例选择 ▼]        │  ✓ 固定 Git Blob 读取                    │
│  模式：[候选证据调查 ▼]               │  ✓ 符号搜索 / 调用链查询                  │
│  模型：[已批准模型 / 未配置 ▼]         │  ✓ IPC 权限 / 数据流事实工具              │
│  预算：[步数] [Token] [费用] [超时]    │  ✓ Git 补丁及版本事实检索                │
│  [创建 Agent 调查任务]                │  × 任意 shell / Git 写入 / 自动 PoC 执行 │
├──────────────────────────────────────┴───────────────────────────────────────────┤
│  Agent 任务列表                                                                   │
│  CASE-001 IPC 权限候选                 证据不足      [查看完整调查]                │
│  CASE-002 ArkTS → Native 桥接          未开始        [查看完整调查]                │
└──────────────────────────────────────────────────────────────────────────────────┘
```

### 交互与状态
- 主入口：风险组详情、案例详情；次入口：Agent 中心“新增任务”。
- 默认输入：Case ID、候选 ID、Repo ID、完整 Commit SHA、Blob SHA、规则及版本、已知事实和未完成义务。
- Agent 模型未连接时显示 `unavailable`，不能显示“正在智能分析”的虚假动画。
- 允许管理员配置模型及权限策略，普通用户只看状态和调查结果。

## 12. 新页面：Agent 调查详情（18）

```text
┌──────────────────────────────────────────────────────────────────────────────────┐
│ Agent 调查 / CASE-001 | 固定 SHA | 工具预算 | 模型版本 | 状态：证据不足            │
├─────────────────────────────────────┬────────────────────────────────────────────┤
│ 调查步骤                            │ 证据台账 / 反证                           │
│ ① 读取固定源码及候选描述            │ 入口可达性           unknown              │
│ ② 搜索入口 / IPC dispatch           │ 真实调用者控制        unknown              │
│ ③ 检查上游权限与接口描述符          │ 权限守卫支配关系      unknown              │
│ ④ 分析输入到敏感操作的数据路径      │ 具体安全后果          unknown              │
│ ⑤ 调查安全反例、产品构建条件        │ 已存在的保护逻辑      待查                 │
│ ⑥ 提议隔离 PoC 计划                 │ 证据引用：Blob SHA + 工具结果哈希         │
├─────────────────────────────────────┴────────────────────────────────────────────┤
│ Tool trace: tool name / params / source SHA / result hash / latency / tokens     │
│ [查看固定源码] [复核证据] [批准进入PoC实验室] [跨版本分析] [导出调查档案]          │
└──────────────────────────────────────────────────────────────────────────────────┘
```

### 核心功能
1. **调查计划**：每一步有明确的待证明事实与可用工具，不是自由无限聊天。
2. **证据与反证同屏**：明确记录上游保护、不可达分支、编译宏、调用者限制等可能使候选不成立的事实。
3. **工具结果可引用**：通过 Git 对象哈希、源码范围、工具输出哈希把模型解释锚定在真实代码。
4. **Unknown 可保留**：工具失败、AST partial、跨进程调用不可解析时必须保留未知状态。
5. **人工干预**：可以标注模型误解、提出新证据或中止调查；人工操作可追溯。
6. **受控 PoC 转交**：Agent 只输出测试假设、受限 PoC 草稿、正常对照及验收标准；由人审核再提交验证队列。

## 13. 新页面：漏洞确认与证据门槛（19）

```text
┌──────────────────────────────────────────────────────────────────────────────────┐
│ 证据门槛 | CASE-001      状态：证据不足                                      │
├────────────────────────────────────────┬─────────────────────────────────────────┤
│ [ ] 固定版本源码路径/内容/哈希         │ 静态检测：候选                             │
│ [ ] 漏洞类型/CWE 及其依据              │ Agent 解释：尚无独立事实证明               │
│ [ ] 攻击者可控输入/入口可达性          │ PoC：blocked（隔离环境未准备）             │
│ [ ] 安全影响和触发条件                 │ 分支影响：unknown                          │
│ [ ] PoC 代码及受控重复执行记录         │ CWE：待人工核对                           │
│ [ ] 修复前/修复后/正常输入对照         │ CVE：无已核验公开编号                     │
│ [ ] 版本/功能模块影响分析              │                                         │
│ [ ] 修复建议、补丁与回归               │ [继续调查] [进入PoC] [修复分析]             │
├────────────────────────────────────────┴─────────────────────────────────────────┤
│ [确认漏洞]：只对被授权的复核人员开放，且必须满足证据条件；不提供模型自动确认。    │
└──────────────────────────────────────────────────────────────────────────────────┘
```

### 状态与术语
- `candidate`：某规则或受约束探索提出的候选。
- `under_investigation`：人工/Agent 仍在补充证据。
- `evidence_supported`：静态或语义证据增强，但没有完成完整确认。
- `validation_ready`：PoC 方案已审查且执行环境就绪。
- `reproduced_in_lab`：在限定环境触发了指定行为，**不等于自动确认安全漏洞**。
- `confirmed`：经实际入口、影响、验证和人工复核，安全结论达到项目确认门槛。
- `reportable`：已补齐正式报告必需的证据和审查条件。
- `rejected`：有足够反证排除当前漏洞假设。
- `unknown`：结论不足或环境受阻，不能折算成阴性结果。

## 16. 结合 GitHub 现状的研发路线（不可捏造已完成）

基于此前核对的 `feat/unified-audit-v2` 及项目 `docs/面板功能与验收.md`：已实现固定 Git 来源、候选和证据、调查案例、只读固定调查轨迹、操作队列与受限 PoC Worker 框架；**真正的 LLM 调用尚未接入**。Docker-only AUTH-01 尚受本机 Docker daemon / 镜像条件限制，不能显示为成功复现。A/B 检测器原始语法候选多，聚类不等于同一根因。跨版本矩阵仅能体现静态观察差异，不能直接确认影响或修复状态。

推荐按照以下顺序推进：
1. **界面信息架构**：新增 17–19 页面和从候选/案例/PoC/版本/报告的跳转，不破坏旧记录。
2. **Agent 工具注册表**：read-only Git blob、符号检索、CFG/权限事实、历史提交对照等明确 schema、预算和错误状态。
3. **真实 LLM 适配层**：显式配置 API 模型提供方、预算、超时、取消、重试、最小数据传输、工具调用审计；没有配置时保持 disabled。
4. **证据义务管理**：将规则产生的 EvidenceObligation 转成可读任务；支持支持性/反证/unknown 状态，来源引用不能丢。
5. **PoC 提议与审批**：Agent 输出验证计划和测试草稿，经过人工批准后提交隔离队列；不能直接调用宿主执行环境。
6. **漏洞确认状态机**：强制证据门槛、人工复核、不可变历史、版本影响和修复重验。
7. **实验验证**：R0（纯静态+人工）、R1（一次模型辅助复核）、R2（工具调用 Agent），在相同固定样本和预算下比较真实误报率、人工时间、有效 PoC 数、费用与证据完整度；不得用模型自评代替真值。

## 17. 对照正式赛题的验收

- 赛题 2：CWE/CVE 的核查及来源展示；CVE 已公开时才关联真实编号。
- 赛题 3：针对已确认漏洞的实际可执行 PoC、隔离环境重复结果，而不是 LLM 生成的代码文本。
- 赛题 4：不同代码模块、功能模块、版本分支的影响证据链；缺证据保留 `unknown`。
- 赛题 5：补丁和修复建议，尽可能配合修复前后的动态对照。
- 赛题 6：报告展示源码、CWE/CVE、PoC、影响版本、补丁、方法局限与真实证据。
- 评估中将误报、PoC 稳定性、代码覆盖、性能与独立人工复核纳入评审；普通功能 Bug 或无安全影响的 DoS 不自动计入漏洞。

## 18. 演示验收脚本（产品与 Codex）

1. 打开总览 → 进入一个真实官方仓库的固定 SHA 扫描，用户未选择任何检测器。
2. 完成后显示实际执行规则/语言覆盖，并在风险中心显示候选组及缺失证据。
3. 选择一个候选，从源码详情进入 Agent 中心；如果模型不可用，界面明确显示“未配置/blocked”。
4. 若 Agent 已接入，记录每步真实工具调用、事实哈希、反证、Token 预算；不可使用虚构日志。
5. 将调查中的测试计划交由人工审批，经隔离环境运行 PoC；缺 Docker 时显示 blocked。
6. 分别展示漏洞版本、修复版本、正常对照的真实执行记录及运行哈希。
7. 在版本影响页展示实际观察差异，未知项不擅自下结论。
8. 仅在全部证据条件满足和人工复核后进入 Confirmed；导出可核验报告。
9. 演示不同 OpenHarmony 仓库的全选、归档开关和社区 15 天增量入口，但在后台尚未实现时按钮不得声称完成真实扫描。
