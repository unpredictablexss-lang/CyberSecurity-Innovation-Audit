## Rule evidence

The OpenHarmony April 2026 bulletin lists CVE-2026-27648 for `web_webview`, CVSS 8.8, in the 5.0.3, 5.1.0, and 6.0 release lines. Its linked release fixes are [chromium_src PR #7093](https://gitcode.com/openharmony-tpc/chromium_src/pull/7093), [#7110](https://gitcode.com/openharmony-tpc/chromium_src/pull/7110), and [#7108](https://gitcode.com/openharmony-tpc/chromium_src/pull/7108). See the [official bulletin](https://gitcode.com/openharmony/security/blob/master/zh/security-disclosure/2026/2026-04.md).

PR #7093 changes two bounds in `nweb_handler_delegate.cc`: `FlowbufStrAtIndex` rejects offset-plus-length beyond the shared flowbuffer data area; `ProcessNativeProxyResultNewFlowbuf` bounds three loops that write `dataList[curIndex]` by the destination list size. The detector retains a candidate if either the unchecked flowbuffer range or the unbounded destination loop/write shape remains in the same source file. It emits a CWE-787 candidate and retains existing product-build, attacker-path, and impact obligations.

## Remediation and claim boundary

The upstream patch rejects flowbuffer entries whose offset and length exceed the shared data segment, then stops reconstruction loops before the destination vector end. This is a remediation reference; OHScanner did not author or validate the upstream patch. A product repair report still needs exact product source/build, the caller and remote-input path, and product-version mapping.

This replay tests the detector signature against a reconstructed positive and exact fixed blob. It does not establish that a historical OpenHarmony release is vulnerable, that any current product includes the component, or that a remote actor can reach the code. The reverse-patch source is explicitly not an upstream historical commit. Findings remain `candidate`, parser coverage remains blocked because parsing was not run, and `validated_vulnerability=0`.
