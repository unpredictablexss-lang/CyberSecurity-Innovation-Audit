# D84 compound-assignment dependency repair

Base: `6cbec8428a5c6c1ca86aa27b62ddc4ff2d06159f`. Detector: `0.21.0` → `0.21.1`.

## Defect and result

Valid C++ reproduction with the synthetic reviewed `Callback` parameter model:

```cpp
void Callback(unsigned key) {
    unsigned value = key;
    value ^= 1;
    HILOG_INFO(1, "%{public}u", value);
}
```

The baseline overwrote the destination dependency with the constant RHS and produced zero
candidates. The repair preserves the old destination plus RHS as may-flow for compound
assignment, and preserves that dependency when the assignment is itself a value expression.
The reproduction now produces one candidate with the source, assignment and sink trace.
Plain `=` still replaces the previous dependency; private operands remain conditional candidates.
This is a false-negative repair, not a claim that lower or higher warning counts measure precision.

## Limits and next slices

The transformation is bounded syntax may-flow. Operator overloads, pointer aliases, arithmetic
zeroing and runtime exposure are not proven; partial/unknown results are preserved. The four
files are a component regression sample, not whole-component coverage or independent labelled data.
No formal accuracy metric or product vulnerability confirmation is claimed.

T83 independently identified that `std::string value=key; value += "suffix";` followed by
`HILOG_INFO(1,"%{public}s",value.c_str());` loses the receiver dependency in the pre-existing
call model. Treat this as a separate receiver-binding development/test slice with compiler-valid
controls. Another future precision slice is sensitive-name heuristic rebirth after proven plain
safe overwrite in an unknown profile; do not suppress unknown calls merely to reduce counts.
