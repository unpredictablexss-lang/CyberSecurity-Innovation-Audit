## 原始漏检与独立修复闭环

原 `D93_POINTER_OUTPUT_GAP_20261020.json` 的 source SHA256 `6418a2ed4490a1416a566ce2ad68fec5503f93b56e608884ff2a89ae1d1a006c` 逐字核验。完整自定义 getter 中 `*length=(unsigned char)value[0]` 把真实输入首字节写到 scalar 输出；Callback 以 &length 接收，随后记录 unsigned length。变量名 length 不改变其 material 语义。

固定 owner 基线 direct/Runner 都是 0 candidate、blocked、service.cpp partial，只有 pointer/member alias gap。这是已知缺口，不能记为安全或 passing metadata。最终二者都产生实际 HILOG material dependency，路径包括 `Callback parameter 0 -> custom getter argument 1 -> assign *length -> may write through argument 4 -> HILOG_INFO public operand 0`。合成 profile 明确将 Callback 参数 0 标为 source，不依赖敏感名字启发式。

独立方法还强制验证直接 *parameter→&local、局部 p=&scalar、透明参数 pointer alias 的实际日志传播；重定向后仅新目标日志携带材料，局部同名 pointer shadow 只污染内部目标。未知 GetDestination() 和 member pointee 写不能静默丢失，最终有具名 `destination_binding` / `unresolved material write` 候选。literal-only *out=7 不生源；普通 scalar overwrite 清除后续日志依赖。callback、unknown/partial 声明保留候选。宏把同名 literal-only helper 替换成 LeakKey 时，实际目标未知，不能借可见函数体免除调用。

另有三项独立 fixed harness 控制直接验证 writeback 边界：

| 控制 | 基线 direct/Runner | 最终 direct/Runner |
| --- | --- | --- |
| 只在 callee 执行 `out=const_cast<char *>(value)`，未写 *out；caller buffer 仍是 public | 2 / 2（cast 被当未知调用、错误 caller 日志） | 0 / 0 |
| 只读 helper，不写 output | 0 / 0 | 0 / 0 |
| memcpy_s 把输入字节写到 out 后记录 caller buffer | 1 / 1 | 1 / 1 |

第三项最终 trace 明确 `memcpy_s -> *out -> caller output -> HILOG`。因此取消输入指针值/局部 pointer rebind 的假输出没有取消真实 pointee 写入。未知目标仍需后续 alias/实际暴露证明；局部显式模型的 completed 状态也不代表产品安全完整性。

## 为什么移除 1880 / 1882 不等于免除私钥内容

判断来自同一 e270 blob `fb0f6cdbf2e151a933ce718a0f95e7ab8e449c28`（utils 67298 bytes / SHA256 `5b5e868bb0b11d8b5172a46c4de49a4fd1548f0a8c261c3c1f141eb033f72bc3`）的原始函数体、前后完整 trace，以及固定 fe8080 的 summary/lvalue 实现，未靠函数名推定释放安全。

1. utils:1878 是 `FreePrivateKeyInfo(options->privateKey)`，传入 PrivateKeyInfo* 的值，没有传 &options->privateKey。FreePrivateKeyInfo:375–390 读取/清理该对象的 privateKey 与 privateKeyPassword 成员；末尾 CF_FREE_PTR(privateKey) 只能改变 callee 的局部 pointer 形参。真实对象字段可以被修改，callee 的输入 pointer 值本身不是新产出的 caller 内容。
2. 1880 实参是 `options->encryptedContentData`，与 privateKey 是不同成员；1882 实参是 `options` 地址本身。旧两条唯一 trace 都是 `1878 heuristic privateKey field -> FreePrivateKeyInfo argument0 -> may write through argument0 ->1880/1882`，没有该字段内容被写入 encryptedContentData 或 options pointer 的 source assignment。
3. 旧 summary 把仍在 callee 参数槽的输入 flow 当成 output，再以 options.privateKey 写回；旧 aggregate fallback 同时污染 root options，于是另一成员和对象地址借用了私钥依赖。最终仅以实际 *parameter/member 写槽产生 raw-pointer output，并区分逻辑 pointee 槽与 pointer 值，取消这段无写入证据的跨成员/地址传播。
4. 私钥材料没有因清理名称被豁免：381、384、386、388 内部 privateKey/privateKeyPassword 的 unresolved 候选仍在，298 的 fetched private-key output 到 890/915 的材料链、ID、message 仍在；自定义首字节输出和真实 memcpy pointee 输出则新增或保持真实日志候选。

该证据只说明旧两条依赖链不再由当前模型支持。原三文件不含完整清理宏/allocator 实现与产品构建，不能证明所有清理调用都安全、所有私钥别名都已追踪或没有实际泄漏。coverage 仍三 partial；callee/macro/type/runtime/impact 的 unknown 按输出保留。
