# D85 explicit local std::string receiver dependency

Follow-up authorized by the D-line lead after T83 found a compiler-valid C++ counterexample
to the original D84 string example. Predecessor: `e72855e970405bb8043cf4bb961207848c957a97`.
Detector: `0.21.1` → `0.21.2`.

```cpp
void Callback(const char *key) {
    std::string value = key;
    value += "suffix";
    HILOG_INFO(1, "%{public}s", value.c_str());
}
```

With the synthetic reviewed Callback parameter model, version 0.21.1 loses the receiver
dependency because `c_str()` has zero arguments. The new rule tracks only explicitly declared
`std::string` local values (direct identifier declarators) and their zero-argument dot
`c_str()` calls. It does not treat an arbitrary same-name method as a standard-library API.
The trace records the receiver conversion; compiler type identity remains an evidence obligation
and the file remains partial when this dependency matters.

`D85_verify.py --source-root D:\openHarmonyScanner\openharmony\foundation\communication\dsoftbus
--output research/data_sensitive/D85_VALIDATION_20261020.json` reproduces:

- Explicit copy and brace initialization, left-sensitive `+=`, and right-sensitive `+=`:
  each changes zero candidates to one.
- Literal-only, ordinary safe overwrite, and unrelated `Fake.c_str()` returning a constant:
  each remains zero.
- Four D10-manifest-verified real DSoftBus C files: five candidates before and after,
  identical findings and outcomes. These C files provide regression evidence only;
  they do not prove C++ receiver-model completeness.

Validation: 51 sensitive module tests passed. The data suite has 90 discovered tests;
89 passed when selecting out the pre-existing Windows `resource` failure described in D84.
The lead has separately repaired that Windows replay issue on the integration branch;
that repair is not part of this D85 worktree or its selected-test result.
T83 independently loaded this implementation and passed eight independent tests, including
the actual std::string paths, safe overwrite, Fake same-name methods and private obligations.
All examples use `%s` with `const char *` from `c_str()` or `%u` with unsigned values.
No target application was built or executed, and no runtime exposure was established.

Known limits: typedefs, `using` aliases, inferred `auto` types, string references/pointers,
temporary/nested receivers, parameters, and other methods remain outside this small rule.
The parser reads `std::string value(key);` as a function declaration without compiler symbol
disambiguation, so this syntax is deliberately not guessed into a constructed local value.
Explicit `std::string` remains a syntax spelling rather than verified compiler identity;
do not promote these candidates without reviewing binding and impact.

The separate unknown-profile sensitive-name rebirth after safe overwrite remains a future
precision task. It was not mixed into this receiver-binding repair.
