## Concrete input error and output gap

In fixed certificate commit `e270363a042bf8f0126881c76d1341ad457cc187`, tree
`e69153afa89928e1318d8b36cf37c65386465fe7`, utils line298 calls:

```cpp
napi_get_named_property(env, obj, CERT_PRIVATE_KEY.c_str(), &data);
```

`frameworks/js/napi/certificate/inc/napi_cert_defines.h:202` defines the global immutable
`const std::string CERT_PRIVATE_KEY = "key";`. This is the property-name input. D87's existing
vocabulary accepted password schema text but rejected this exact name/literal pair.
The old unreviewed-name heuristic therefore treated the c_str() input as a suspected
sensitive return. Meanwhile the ordinary output name `data` did not itself create material
flow, losing the value retrieved from that sensitive property.

The minimal get/has key-only controls each had direct/Runner `1/1`, now `0/0`.
With a following `Consume(data)` or UTF-8 getter call, the count remains `1/1`, but the
candidate moves from the property-name call to the actual output consumer and its trace
starts at `napi_get_named_property private-key-property output argument 3`.
This semantic distinction is visible in the complete frozen probe records.

## Narrow implementation

- Only the exact identifier/literal pair CERT_PRIVATE_KEY="key" is added. Arbitrary
  const strings, other identifiers initialized to key, different literals, mutable values
  and dynamic initializers do not qualify. The existing password vocabulary is retained.
- D87's complete-caller, unique global definition, same namespace, const std::string,
  exact c_str receiver, explicit unique complete include and local-shadow checks still apply.
  API/local custom-body and macro overrides keep normal unresolved behavior.
- The new pair is enabled only through the two reviewed NAPI read APIs in argument2.
  Other operands, unknown wrappers and set-property calls are not excluded.
- A small internal PropertyKeyBinding record carries declaration identity and material kind.
  Existing password source descriptions stay unchanged; the new get output is described
  as private-key-property material. A neutral output name does not hide its may-flow.
- get preserves other operand candidates, creates output3 material and retains unknown
  destination obligations. has returns status/boolean metadata without inventing material.
- The new vocabulary does not extend D89's separate LOGE proof. Binding cache keys include
  the new-pair eligibility flag, so an earlier NAPI read cannot let a later LOGE call borrow
  the new key proof. A usable log-header control still excludes the prior password schema
  operand while retaining CERT_PRIVATE_KEY.c_str().

This retains conditional and unknown states; it does not claim that every fetched property
contains a valid deployed private key or that an unresolved consumer exposes its bytes.
