## Binding decision and length tracking

The original T85 three-file selection includes neither the declaration nor implementation.
Direct N-API includes and GN component dependencies describe dependency names, while the
local master manifest does not fix certificate-e270 to API-bfe8/Node-d6bf. There is still no
exact same-build identity proof or full preprocessor environment.

Therefore nullptr/0 is insufficient to remove a call. A custom body, function pointer,
macro or unknown wrapper can consume material even with those arguments. No global API
name or null-buffer-shape exemption is added. This is a binding limitation, not a demand
for product fingerprints, human review or a new approval.

The existing model can keep length/status logs free of material flow when a complete
visible invented helper only writes a literal scalar and returns a status. The test names
that helper as a local role control, not as the original N-API library. A visible byte-copy
helper still carries source material through memcpy_s into a buffer and its subsequent log.
A same-name custom return remains a material dependency; it is not globally marked status.
An unknown length output must not be declared public merely because of its name or scalar
type. Its alias/write behavior may be unsupported even when an upstream call candidate exists.

## Additional negative: scalar pointer-output gap

Developer research found a separate existing gap, recorded in
`D93_POINTER_OUTPUT_GAP_20261020.json` with full valid custom C++ fixture, explicit source
profile, expected behavior, observed findings/status and limitations:

```cpp
// A custom visible implementation, not the reviewed N-API body:
*length = (unsigned char)value[0];
return napi_ok;
// Caller subsequently logs (unsigned)length.
```

The scanner currently reports zero candidates and blocked/partial with
`pointer/member assignment requires alias proof`. It fails to carry that material write
through the unresolved pointer output or retain a write/call candidate. This is a known
negative result, not a passing safe control. The passing seven-method suite does not assert
that all custom scalar outputs are safe. An exploratory assertion expecting the later log
failed and was retained as this explicit negative research artifact rather than silently
changed into a green safety claim.

This gap further rules out a generalized length exemption. It is outside the D93 decision
to retain original890/915; no broad alias implementation is attempted here. A useful next
slice should at least preserve an unresolved material-write candidate when assignment
alias resolution fails, and separately test concrete destination propagation. It must keep
literal-only metadata writes distinct from writes derived from secret input.
