# D38：CVE-2026-92392 libcurl HTTP/2 upload UAF 候选规则

## 结论

`ohscanner.known_disclosed_cves` 0.15.0 保留一个窄范围 C 源码规则：在 `lib/multi.c` 的 `multi_done` 中，若 `Curl_conn_ev_data_done` 先于 `Curl_req_done`，且连接池回收发生在请求清理之后，则保留 CVE-2026-92392 / CWE-416 候选。0.14.0 曾要求同一函数内存在 `multi_schedule_pending`，导致 8.12.0 和 8.21.0 两个真实受影响源码版本漏报；这两版使用 `process_pending_handles`。0.15.0 去掉与根因无关的调度函数名条件，把证据边界收敛到连接过滤器释放引用早于请求清理。源声明版本位于公告受影响范围时，结果明确记录适用性；没有唯一版本时仍保留形态候选并标出版本 unknown；公告明确不受影响的版本不会因该签名产生该 CVE 候选。

固定源码回放结果：官方 curl 8.12.0-DEV、8.21.0-DEV 两种漏报形态修复后各 1 条候选，8.22.0-DEV 1 条（`lib/multi.c:742`），8.23.0-DEV 修复版 0 条；G 盘 OpenHarmony `third_party_curl` 的提交 HEAD `1386bb128bb060b284309397b97adcaaec21c003` 声明版本 8.8.0，0 条。8.12/8.21 是规则开发时发现漏报并用于修复的样本，不计入独立 holdout。该镜像工作树 dirty，实验仅读取提交对象中的两个文件，没有使用或更改未提交工作区内容。零命中只说明该提交的版本不在公告范围，不能解释成对整个产品的安全证明。

## 公告、根因和修复

curl 项目 2026-10-14 公告描述：上传期间，服务器发来的 HTTP/2 `RST_STREAM`（原因 `HTTP_1_1_REQUIRED` 或 `REFUSED_STREAM`）可能使 `struct Curl_easy` 被释放后继续使用。公告列出的受影响版本为 8.12.0 至 8.22.0（含）；不受影响版本包括低于 8.12.0、高于或等于 8.23.0，以及对应分支修复版 8.14.3、8.16.2、8.20.2 起。官方修复提交为 `8b0744af5b1b631da5b938ca31c3f9895ad5a321`。

回放确认修复差异和规则方向一致：8.22.0 的 `multi_done` 在请求清理 `Curl_req_done` 前先通知连接过滤器并调度 pending handles；8.23.0 将请求清理移到连接过滤器释放之前，并在连接池返回后再调度 pending handles。规则只匹配这一窄序列及版本头，不依据 CVE 名称、组件名或函数名单独判定。

修复建议：升级到 curl 8.23.0 或应用官方修复提交；若维护分支采用回补，需核对其对应的 8.14.x、8.16.x、8.20.x 修复版本。公告还列出禁用 HTTP/2 作为临时规避。是否需要在 OpenHarmony 具体产品采取修复，须先绑定实际构建的 libcurl 版本及 HTTP/2 上传入口。
