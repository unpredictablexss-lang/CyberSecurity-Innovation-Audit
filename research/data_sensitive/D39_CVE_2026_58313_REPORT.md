# D39: CVE-2026-58313 App Domain Verify LRU concurrency memory error

## Conclusion

OHScanner 0.16.0 adds a narrow candidate rule for this historical source shape. The rule requires the LruCacheUtil list node, an unordered_map that stores list iterators, and Get plus Put/Clear operations on the same containers. It reports CWE-416 when those methods do not use the same mutex. A class name or method name alone is insufficient.

On pinned upstream source, the pre-fix header yields one candidate and the lock-protected header yields none. An isolated component harness with synthetic cache keys triggers an AddressSanitizer double-free in 3/3 runs on the pre-fix source; the lock-protected version completes 3/3 runs. This proves that the old component source can produce a memory error under concurrent cache operations. It is not a complete OpenHarmony service build and does not prove a local attacker can reach the path. The public CVE is confirmed; the scanner output remains candidate, product impact remains unknown, and validated_vulnerability remains 0.

- OpenHarmony's August 2026 security bulletin lists CVE-2026-58313 as a bundlemanager_app_domain_verify UAF affecting the v6.1 release line and points to that component's PR #229.
- The pinned fix adds mutex_ to LruCacheUtil and uses std::lock_guard in Get, Put, Clear, and IsEmpty. The old code stores list iterators in lruMap_; Get itself erases and reinserts list nodes, which can race with Put/Clear on the shared containers.

## Component PoC and remediation

The standalone harness is D39_CVE_2026_58313_ASAN.cpp. Its exact source inputs come from pinned Git blobs; results are recorded in D39_CVE_2026_58313_ASAN_REPLAY.json. The harness does not access the network or execute source-repository build scripts. It runs concurrent Get/Put/Clear operations with synthetic keys under ASan.

Use a release containing the official mutex fix or backport equivalent synchronization, and verify that every cache access path uses the same lock. In this run, ASan reported a double-free in the old source and no sanitizer finding in the lock-protected source. The pinned upstream header also emits an unrelated compiler warning because SetMaxCap returns bool without a return statement; this work did not alter upstream code.
