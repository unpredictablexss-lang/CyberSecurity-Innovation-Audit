# D86 heuristic semantic boundaries and C++ type-alignment false positive

Owner input: `1e3b4c0cf02a1d5b0a817cc86dc746d28751b1e8`, detector `0.21.2`.
The worktree's D85 implementation/tests matched that input byte-for-byte. The owner branch
was merged into this branch as `dd8e3b70277127897a4fd1a12e899ebfd7c96d7e`, preserving shared
changes and the Windows replay repair. D86 detector version: `0.21.3`.

## Defensible false positive and minimal repair

```cpp
void f(const char *password) {
    HILOG_INFO(1, "%{public}zu", alignof(decltype(password)));
}
```

The baseline emits one sensitive-material candidate even though only a type's alignment is
output. A second false positive occurs for `alignof(decltype(UsePassword(password)))`: the
baseline walks the unevaluated call as though it executes. The
[C++ draft alignof specification](https://eel.is/c++draft/expr.alignof) defines a `std::size_t`
alignment constant for the operand type. That value is not password bytes.

The repair skips only C++ `alignof_expression` nodes in both value propagation and expression
effects, paralleling the existing sizeof treatment. It does not suppress a whole enclosing
expression or nearby statement. C/GNU extensions and the parser's ambiguous noexcept call
representation are unchanged.

## Named positive, negative and unknown controls

- Hardcoded `"actual-secret"`, ambiguous `"password"`, ambiguous `"<redacted>"`, empty string,
  and unknown API return assigned to a sensitive name all stay `1 → 1`. These literal spellings
  do not establish whether the application uses them as real credentials, attribute names,
  or presentation strings. Empty explicit taint is not treated as proof of public data.
- Type alignment and a call nested inside its decltype change `1 → 0`.
- An actual secret dereference alongside alignment, an actual standalone function call, and
  ordinary material logging remain candidates. Existing sizeof remains nonmaterial.
- Reviewed-source material still reports at its actual log line, while its type alignment
  does not report. Private operands retain sink-privacy obligations; partial parses and
  unknown profiles retain their partial/blocked coverage.

Commands: `python -m unittest tests.detectors.data.test_d86_heuristic_semantics -q` passes seven
named test methods; `python -m unittest discover -s tests/detectors/data -q` passes all 108 tests,
without selecting out the former Windows failure. The replay timeout test intentionally prints
a blocked timeout result while passing its containment assertions.

T85 independently loaded the implementation and checked six valid C++ controls: both alignment
cases `1 → 0`, sizeof `0 → 0`, actual log/hardcoded password/actual call each `1 → 1`.

## Real C++ replay and development/test feedback

`D86_verify.py` verifies T85's exact commit/tree/blob/size/SHA-256 for complete selected files,
with Git lazy fetch and transport disabled. Its nine before/after controls and the real replay
are saved in `D86_VALIDATION_20261020.json`; `--revision` can bind the implementation to a fixed

  --cert-git-dir <openharmony/.repo/project-objects/security_certificate_framework.git>

  `edd28e23c84d17fa072f8501d7fe3dfbfa55498f`, two files/27,560 bytes: `3 → 3`, identical candidate

  `AssetAdd`. T85's older-version replay shows the same warning count but stronger dependency

- Certificate framework `e270363a042bf8f0126881c76d1341ad457cc187`, tree

T85's concrete follow-up is the certificate property key: `CERT_PASSWORD = "password"` at
`frameworks/js/napi/certificate/inc/napi_cert_defines.h:203`; use at
`frameworks/js/napi/certificate/src/napi_cert_utils.cpp:342/347/349` identifies a NAPI property
and logs its name on failure. The heuristic sees `CERT_PASSWORD.c_str` as a sensitive-return
name and retains unresolved-escape candidates. The actual password value is fetched into
the separate `password` variable at line 347. Source/property binding makes this a useful
precision investigation, but this slice does not implement global-constant resolution or
claim modeled product leakage. Generic literal suppression would incorrectly hide real
hardcoded secrets, so it remains unchanged.

## Limits and next executable slice

The repaired false positives are named language-semantic controls; the real components do
not happen to contain the targeted alignment false positive. Counts are not accuracy labels
or formal Precision/Recall, and zero alignment findings are not whole-file safety proof.
The two real components still use unknown-profile heuristics and remain partial/blocked.
No target was built/executed; runtime readers, product visibility and impact are unknown.

Next investigate hash-bound global immutable property-name definitions and property-key
argument positions separately from fetched material. Keep hardcoded credential and unknown
mutation controls, and feed T85's exact files/candidates into the next developer/test pair.
Do not extend this to the second-layer model or suppress arbitrary password-looking strings.
