In this exact arkui implementation, napi_typeof takes the environment and value handle,
checks environment/arguments, chooses a `napi_valuetype` from type predicates, writes that
enum through argument2, and returns napi_status. CHECK_ENV/CHECK_ARG return error status;
napi_clear_last_error clears runtime error metadata and returns napi_ok. The direct function
body contains no string-buffer copy or formatting of the input value. This is a source role
observation at a pinned implementation, not a proof of every transitive engine operation.

The string getter has materially different branches: with null buf it reports UTF-8 length;
with non-null buf and nonzero size it calls WriteUtf8, writes a terminator and reports copied
length. Its return is a status, while bytes flow through buf. In the fixed certificate caller,
line192 specifically queries length, and line208 copies bytes. Both remain unresolved
candidates in the original scanner scope; this slice does not suppress even the length query
without API binding. Describing line192 itself as byte extraction would be inaccurate.

## Why the original candidate remains unknown

The original T85 three-file input contains the certificate cpp, defines header and log
header, not the N-API declaration or implementation. The available repository manifest
uses floating master project revisions, not a fixed certificate-e270-to-NAPI-bfe8 binding.
The GN component dependency identifies a dependency name without fixing its source revision
or preprocessor/link environment. Co-located local heads are separate observations.

The shared frontend also reports the original native_api.cpp, native_api.h, node_api.h and
js_native_api.h as partial; native_api_internal.h and js_native_api_types.h are complete.
These actual statuses are recorded, not overridden. No declarations were cut into a new
synthetic header and presented as the original complete source.

Thus the exact original napi_typeof call can plausibly be metadata-only under the reviewed
implementation, but current scope does not bind it to that implementation. Adding a global
name whitelist would also suppress a same-name custom body, local callable or macro. The
original185 candidate remains unknown, as do192/208. This is a source-identity limitation,
not a product-fingerprint or human-approval prerequisite.
