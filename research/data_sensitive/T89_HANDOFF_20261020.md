## 发现、反馈与闭环

显式合成 source model 将 `service.cpp::Callback` 参数 0 设为 material source，完全不依赖 key 的命名推断。两种有效 C++ 调用形态在基线中均丢失所有 direct/Runner 候选：

```cpp
void Callback(const char *key, void (*CfFree)(const char *)) {
    CfFree(key);
}
void Callback(const char *key, void (*handler)(const char *)) {
    auto CfFree = handler;
    CfFree(key);
}
```

原因是原 `call()` 发现本地 shadow 后直接返回。独立最小反例即时发送开发线与负责人，D90 在该分支记录 unresolved escape。固定版本两案均 direct 0 → 1、Runner 0 → 1，路径为 `Callback parameter 0 -> unresolved call CfFree`，理由为 `local callable target shadows the named API; implementation is unknown`。这是保留未知 callee 消费敏感参数的候选，没有证明 callback 真正泄漏。

其余控制均保持候选：只有名称的 CfFree/CF_FREE_PTR/CfBlobDataFree/memset_s；本地或跨文件同名日志 body；自定义 namespace allocator；缺失/partial header；CfFree、free 或 NULL guard 的宏替换；真实后续日志。宏覆盖放在标准头 include 之后，避免标准头重新定义影响反例。清理后日志正控制先把字节复制到独立缓冲区，再清理原指针，最后记录副本，避免用读取已释放内存充当有效行为证明。

独立读取 Git blob 确认：cf_memory.c:47–52 的 CfFree 为 NULL guard 后 `free(addr)`；cf_memory.h:31–39 的 SELF_FREE_PTR/CF_FREE_PTR 做判空、调用给定释放器、置 NULL；cf_blob.c:43–51 的 CfBlobDataFree 调用 CfFree 后清 data/size。原三文件没有这些定义，不能按名称获得摘要。

即使同 TU 具有精确 CfFree body，当前事实仍不能完成外部 free 的标准库身份及预处理环境绑定，所以本轮拒绝该排除证明。这个保留结果不是指认真实 CfFree 存在泄漏，而是明确当前静态摘要证据不足。输入扩展触发的跨 TU 展开及 partial 门控也导致 direct/Runner 数量不同，故二者分别保留完整结果，不互相替代。
