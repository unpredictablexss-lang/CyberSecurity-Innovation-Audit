### CVE-2024-39775 的源码证据与判定

官方 2024-09 披露表将 CVE-2024-39775 列为 `communication_netmanager_base` 的“网络管理权限绕过”，并链接 4.0 PR #2404、4.1 PR #2403；[NVD 条目](https://nvd.nist.gov/vuln/detail/CVE-2024-39775)记载越界读导致信息泄露，CWE-125。

复验固定对是修复提交 `b99cb78281915a9a2587aca981fa69c969ba8f93` 的直接父提交 `c172839fd6354d9bff189c8b1ade2cf621f4b24f` → 修复提交。该修复提交主题为“修复权限拦截失败问题”，差异仅在 `services/netstatsmanager/src/stub/net_stats_service_stub.cpp` 将 `CheckNetManagerAvailable` 两个拒绝分支从 `return NETMANAGER_SUCCESS` 改为相应拒绝码。调用者 `OnGetIfaceStatsDetail`、`OnGetUidStatsDetail`、`OnResetFactory` 均在 helper 返回非成功时立即退出；漏洞端错误地返回成功会越过这个早退闸门。

当前 B 的 AUTH-07 在两个权限拒绝返回点各产生一条候选（2），补丁端两条都消失（0）。因此我们将“CVE 对应的权限拒绝失效机制”标记为**已披露漏洞的代码级回归命中**；这不是把 CVE 字符串硬编码进规则。检测器 JSON 的 `validated_vulnerability` 仍是 0，静态回放没有验证设备可达性或攻击者影响。当前回放没有独立证明公告提到的 OOB read 数据流及信息泄露后果；这部分仍为未验证，不能把候选或回归命中写成运行时漏洞确认。

旧的 `eb00…→7d0c…` 端点不属于此修复的直接父子对，不用于本清单统计。

2026-10-19 二次源码追踪补记：本地固定源码仓库 `/home/audit/oh-audit-targets/cve39775-netmanagerbase` 含修复对象 `b99cb78281915a9a2587aca981fa69c969ba8f93`，其直接父提交为漏洞端 `c172839fd6354d9bff189c8b1ade2cf621f4b24f`。在 `services/netstatsmanager/src/stub/net_stats_service_stub.cpp` 中，五个入口调用 `CheckNetManagerAvailable`：`OnRegisterNetStatsCallback`（:92）、`OnUnregisterNetStatsCallback`（:115）、`OnGetIfaceStatsDetail`（:297）、`OnGetUidStatsDetail`（:322）和 `OnResetFactory`（:379）；五处均在 helper 返回值非 `NETMANAGER_SUCCESS` 时立即返回。漏洞端 helper 的 `!IsSystemCaller()` 与 `!CheckPermission(GET_NETWORK_STATS)` 两个分支虽已向 reply 写入拒绝状态，却都返回 `NETMANAGER_SUCCESS`，因此调用者会越过拒绝闸门；修复提交将其分别改为 `NETMANAGER_ERR_NOT_SYSTEM_CALL` 与 `NETMANAGER_ERR_PERMISSION_DENIED`。这是补丁、调用关系与当前 AUTH-07 2→0 回归结果相互吻合的代码级证据。该证据没有追踪具体 OOB-read 源/汇，也没有设备端普通应用可达性或信息泄露实测，因此本清单只记为“披露漏洞权限失效机制回归命中”，不记为完整复现或 scanner-confirmed。

补丁来源：[OpenHarmony communication_netmanager_base PR #2403](https://gitee.com/openharmony/communication_netmanager_base/pulls/2403)。公开影响描述仍以 [NVD CVE-2024-39775](https://nvd.nist.gov/vuln/detail/CVE-2024-39775) 为准。

### CVE-2022-42463 的候选为何在修复端保留

OpenHarmony 2022-10 披露表将 CVE-2022-42463 对应到 `communication_dsoftbus` 的 OpenHarmony-SA-2022-1004，并链接 PR #2348；[NVD 条目](https://nvd.nist.gov/vuln/detail/CVE-2022-42463)将其描述为 Softbus_server 回调处理函数认证绕过，并提及 Bluetooth RFCOMM 攻击和任意命令执行。

固定对为漏洞提交 `0db7315e38331e1f28df7ca9e1b8ad62c71c018b` → 修复提交 `07f33ab96652b06f6b84852ea59645d73ff064c7`。修复提交新增 `CheckAuthChannelOfPkgInfoIsValid`，允许 `ohos.distributedhardware.devicemanager.resident` 与 `com.huawei.devicegroupmanage`，并在 `OnRecvAuthChannelRequest` 的解包后、认证通道状态更新前调用。检查使用 `strncmp(peerSessionName, allowedName, strnlen(allowedName, ...)) == 0`，因此代码层面接受匹配白名单前缀的后缀字符串；这一点是确定的源码事实，不等于已证明后缀输入能利用。

当前 B 0.12.12 的固定对回放两端各有一条 AUTH-06：漏洞端 `trans_auth_manager.c:247` 是缺少白名单检查；修复端 `:275` 是前缀比较。候选数量 1→1，但候选依据发生变化。修复端诊断明确写出：精确注册表查找只能证明名称对应某个已注册会话，不能证明它是精确白名单成员，也不能证明注册策略授权该 peer。因此不应仅因查到了 `strcmp` 注册表就把固定端候选压成 0；后缀会话是否可注册/由攻击者控制、传输层是否允许目标 Bluetooth RFCOMM 路径，以及安全影响仍需运行时或更完整产品策略证据。

2026-10-19 再以当前本地工作树重跑这组固定端点，并补充字段来源说明：唯一 `TransAuthChannelMsgUnpack` 定义把 JSON 键 `DST_BUS_NAME` 传给 `GetJsonObjectStringItem`，目标字段是 `AppInfo.myData.sessionName`；解析失败会返回错误。漏洞端与修复端仍为 1→1，确认数仍为 0。诊断只说明被检查字段的源码解码位置，不推断攻击者控制、Bluetooth/RFCOMM 可达性或影响。完整当前工作树报告、SHA-256、测试命令和结论见 [AUTH-06 字段来源复核](20261019-cve-2022-42463-provenance-v0.12.12/README.md)。

旧目录 `CVE-2022-42463-v0.12.3` 中“修复端 0 候选”的结论来自较早模型，本清单以当前 0.12.12 两提交回放为准；旧产物保留作历史记录，不作为当前通过证据。
