## 目的与数据口径

本轮从 B 线 advisory 清单和已披露公告中挑选能取得公开补丁的真实样本，固定修复前后完整 Git commit，用同一版 `ohscanner.interface.ipc` 和单文件 scope 重放。修复前后候选变化用于检查检测器能否观察到补丁对应的代码机制；它不是 Precision/Recall，也不等于漏洞利用验证。目标文件多数为 partial，报告里的“0 候选”不代表未发现风险。

测试提交和公开披露可能不是一一对应的漏洞根因修复。以下每个样本都同时记录补丁实际改动、静态差异和未解决边界。没有因 CVE 已公开而将扫描 finding 升成 confirmed。

## AUTH-07 的实现边界

本轮新增 `ipc.auth.denial-transport-success`，记录“权限拒绝分支向 reply 写错误，但直接返回 transport success”的候选。首次用 Tree-sitter 在真实 Net Manager 文件运行时触发 Python 段错误；为防止新增规则造成整仓扫描崩溃，当前实现使用保留字符位置的有界词法扫描，屏蔽注释与字符串，再检查平衡括号、拒绝条件、错误 reply 写入和同一分支的成功返回。

该规则没有证明 Binder proxy 是否把返回值和 reply payload 分别作为授权结果，也不证明错误码最终被忽略。十条候选中只有 `OnResetFactory` 两条随 PR 2404 删除；其余八条仍在修复版本，正是当前需要人工核查的噪声风险。因此 AUTH-07 保持 `unmeasured`，不可据本次一个修复对声称已校准或达到高准确率。测试覆盖了正例、拒绝码修复例、无关输入失败、安全回复及注释/字符串干扰；没有使用该披露对 holdout 作“通过”标记。

## 下一步优先级

1. **先复核 AUTH-07 的 8 条修复端残余**：绑定各代理方法、reply 解码与服务端 transaction code；若消费者总是读取 reply 中的拒绝码，则对应候选应降为已知误报机制，而不是继续泛化规则。
2. **给权限授权建立显式 API 契约**：对 CVE-2025-26691 这样的权限常量错配，先从接口注解/权限定义/受控策略表导出预期权限，记录来源与版本，再比较实现检查的权限；不得靠方法名或 CVE 函数名硬编码。
3. **扩展服务策略分析而非把 IPC 规则当万能扫描器**：CVE-2025-27247 需要把 `VerifyPermission`、默认 allowlist、配置为空的语义与 IPC caller 连起来。若证据链无法跨文件完整建立，结果应是 unknown/partial，而非“未发现”。
4. **修正 CVE-2025-27563 残余模型**：解释 `GetTokenTypeFlag` 角色条件和 `ACCESSTOKEN_UID` 来源，补正、反、固定样本后重放整组件；不能只删一条 finding 来使计数变好。
5. 这些披露样本属于调参与回归材料，不进入独立 holdout。真实 holdout 仍为 `not_established`，所有家族仍为 `unmeasured`。
