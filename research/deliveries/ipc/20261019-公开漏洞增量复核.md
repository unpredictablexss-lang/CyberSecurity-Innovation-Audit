## CVE-2024-38382：Ability Runtime 漏检边界

修复前 parent：`fd8cd59c2f98c9b5365ee422f58bd82064fe2359`；修复 PR 7767：`f2898e72966a8fcc59ecebc3cdea8d9aab063b1d`。固定三文件范围：

- `interfaces/inner_api/app_manager/src/appmgr/app_mgr_stub.cpp`
- `services/appmgr/src/app_mgr_service.cpp`
- `services/appmgr/src/app_mgr_service_inner.cpp`

修复将 `IsSACall()` 检查加到 `AppMgrServiceInner::GetAppRunningStateByBundleName`。路径由 Stub handler 调用 Service 方法，再转发到 Inner service；修复前后扫描都只报两个与该路径无关的 `ipc.capability.export` 候选（`HandleGetAmsMgr`、`HandleGetAbilityRecordsByProcessID`），没有 CVE 根因候选。覆盖为 1 complete + 2 partial，不能将 2→2 或 0 个相关候选写成“检测器通过”。

曾在临时实验中仅把 `GetAppRunningStateByBundleName` 加入敏感 API 名单，并把 `IsSACall` 加入调用者角色名。结果在修复前后都增加同一条 AUTH-02 候选，仍不能绑定 Inner service 的 guard；这项 counterfactual 修改已撤回，未留在工作树。由此确认：继续加函数名会制造修复后残余误报，正确方向是可审计的跨文件委托链和 guard 归属解析，并须有独立正例、修复例、安全例、无关例后才实现。
