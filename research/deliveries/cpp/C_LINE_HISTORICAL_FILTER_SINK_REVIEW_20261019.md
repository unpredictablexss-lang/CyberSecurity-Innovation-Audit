## Parent path and hypothesis

In the pinned parent `builtins_typedarray_stub_builder.cpp`, `Filter` first checks the receiver/prototype fast-path guards (lines 1384–1403), then calls the user-provided callback inside the loop (1445–1450), creates the output through `NewTypedArray` after the loop (1476–1479), and writes accepted elements with the receiver's `arrayType` token (1494–1499).

The pinned creator checks the species-protector cell again; when invalid or when the accessor has changed, it calls `TypedArraySpeciesCreate` (parent `new_object_stub_builder.cpp`, lines 2285–2296 and 2333–2337). `TypedArraySpeciesCreate` constructs the chosen species and rejects a ContentType mismatch, but permits different Number TypedArray element types (parent `base/typed_array_helper.cpp`, lines 1003–1023). The bound parent `object_operator.cpp` (blob `a192003108694900f1c39a4263a77a782f7c67c4`) invalidates the shared TypedArray species protector when the shared `%TypedArray%` constructor's `@@species` is changed (lines 392–398); `NewTypedArray` rechecks that cell after the callback. This leaves a source-level path for the callback to redefine `Object.getPrototypeOf(Int32Array)[Symbol.species]` as `Uint8Array` after Filter's entry guards and before output creation.

The bound parent runtime chain forwards the provided type token through `SetTypedArrayPropertyByIndex` (`stubs/runtime_stubs.cpp`), then `JSTypedArray::FastSetPropertyByIndex` (`js_typed_array.cpp`, lines 713–748) checks `index < destination.ArrayLength` but derives `elementSize` and `DataViewType` from the passed `jsType`, computes `index * elementSize + destination.ByteOffset`, and calls `FastSetValueInBuffer`. The bound ArrayBuffer implementation writes at that byte index; this path does not visibly check that the write width fits the destination buffer. For a source type wider than the returned Number species, the parent control flow therefore has a credible destination-write-overrun hypothesis. This is stronger than a mere different-origin observation, but remains a source audit: no Ark executable was run and native allocation/adjacent-memory effects have not been measured.

The fix target uses the result object's HClass-derived `newArrayType` for this store (fix target line 1499), so the reviewed parent mismatch is removed in that pinned source. This is a code-difference observation, not product runtime confirmation.
