# A-NULL 静态开发与测试计划

范围限定为比赛需要的 C/C++ 源码静态分析。开发线和测试线并行推进，通过固定源码、规则版本、输入清单与回放结果交接；不把静态候选数当成准确率，也不以动态验证作为本轮完成条件。

## 当前基线

- NULL 默认关闭；只有明确选择全规则研究模式才运行。unknown-return 结果以弱候选/待复核呈现，缺少可靠绑定或构建上下文时保留 `unknown`/`partial`。
- unsafe-memory-call 修正了格式参数位置和字面量边界处理。原始行、来源哈希和不完整覆盖状态保留在最终回放材料中。
- 主线最新基线为 `db77164`。本 PR 把开发侧实现、固定样例和紧凑回放证据放在一起；Python 静态专项 35 项、前端请求 13 项通过，前端构建通过。
- 当前交付只证明指定静态样例与输入子集的行为。它不证明全库 precision/recall，也不替代完整 CFG、类型/别名或构建上下文分析。

## 并行任务树

```text
A-NULL 静态后续
├─ D：开发线（实现与开发证据）
│  ├─ D1 维护 NULL 默认关闭、显式研究选择和弱候选标识
│  ├─ D2 维护未知返回、未知绑定与 partial/unknown 的保守结果
│  └─ D3 每次改规则固定输入/源码哈希，跑 pinned before/after 和静态 controls
└─ T：测试线（独立回归与测量）
   ├─ T1 独立复跑固定 fixtures、controls 和已提交 replay 子集
   ├─ T2 逐项核对源码身份、规则版本、位置、覆盖及原始观察保留
   └─ T3 将无法绑定或无法判断项列为 unknown/partial，不推算准确率
```

## 开发线提示词

```text
角色：A-NULL C/C++ 静态分析开发负责人。
持续目标：持续改进比赛范围内的静态 NULL 与 unsafe-memory-call 分析，让每条候选可追溯到固定源码位置；证据不足时明确输出 weak candidate、unknown 或 partial。
本轮输入：最新 main、A-NULL detector、方法卡、固定 fixtures、已提交的 pinned replay JSON。
步骤：先核对当前 main 和本 PR 的实现；每次只针对一个有复现依据的静态边界改动；补充 positive、negative、same-name/宏/字面量 controls；记录规则版本、源码哈希、覆盖和候选身份；运行对应回归并生成 before/after。
完成条件：实现与测试一起提交；原始位置和不完整状态不丢失；局部变化可由固定输入复现；没有把数量变化写成真阳性/误报结论。
边界：只做 C/C++ 静态分析；没有可信编译上下文时不宣称 CFG、跨函数别名或运行时可达性已证明；不混入动态 PoC 或其他开发线的 detector。
```

## 测试线提示词

```text
角色：A-NULL 独立静态回归与测量负责人。
持续目标：独立核验开发线冻结的源码、规则、scope、静态样例和 replay；候选保持可追溯，无法确认的结论保持 unknown/partial。
本轮输入：开发线提交的 commit、固定 fixtures/control 清单、源码哈希和 replay JSON。
步骤：在独立 checkout 复跑指定静态测试；核对源码哈希、规则版本、候选位置、覆盖与原始行数；检查 fixed/safe/decoy controls；报告差异和最小复现；分别记录观察行、候选组与人工标签，标签未完成时不报告 precision/recall。
完成条件：提供可复跑命令、输入身份、通过/失败项和限制；只对实际复验范围给 PASS/PARTIAL/BLOCK；未核验的结果不背书。
边界：不改 detector 或开发线结论；不以输出减少判定准确率提升；不运行动态 PoC；缺少构建信息、源码身份或独立标签时明确写 unknown/partial。
```

## 交接规则

开发线提交 commit、回放输入身份和预期行为后，测试线据此独立复跑并回传差异。测试失败由开发线修改后重新冻结；没有新证据时两条线继续各自未完成项，不将其合并成一个准确率结论。
