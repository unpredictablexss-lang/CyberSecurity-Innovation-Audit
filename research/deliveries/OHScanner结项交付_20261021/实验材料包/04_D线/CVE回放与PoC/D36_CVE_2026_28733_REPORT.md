# D36: filemanagement storage statistics iterator lifetime (CVE-2026-28733)

Date: 2026-10-19
Detector: `ohscanner.known_disclosed_cves` 0.12.0
Conclusion: **the detector identifies a shared-map iterator lifetime hazard in the public 5.1 source and its linked upstream mutex patch; the finding remains candidate and no OpenHarmony product impact is confirmed.**

## Evidence

The OpenHarmony May 2026 security bulletin（文件引用：https://gitcode.com/openharmony/security/blob/master/zh/security-disclosure/2026/2026-05.md） lists CVE-2026-28733 as a `filemanagement_storage_service` UAF with local attacker code-execution impact, affecting the 5.1.0 release branch. It links the 5.1 fix to MR !2114（文件引用：https://gitcode.com/openharmony/filemanagement_storage_service/pull/2114）. The exact MR commit is `677d6602226d64631fb136fbeabdc39ab5a7eaca`; its parent is `4bd078b3d4034af725f42a69bd67b4806fc6e717`. The 5.1 release branch head inspected during this replay is `3b57e9d315910f390b52545125f5fc3334a35fe0`.

The pre-patch and linked patch change only two files and add `mutexStats_` around `GetUserStatistics` map lookup/insertion and `GetTempStatistics` map copying/clear. The getter returns a `std::map<uint32_t, RadarStatisticInfo>::iterator`; the lock guard is destroyed as the getter returns. Multiple handlers later write through the returned iterator. The radar thread separately calls `GetTempStatistics`, which clears `opStatistics_` under that same mutex. The lock therefore serializes map operations but does not preserve the returned iterator's lifetime during later handler use. The 5.1 release branch source blob is identical to the linked patch source blob, so this pattern is present in the inspected branch head.

The detector matches the same source relation across three pinned revisions: pre-patch, linked patch, and inspected 5.1 branch head. The rule deliberately does not treat the upstream mutex addition as a safe negative control. A value-return/update-under-lock redesign is the safe-shape negative control in unit tests. This is a source-level concurrency candidate; it does not prove a race schedule, exploitability, or that the remaining iterator hazard is the precise cause of the published CVE.

## Fix guidance and limits

Avoid returning an iterator or reference to shared map storage after releasing its mutex. Replace this pattern with an operation that performs lookup/update while holding the same lock, and make snapshot-and-clear atomic relative to those updates; alternatively use a concurrency-safe ownership model that keeps values alive for the full access. A copy-return API alone is insufficient if handlers then need to update shared statistics and silently lose increments.

The CVE itself is publicly disclosed, but this scan does not establish the product build, exact shipped source, runtime race, attacker reachability, or product impact. No service-level exploit PoC or ASan component build is claimed in this report. Product status remains `candidate/unknown`, and `validated_vulnerability=0`.

## Source-shaped ASan concurrency harness

A deterministic source-shaped harness uses the same two operations—return an iterator from the map getter, then snapshot-and-clear the shared map—while a handler thread is paused between obtaining and dereferencing the iterator. With GCC 11.4 and AddressSanitizer, the iterator-escape harness reports heap-use-after-free in 3/3 runs. A safe control that updates the shared value under the same lock used for snapshot/clear reports no ASan error in 3/3 runs. This is a controlled C++ container-lifetime demonstration, not a build of OpenHarmony's service, a product exploit, or proof of attacker reachability.
