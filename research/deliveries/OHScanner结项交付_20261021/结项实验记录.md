# OHScanner 设计到实验结项记录

**整理日期：2026-10-21（中国标准时间）**  
**用途：** 汇总项目设计主线、A/B/C/D 研究实验、平台验证和结论边界，作为结项材料导航。本文是索引与综合记录；实验原始输入、脚本、日志、JSON 和逐项报告仍以所列来源为准。

## 1. 项目目标与验证框架

OHScanner 面向 OpenHarmony 开源代码漏洞挖掘。项目设计目标是串起固定源码版本、静态检测、证据复核、受控组件验证、影响范围分析、修复建议和复验，并提供报告与性能证据。设计原则和产品架构见项目入口（文件：../../docs/README.md）、架构与公共协议（文件：../../docs/架构与公共协议.md）及赛题交付物对齐计划（文件：../../docs/strategy/competition_deliverables_plan.md）。

实施中将不同验证层分开记录：

1. **规则/夹具验证：** 正例、修复例、安全例和无关例控制，用于验证检测规则行为。
2. **固定源码回放：** 对绑定到 commit/blob/hash 的真实或历史源码运行检测器，观察候选和覆盖状态。
3. **组件级动态验证：** 隔离 Harness、ASan 等工具重现特定组件/API 或抽象代码形态，并对照修复形态。
4. **平台与工程验证：** CLI/Worker/API/面板、固定源码读取、报告、并发迁移、构建和回归测试。
5. **产品级漏洞验证：** 需把实际产品构建、入口与权限边界、攻击者可控输入、触发条件和具体安全影响连起来。现有组件结果不自动跨越此层。

状态词按原记录解释：`candidate` 是待核实线索；`unknown` 是缺少证据；`partial/blocked/not_run` 是覆盖或执行状态；它们都不能改写成“安全”或“通过”。只有适合的独立标注数据才用于正式 Precision/Recall。

## 2. 设计到实验的主线

| 阶段 | 设计问题 | 实验/记录 | 可支持的结论 |
|---|---|---|---|
| 建立固定输入 | 检测器究竟分析哪个仓库、版本和文件？ | A/C/D 固定 commit/blob/source hash；IPC 组件清单；全扫描 manifest | 对记录的固定源码和范围可复跑；不代表所有产品版本或整个上游树 |
| 验证规则机制 | 正例能否触发，修复后能否消失，安全/无关控制是否保持安静？ | A 内存安全控制矩阵；B 六家族夹具与规则控制；C parser/runtime 控制；D 旧/修复 CVE 源码对照 | 支持指定规则/控制下的机制行为，不等于全局检出准确率 |
| 测量真实源码表现 | 规则在真实组件中的触发、覆盖与候选形态如何？ | A 五个组件内存安全扫描；B 组件语料普查与规则筛查；C Ark Runtime 固定切片；D 多组件回放 | 支持具体输入范围的源码级观察；候选数量不等于漏洞数，零命中也不证明安全 |
| 验证动态机制 | 隔离输入能否触发错误，修复控制是否阻止该错误？ | A ASan 机制 PoC；D cJSON/libpng/libtiff 等组件 PoC 或 source-shaped Harness | 只支持对应 Harness/API/组件和输入所证实的现象，不能自动证明产品可达或可利用 |
| 验证工具链 | 固定源码扫描、报告和工作台链路是否可用？ | Python/Web 回归、CI、面板隔离验收、源查看哈希核验 | 支持已执行的软件路径；不证明真实 Provider 效果、产品漏洞或未执行部署 |
| 测量成本 | 处理固定组件源码所需时间和内存是多少？ | 11 个固定组件性能测量 | 支持该语料、规则和串行运行设置下的成本估计，不外推整棵源码树或并发负载 |

## 3. 研究线实验结果

### A 线：C/C++ 内存安全与已披露 CVE 回放

- **设计/范围：** bounds、integer/size arithmetic、resource lifetime、unsafe memory calls 等窄静态检测能力；固定 Git 对象扫描与历史修复对照。
- **真实组件测量：** 5 个组件、4,983 个文件、51,551,827 字节，得到 33 条候选、22 个词法分组，累计 67.107 秒；分组只是词法去重。
- **历史回放：** 4 个适用历史案例中，漏洞版本均有 possible hit（4/4）；修复版 3/4 无命中，另 1/4 留有候选。此为小型历史能力集，不是产品 Precision/Recall。
- **隔离 PoC：** 记录了 OOB、整数溢出、UAF/double-free 的机制 Harness 和修复控制；Harness 不等同完整 ArkCompiler/OpenHarmony 产品构建。
- **主要边界：** 尚未确认新发现产品漏洞；产品入口、攻击者控制、部署版本、独立标注真值和全局准确率仍未建立。
- **原始材料：** A 线内存安全交付（文件：cpp/A_MEMORY_SAFETY_DELIVERY_20261017.md）、`cpp/A_MEMORY_SAFETY_SOURCE_HASHES_20261017.json`、`research/evidence/cpp/a_memory_safety_poc_20261017/`、CVE 扫描配置（文件：cpp/A_DISCLOSED_CVE_SCAN_PROFILE_20261019.md）。

### B 线：IPC / 接口安全规则

- **设计/范围：** 六个 IPC 家族，围绕调用者身份、授权、Parcel 长度/位置、Capability 等机制建立可审查规则、夹具和覆盖分析。
- **规则控制：** 交付记录指出 11 条目录规则均有正例控制，六个家族均有 positive/fixed/safe 控制；后续 DATA-06 集成补充正例、修复例、安全例及版本/历史 holdout 契约。
- **真实组件测量：** 30 个组件、约 244 万行代码中，当时只有 5 条规则产生候选；AUTH-01 贡献 166 条候选中的 92 条。数字是候选观察，不是 166 个漏洞或误报标签。
- **覆盖/归因实验：** 对 silent rules、caller-class、解释器归因、覆盖上限、触发形状和 counterfactual 做了分批测量；原始材料逐项说明了规则何时没有触发及其限制。
- **DATA-06：** `ipc.parcel.array-allocation-width` 有规则/夹具和集成回归，报告中明确当前 holdout 测量为 `not_run`；不得从集成通过推导准确率。
- **验证：** D75 集成定向 44 项通过；IPC 套件 368 passed、47 skipped（415 total）。测试结果仅属于对应集成快照。
- **原始材料：** B 线交付记录（文件：ipc/20261017-lane-delivery-record.md）、六家族组件测量（文件：ipc/20261017-six-family-component-measurement.md）、覆盖上限测量（文件：ipc/20261017-coverage-ceiling-measured.md）、`ipc/d74_detector_design_review-20261020.json`、`ipc/d75_data06_integration_closeout-20261020.json`、`research/evidence/interface/ipc/`。

### C 线：Ark Runtime TypedArray / AST 子集研究

- **设计/范围：** 针对固定 Ark Runtime 目标源码与 TypedArray species 行为建立来源绑定、AST 子集分析及受限运行时对照；规则为显式研究候选，不应与普适 C++ 检测能力混为一谈。
- **产品构建证据：** C1 记录从固定 HiHope 配置生成 ARM32 目标对象与依赖闭包，并在隔离环境执行有限运行时探针。species 行为出现候选语义差异，若干独立控制通过；汇总控制脚本在一项断言处中止，其他项保留 partial。
- **parser/检测器最终核验：** T103 对固定 D104 实现复核 data 431/431、compatibility 69/69、定向 51/51；这些测试存在重叠，不能相加为独立样本数。D103 固定 ArkUI N-API 三文件回放为 direct/Runner 0/0 且 blocked，覆盖 3 个 frontend 文件、3 个 detector partial。
- **主要边界：** C1 profile 保持 partial，产品准入 blocked；N-API 真实构建绑定、一般 CFG/alias/namespace/preprocessor、cleanup/sink 绑定等有限。0 条候选不代表无风险；未报告产品准确率或影响。
- **原始材料：** C1 构建 profile（文件：cpp/C1_ARK_RUNTIME_BUILD_PROFILE_20261018.md）、`research/experiments/ark_runtime/c1_product_gn_20261019/`、T103 独立最终验证（文件：../data_sensitive/T103_CLOSEOUT_20261020.md）、D 线最终收尾（文件：../data_sensitive/D_LINE_FINAL_CLOSEOUT_20261020.md）。

### D 线：敏感数据到日志与已披露 CVE 组件复放

- **设计/范围：** 用逐步扩展的源码级敏感流检测器跟踪来源、传播、指针/别名和 sink，同时保留 partial/unknown；另以固定旧版与修复版回放已披露 CVE，并做组件 Harness/ASan 对照。
- **迭代与收尾：** D83–D104 汇总了多个窄规则/解析器切片。最终 D104 对固定实现和证据做有界核对：data 431/431、compat 69/69、focused 51/51；这是实现回归核验，不是 431 个独立漏洞样本。D103 固定 ArkUI 源切片 3 文件、33,437 字节、217 条调用事实，direct/Runner 均 0 且 blocked。
- **组件 PoC 例子：** cJSON CVE-2025-57052、libpng CVE-2026-46675、libtiff CVE-2025-9900 有对应的固定组件/修复形态证据；其他若干 ASan 结果来自 source-shaped Harness，只证明抽象代码形态或数据结构行为。每个报告分别界定证据层次。
- **平台复放：** D39 两轮 Workbench API→Worker→报告→固定源码查看器链路对旧版有候选、修复版无候选；这是工具链/源码规则回放，不是产品入口验证。
- **主要边界：** 产品构建、真实入口可达、攻击者输入可行性、完整日志 sink 绑定和产品影响仍 unknown/not_run。候选为 0 不能证明安全；产品 `validated_vulnerability=0`。
- **原始材料：** D 线最终收尾（文件：../data_sensitive/D_LINE_FINAL_CLOSEOUT_20261020.md）、D104 证据收尾（文件：../data_sensitive/D104_CLOSEOUT_20261020.md）、CVE PoC 与修复索引（文件：../data_sensitive/D_KNOWN_CVE_POC_REMEDIATION_INDEX.md）、`research/data_sensitive/D*_REPLAY*` 与 `D*_REPORT.md`。

## 4. 平台、性能与集成实验

### 性能与规模

固定 11 个组件，扫描 9,508 个源文件、107,087,947 字节（组件树 C/C++ 共 2,618,176 行）；累计串行墙钟 113.64 秒，单进程峰值 RSS 上界 265.7 MB，平均 84 files/s。测量使用固定 Git 对象读取、Tree-sitter AST 解析和非安全示例插件，目标是平台成本，不是漏洞检测能力。`window_window_manager` 超出当前单次范围，按 7 个分片测量；partial 解析文件计入未分析。详见性能实测报告（文件：../../docs/testing/ohscanner_performance_scale.md）和 `benchmarks/perf_scale_corpus_2026-10-10.json`。

### 发布与工作台

项目状态文档记录了主线合并快照：PR #36 合并提交 `2a807d58007c48b9fc87795cf961ba4057f89240`；对应 CI Python 1,464 项运行（16 项按环境条件跳过、无失败），前端检查/构建/UI 测试通过。另有合并前的本地回归快照，计数不同，均应按各自提交与命令理解，不合并成一个总样本数。隔离 18776 端口完成过固定源码扫描、候选/覆盖查看、报告快照及重复生成检查，并修复任务详情缺失哈希白屏。主服务 8765 是否重启到合并代码，在状态快照中明确为未重启。

标准 Worker、真实 Provider、全量产品构建和真实产品动态 PoC 不因软件单测通过而视为已验证。完整版本/提交和后续状态以项目现状与下一步（文件：../../docs/项目现状与下一步.md）为准。

## 5. 综合结果与结论

| 结论项 | 本项目有据可查的结果 | 结论边界 |
|---|---|---|
| 静态检测设计与实现 | A/B/C/D 研究规则、来源绑定、控制输入、固定源码回放和多个报告路径 | 各规则能力受家族、语法、范围、编译配置和版本约束 |
| 组件级漏洞机制 | 若干历史 CVE 或组件/API 的固定版本和修复版本对照；部分隔离 PoC/ASan 复现 | 不自动证明 OpenHarmony 产品包含该版本、入口可达或可被攻击者利用 |
| 修复效果 | 多个历史修复/安全控制在同一回放或 Harness 下未再触发原机制 | 仅对具体测试输入和修复形态成立，不能推导无其他缺陷 |
| 工具工程质量 | 多轮单测、IPC/C++ 子集测试、前端构建、CI、面板/API/Worker 隔离路径验证 | 证据限于列明版本、环境和实际执行路径；被跳过或未执行者保持原状态 |
| 扫描性能 | 11 组件、9,508 文件的串行组件级基准 | 非整树、并发、增量缓存或安全检出效能基准 |
| 检测准确率 | 未形成足以报告正式产品 Precision/Recall 的独立标签集 | 不报告正式 Precision/Recall；开发夹具、历史 CVE 和模型判断不能替代独立真值 |
| 新产品漏洞确认 | 当前材料未证明新的产品级确认漏洞 | 产品 `validated_vulnerability=0`；候选与未知项仍按原报告保留 |

**结项口径：** 项目形成了可运行的源码扫描与证据复核工具、若干规则研究和组件级实验、可追溯的工程验收与性能记录；同时，产品级可达性/影响、完整竞赛漏洞闭环及独立准确率评估没有被当前材料证明完成。此结论是材料范围内的总结，不将未运行步骤写成通过，也不把未知改写为否定结论。

## 6. 复现与归档指引

- 复现时先按各报告指定的完整 commit、tree/blob/source hash、detector/rule 版本、scope/profile、环境和命令执行；不要仅凭文件名选“最新”结果。
- JSON、CSV、原始 Harness、源码副本、命令输出和 hash 清单保存在对应 `research/evidence/`、`research/experiments/`、`research/data_sensitive/` 或 `outputs/` 子目录。本文不复制这些大文件，避免形成不一致副本。
- 历史报告的数字属于各自版本/命令/语料；suite 重叠、分组非漏洞去重、候选非漏洞标签等口径已在相关段落标出。
- 本记录中的项目日期按中国标准时间；源材料保留自身日期和时间口径。
