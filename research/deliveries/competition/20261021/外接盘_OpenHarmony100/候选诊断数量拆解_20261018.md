## 结论

工作簿中的 557,868 是 79 个已生成报告仓库的静态诊断明细行数，不是 557,868 个已确认漏洞，也不是全局去重后的缺陷数。汇总字段 `validated_vulnerability=0`。目前数量几乎完全由 A 线 NULL 候选检测器产生：`ohscanner.cpp.null_dereference` 共 546,559 条，占总数 97.97%；其余 8 个检测器合计 11,309 条。

所以，这个数对“显式启用了宽松候选模式的大型 C/C++ 代码库扫描”并非不可预期，但对“可直接交给人逐条处置的漏洞列表”明显过大、精度不足。它反映了检测器的候选语义和规则粒度尚不适合直接用作产品级漏洞统计，不能仅凭数量判定每条都是误报或断言代码开发质量差。

## 数量集中在哪里

NULL 检测器候选最多的仓库为：Linux kernel 6.6（235,109）、third_party_u-boot（89,608）、device_soc_hisilicon（87,896）、third_party_mingw-w64（45,435）。这四个仓库合计 458,048 条 NULL 候选，约占总明细的 82.11%。它们是代码量很大的 C/C++ 仓库，因而候选行数会显著放大。仓库内按源位置计数，跨仓库的相同/复制源码也没有在这张明细表中做全局合并；行数不能解释成互不相同的漏洞根因数。

## 为什么 NULL 候选会多

代码和运行报告共同给出以下边界：

- Catalog 将 NULL 检测器注明为默认关闭，理由是“unknown-return nullability produces broad weak candidates”，并要求先在有界范围复审。
- 规则版本为 A-NULL-01 v0.2.0，采用有界的同函数 C/C++ 词法分析；不是完整控制流图、支配关系、类型/别名、宏、模板、异常或构建上下文分析。
- 报告状态为 `blocked`，候选为 `unassessed`，要求 A-NULL-01 EvidenceObligation gate；`validated_vulnerability=0`。
- 样例的候选成因包括 `parameter_may_be_null` 和 `function_return_value_unknown_nullability`，命中形状包括 unary/method dereference。报告本身明确说语法证据不能证明解引用会失败、输入受攻击者控制、产品路径可达或存在 CIA 影响。

因此，主要原因可以确定为：A 线 NULL 候选规则覆盖面和不确定性边界过宽，且大规模运行把候选直接逐条列出；目前统计不足以给 546,559 条逐一判真伪。本报告不推断它们全是误报。

## 是否正常、开发是否不够细致

对“研究阶段、fail-closed 的候选生成”来说，出现大数量可以预期，尤其本次显式启用了 Catalog 已提示会产生宽泛弱候选的 NULL 检测器。对“成熟扫描器直接给人的漏洞清单”来说，这个规模不正常：需要先降噪、合并和分级，再谈识别率与产品价值。较准确的评价是 NULL 检测器当前规则精度/证据门槛还不够细，不代表 A/B 所有检测器都同样粗糙。

当前 8 个非 NULL 检测器合计 11,309 条也仍然是候选，需要抽样复核；其中 A 线其它规则 11,109 条，B 线（ArkTS/JS + IPC）200 条。数量少不代表更准确或更完整。

## 建议的改进顺序

1. **分开默认扫描与研究扫描**：默认配置继续遵循 Catalog，暂不默认启用 NULL；另提供显式 `--profile broad-candidate` 一类研究模式，并在 UI/报表醒目标为“弱候选”。
2. **先做候选聚类和分层**：按 finding identity、函数、根因表达式、文件、规则源类型聚类，展示簇数和代表样本；保留全部 occurrence 可追溯，避免把多处调用/解引用压成一条后丢证据。跨仓库复制代码再用 source hash/AST fingerprint 做单独的重复簇视图。
3. **提高 NULL 规则证据门槛**：把参数“可能为空”和未知返回值拆成不同规则/置信档；优先要求可证明的 nullable 来源或失败返回值、同函数路径上缺少有效 guard、并有实际解引用 sink。补全控制流支配、赋值/别名、返回值注解与项目内包装函数模型；不能证明时保留 unknown，不升级为强候选。
4. **做可复核精度实验**：从不同语言、代码规模和候选密度仓库分层抽样，人工标注 true/false/unknown 与原因；记录每规则精度、unknown 率和解析覆盖率。没有标注数据前，不要用 46 万行宣称召回率或漏洞发现能力。
5. **改善大仓库输出**：增加基于诊断量/序列化体积的自适应切分、流式报告、规则级开关和候选上限/告警；超预算必须报告 unknown/partial，不能显示成零候选。
