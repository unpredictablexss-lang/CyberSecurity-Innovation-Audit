# OHScanner 运行性能审查（人类阅读版）

- 审查日期：2026-10-14
- 代码基线：`main` 的 `60052bd`

**项目当前代码可以编译、测试、构建和运行；性能稳定。**

但 Docker 隔离 PoC 和一项依赖历史基线的 IPC 回归还没有真正跑完，所以不能说“全部竞赛验证都完成”。

## 性能重点

- 每轮扫描总量：`9,508` 个文件、约 `107 MB` 源码、约 `262 万` 行。
- 两轮总墙钟：`111.30 秒` 和 `110.90 秒`。
- 最大内存：`266.3 MB`。
- 最大组件是 `window_window_manager`：约 `35.1 秒`、`266.3 MB`，使用 7 个分片。
- 平均吞吐约 `86 个文件/秒`。
- 两轮总耗时只差 `0.40 秒`，说明本机性能波动不大。

## 哪些地方还不能下结论

### 1. Docker 动态验证没有运行

当前机器没有 Docker 或 Podman。AUTH-01 的两个 PoC 测试按项目安全边界被跳过。

这不是测试失败，但也不等于 PoC 已验证。要完成竞赛级证据，还需要在隔离容器里执行并保存触发效果、命令、环境和 sanitizer 结果。

### 2. owner IPC 历史对照缺少输入

`scripts/verify_owner_ipc_components.py` 需要一套历史基线 JSON。当前仓库里没有这套输入，脚本启动后找不到文件。

所以本轮不能把历史文档里的候选数量当成新的验证结果。需要补齐固定基线产物，或者把它们设计成可重建输入。

### 3. npm 安装较慢，并有构建脚本提示

`npm ci` 花了约 7.6 分钟，并提示 `esbuild` 的 postinstall 没有被 allowScripts 规则覆盖。构建成功，但后续应固定 Node/npm 版本并审查安装脚本。

## 怎么理解测试里的“0 个候选”

`0 个候选` 只表示这次检测器没有输出诊断。报告同时显示有 30 个部分解析文件和若干限制，因此：

- 不能说组件安全；
- 不能说没有漏洞；
- 不能把 `completed_with_limitations` 当作完整无风险。

## 最终判断

- **工程状态：可运行、可构建、性能可重复。**
- **证据状态：静态和集成验证完成；动态 PoC、owner IPC 历史复核和外部工具对照仍缺。**

下一步优先级：

1. 准备 Docker-only 验证环境，跑 AUTH-01 PoC；
2. 固定并入库/生成 owner IPC 基线输入；
3. 固定 Node/npm 版本，处理 `esbuild` 安装脚本策略；
4. 再补充真实漏洞动态证据、影响版本和修复重验。
